# 003. 主キーに UUIDv7 を使い、DB で生成する

## ステータス

承認。データモデルの設計（`../architecture/data-model.md`）で採用した。

この決定は、PostgreSQL 18 以降を使う判断を前提にする。18 未満の PostgreSQL に縛られた場合は、「見直す条件」に従う。

## コンテキスト

### 決めること

全テーブルの主キーの型と、値を作る場所を決める。

### 本デモの事情

相互アクセス型のマルチテナントでは、ID がテナントの外へ出る。

- **イベントが ID を運ぶ**：出荷実績 ID・請求書 ID・発注明細 ID は、イベントに乗って相手テナントのテーブルに保存される。
- **相手テナントが ID を目にする**：発注側は、出荷実績と受領請求書の ID を GraphQL で受け取る。
- **ID で参照し、外部キーを張らない**：コンテキストをまたぐ参照は ID 列だけで持つ（`../architecture/context-map.md`「疎結合を守る規則」）。

連番の ID が相手に渡ると、2 つの値の差から受注側の取引量を推し量れる。テナントをまたいで連番が共有されていれば、他社との取引量まで漏れる。

主キーには、索引の局所性も求められる。値が無作為に散らばると、B-tree の挿入位置がばらつき、ページの分割とキャッシュの取りこぼしが増える。

## 決定

- 全テーブルの主キーを `uuid` 型にし、値は UUIDv7 にする。
- 値は DB で作る。マイグレーションでは `create_table ..., id: :uuid, default: -> { "uuidv7()" }` と書く。`uuidv7()` は PostgreSQL 18 の組み込み関数である。
- 外部キーの列と、他コンテキストを指す ID 列も `uuid` 型にする。

UUIDv7 は、先頭 48 ビットにミリ秒単位の時刻を持つ。そのため、値は作った順に並び、索引の挿入位置は末尾に集まる。残りのビットは無作為なので、隣り合う値から他の値を推し量れない。

## 結果

### 得られるもの

- ID から取引量が漏れない。
- 新しい行の挿入が索引の末尾に集まり、連番に近い挿入性能が出る。
- ID の順で並べると、おおむね作成順になる。
- イベントやシードの ID を、DB に問い合わせずに作れる。テストで固定の ID を使う場合も、形式を揃えられる。

### 引き受けるコスト

- 主キーと外部キーの索引が、`bigint` の 2 倍の 16 バイトになる。
- 先頭の時刻部分から、行を作ったおおよその時刻が読める。本デモでは、作成時刻を相手に知られても困る ID は無い。
- `uuidv7()` は PostgreSQL 18 以降にしか無い。

### 見直す条件

- デプロイ先の PostgreSQL が 18 未満に縛られる → 値をアプリで作る（Ruby 3.3 以降の `SecureRandom.uuid_v7` を、基底モデルの `before_create` で入れる）。列の型は変わらない。
- 作成時刻を相手に知られることが問題になる ID が現れる → その表だけ UUIDv4 にする。

## 代替案

### A. `bigint` の連番

索引が最も小さく、Rails の既定である。しかし、相手テナントに渡る ID から取引量が漏れる。「相手には渡さない内部 ID と、公開用の ID」を二重に持つ方法もあるが、どの列を外に出してよいかの判断が、イベント・GraphQL・ジョブの全箇所に散らばる。

### B. UUIDv4

ID から取引量は漏れない。しかし値が無作為で、索引の挿入位置が散らばる。本デモは小さいので性能差は表に出ないが、v7 を選んで失うものは無い。

### C. アプリで UUIDv7 を作る

PostgreSQL のバージョンに依存しない。しかし、生 SQL やコンソールで行を足すときに ID を自分で作る必要がある。DB の既定値なら、どの経路でも同じ値の形になる。「見直す条件」に当たったときの退路として残す。

## 確認した事項

- Rails 8.1 の `structure.sql` は、ダンプと読み込みを経ても `DEFAULT uuidv7()` をそのまま保つ。`spec/db/uuidv7_default_spec.rb` が、テスト DB の列の既定値と、作った行の UUID のバージョンを確かめる。

> PostgreSQL 18.6・pg_dump 18.6・Rails 8.1.4 で、`db:schema:load` の後の `db:schema:dump` が `structure.sql` に差分を出さないことを確かめた。
