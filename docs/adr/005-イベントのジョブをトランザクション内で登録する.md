# 005. イベントのジョブを、業務のトランザクションの中で登録する

## ステータス

承認。イベントの登録と受信の仕組み（`../handoff.md`「次にやること」）で採用する。

この決定は、Solid Queue を業務 DB と同じ DB・同じ接続に置くことを前提にする。キューを別の DB や Redis に移す場合は、「見直す条件」に従う。

## コンテキスト

### 決めること

コンテキスト間のイベント（`packs/contracts` の `Contracts::` に定義する）は、ジョブに載せて受け手へ運ぶ。このジョブを、発行元の業務データと同じトランザクションの中で登録するか、コミットの後に登録するかを決める。

### 本デモの事情

イベントを 1 件失うと、2 社の伝票が食い違ったまま戻らない。「発注登録」を失えば受注が作られず、「検収完了」を失えば請求されない。受け手の冪等キー（`../architecture/data-model.md`「イベントの受け口と冪等キー」）は重複には効くが、欠落には効かない。

ジョブの登録の時機は、Active Job の `enqueue_after_transaction_commit` でジョブのクラスごとに決まる。

- **`true`**：登録を `ActiveRecord.after_all_transactions_commit` に回し、コミットの後に行う。ロールバックした操作のジョブは登録されない。一方、コミットと登録の間でプロセスが落ちると、ジョブを失う。
- **`false`**：`perform_later` を呼んだ時点で登録する。キューの表が業務データと同じ接続にあれば、ジョブの行は業務データと同じトランザクションで書かれる。コミット前の行はワーカーから見えないので、ロールバックすればジョブも消え、コミットすればジョブも必ず残る。キューが別のストアにあれば、コミット前に投入され、ロールバックした操作のジョブが走る。

Rails 8 の既定の構成は、キューを業務 DB と別の DB に置く。既定のまま始めると、`false` にしても同じトランザクションには入らない。

> rails v8.0.2・v8.1.0 の `activejob/lib/active_job/enqueuing.rb` は、`enqueue_after_transaction_commit` をクラス属性（既定値 `false`）として定義する。アプリ全体の設定 `config.active_job.enqueue_after_transaction_commit` は v8.0.2 で非推奨になり、v8.1.0 の `activejob/lib/active_job/railtie.rb` では読まれなくなった。v8.1.0 の `enqueue_after_transaction_commit.rb` は値を真偽で評価するので、`:never` のような記号は `true` として働く。キューの DB は、v8.1.0 のアプリの雛形 `config/databases/postgresql.yml.tt` が production に `queue` を作り、solid_queue の `lib/generators/solid_queue/install/install_generator.rb` が `config.solid_queue.connects_to = { database: { writing: :queue } }` を書き込む。solid_queue の README は、同じ DB に置く手順を「Single database configuration」に示し、同じ DB に置くとトランザクションの一体性が得られることを「Jobs and transactional integrity」に書いている。

## 決定

1. **Solid Queue を業務 DB と同じ DB に置く。** `database.yml` に `queue` の DB を作らず、`config.solid_queue.connects_to` を設定しない。`SolidQueue::Record` は `ActiveRecord::Base` の接続をそのまま使う。キューの表は、Solid Queue の `db/queue_schema.rb` を通常のマイグレーションに写して作り、`structure.sql` に載せる（`001`）。アダプタ（`config.active_job.queue_adapter = :solid_queue`）は `config/application.rb` に書き、全環境で同じにする。
2. **`ApplicationJob` は `self.enqueue_after_transaction_commit = true` にする。** イベントを運ばないジョブは、キューの置き場所にかかわらずコミットの後に登録される。
3. **イベントを運ぶジョブは、基底クラス `EventJob`（`ApplicationJob` を継承する）から作り、`self.enqueue_after_transaction_commit = false` にする。** 発行元の公開 API は、業務データを書くのと同じトランザクションの中で `perform_later` を呼ぶ。サブクラスはこの設定を上書きしない。`EventJob` には `limits_concurrency` を付けない。受け手の排他は、冪等キーと行ロックで取る。
4. **ガードテスト（`spec/jobs/event_job_atomicity_spec.rb`）を初日に置く。** 次の 3 つを CI で確かめる。
   - トランザクションの中で、`SolidQueue::Record.connection` と `ActiveRecord::Base.connection` が同じ接続である。
   - `EventJob` と、そのすべてのサブクラスの `enqueue_after_transaction_commit` が `false` である。
   - アダプタを `:solid_queue` にして、トランザクションの中で `EventJob` を登録してからロールバックすると、`solid_queue_jobs` に行が残らない。
5. **Solid Queue の表は、テナントの表として扱わない。**
   - `owner_tenant_id` を持たせず、RLS を付けない。テナント列の列挙テストの除外宣言に「Solid Queue の表。全テナントのジョブを 1 つのキューで扱う基盤で、引数はテナント ID と伝票の ID だけを運ぶ」と書く。
   - 主キーは Solid Queue のスキーマのまま（`bigint`）にする。UUIDv7 の規則（`003`）の対象外である。
   - アプリの DB ロールに、Solid Queue の表と連番への参照・書き込みの権限を与える。ワーカーはテナントを設定せずにキューを読むので、RLS を付けると 1 件もジョブを取れなくなる。

## 結果

### 得られるもの

- **業務データが確定すれば、イベントのジョブも必ず存在する。** outbox の表と、そこからジョブを送り出すプロセスが要らない。
- **戻した操作のイベントは届かない。** 失敗を返す公開 API がセーブポイントまで戻すと（`../architecture/graphql-schema.md`「エラー」）、その中で登録したイベントのジョブも一緒に戻る。
- **受け手の処理と、その先のイベントも一体になる。** 受注側の ACL が「発注登録」を受けて受注を作り「受注確定」を出す場合、受注の行と次のジョブが同じトランザクションで確定する。

### 引き受けるコスト

- **キューを別の DB に移すと、この性質は黙って失われる。** `EventJob` が `false` のまま移すと、コミット前の投入になり、ロールバックした操作のイベントが届く。ガードテストの 1 つ目が CI でこれを落とす。
- **ジョブの表への書き込みが、業務 DB の負荷になる。** ポーリングと完了したジョブの削除も業務 DB で行う。
- **ジョブはコミットまで動かない。** GraphQL のリクエスト全体を 1 つのトランザクションで包むので（`../architecture/graphql-schema.md`「1 回のリクエストがたどる道」）、イベントの配送はリクエストが終わるまで始まらない。

### 見直す条件

- **ジョブの流量が業務 DB を圧迫し、キューを別の DB か Redis に移す。** `EventJob` を `true` に戻し、イベントの発行を transactional outbox（業務 DB の表に書き、別のプロセスが投入する）に切り替える。`../architecture/decisions.md` 5 章の 2 条件に当たる。
- **Rails がジョブのクラスごとの `enqueue_after_transaction_commit` を廃止する。** 同じトランザクションで登録する別の手段（Solid Queue の API を直接呼ぶなど）を、`Contracts::` の発行口 1 か所に閉じ込める。

## 代替案

### A. すべてのジョブをコミットの後に登録し、outbox を置かない

不採用。設定は `ApplicationJob` の 1 行で済む。しかし、コミットと登録の間でプロセスが落ちるとイベントを失い、2 社の伝票が食い違う。失ったことに気づく手段も無い。

### B. コミットの後に登録し、イベントの経路にだけ transactional outbox を置く

不採用。キューの置き場所に依存しない。しかし、キューが業務 DB と同じ接続にあるなら、ジョブの表そのものが outbox の役を果たす。outbox の表と送り出しのプロセスを二重に持つことになる。キューを別の DB に移すときの退路として残す。

### C. Rails 8 の既定どおりキューの DB を分け、`false` で登録する

不採用。キューの DB への書き込みは業務のトランザクションに入らないので、コミット前の投入になる。業務のトランザクションが例外で戻っても、イベントは受け手に届く。

## 未確認の事項

- RSpec の job テストでアダプタが `:test` に差し替わる範囲。ガードテストの 3 つ目が `:solid_queue` のアダプタで動くことを、最初の実装で確かめる。
- Solid Queue の表に RLS を付けない構成で、アプリと同じ DB ロールのワーカーがジョブを取り出せること。ロールの権限の付け方とあわせて、最初の実装で確かめる。
- `EventJob` を置くパッケージ。`ApplicationJob` はルートパッケージにあり、各コンテキストのパッケージから継承できるかは packwerk の依存の宣言による。実装計画の「イベントの登録と受信の仕組み」で決める。
