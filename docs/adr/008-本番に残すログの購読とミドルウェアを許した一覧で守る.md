# 008. 本番に残すログの購読とミドルウェアを、許した一覧との一致で守る

## ステータス

承認。値を文字列のまま書くフレームワークの経路は、実行時には拒否の一覧で止めたままにし、本番の環境に残る購読とミドルウェアの並びが許した一覧と一致することを spec で確かめる。

裏返る条件：CI の spec を通らずに依存が本番へ入る経路ができたら、実行時に許した一覧の外の購読を外す形（代替案 A）に変える。

## コンテキスト

### 決めること

本番のログは 1 行が 1 件の JSON で、値を文字列のまま `Rails.logger` に書くフレームワークの経路を、書式に頼らずに止めている（`../guides/config.md`「止めたフレームワークの文字列のログ」）。止め方は、購読 4 つとミドルウェア 2 つを名指しで外す拒否の一覧である。

拒否の一覧は、Rails・Solid Queue・Ruby の版に結び付く。依存を上げて、値を文字列で書く購読かミドルウェアが新しく加わると、名指ししていないので止まらない。そこで、依存を上げたときに新しい経路を誰が・どう見つけるかを決める。

### 本デモの事情

- 依存の更新は、`bundle update` か Dependabot の PR で入り、どちらも CI の rspec を通ってからマージする。
- これまでのログの衛生の spec は、外した購読とミドルウェアが無いことだけを見ていた。新しく加わった購読は、名指ししていないので落ちない。
- 本番は全コードを先に読み込み（`eager_load = true`）、読み込んだ時点で購読が付く。テストの環境は CI でだけ全コードを読み込むので、テストの環境の購読の集合は手元と CI で違う。

## 決定

1. **実行時の止め方は、拒否の一覧のままにする。** `Platform::Logging.configure!` が名指しの購読とミドルウェアを外す。
2. **本番の環境に残るものを、許した一覧と完全に一致させる spec を置く。** `spec/platform/logging_spec.rb` が子のプロセスで本番の環境を初期化し、`ActiveSupport::LogSubscriber.log_subscribers` のクラスの集合、`Rails.event` の購読者、ミドルウェアの並びを、それぞれ許した一覧と比べる。増えても減っても落ちる。
3. **一覧に足すのは、値を文字列で書くかを読んでからにする。** spec が落ちたら、増えた購読かミドルウェアのソースを読み、値を文字列で書くなら拒否の一覧に足して止め、書かないなら許した一覧に足す。止めたものは `../guides/config.md`「止めたフレームワークの文字列のログ」の表に書く。

## 結果

### 得られるもの

- **依存を上げた PR で、新しい経路が CI で落ちる。** 誰かが変更点を読むことに頼らずに、読むべき購読とミドルウェアの名前が spec の失敗に出る。
- **実行時の振る舞いが、名指しした分だけに限られる。** 外す購読が増えても減っても、`configure!` を読めば何を止めているかが分かる。

### 引き受けるコスト

- **依存を上げるたびに、一覧の差分を読む手間がかかる。** 文字列を書かない構造化の購読（`*::StructuredEventSubscriber`）が増えたときも落ちるので、読んでから一覧に足す。
- **購読とミドルウェアの外の経路は拾わない。** `ActiveSupport::Notifications` を直接購読してログに書くものと、gem の中から `Rails.logger` を直接呼ぶものは、一覧に出ない。これらは依存の更新の PR で、変更点を読んで見る。

### 撤退コスト

小さい。spec の 1 つの example を、外した購読とミドルウェアが無いことだけを見る形に戻せば、元の拒否の一覧の検査に戻る。

### 見直す条件

- CI の spec を通らずに依存が本番へ入る経路ができる。実行時に止める形（代替案 A）に変える。
- 購読とミドルウェアの外の経路で、値を文字列で書くものが見つかる。その経路も一覧で比べる対象に足す。

## 代替案

### A. 実行時に、許した一覧の外の購読をすべて外す

不採用。原則出さない形で、新しい購読は名指ししなくても止まる。しかし止められるのは `ActiveSupport::LogSubscriber` の購読だけで、ミドルウェアと `Rails.logger` の直接の呼び出しは止まらないので、ミドルウェアの並びを確かめる spec は結局要る。依存の更新はすべて CI の spec を通るので、spec で落とせば、実行時に止める仕組みを二重に持たずに済む。

### B. 拒否の一覧の spec のまま、依存の更新の PR で変更点を読む

不採用。新しい購読が加わっても spec は通るので、見つかるかどうかが、読む人が変更点の中から該当の箇所を拾えるかに懸かる。

## 確認した事項

- Ruby 3.3.3 と 3.4.11 で、本番の環境の購読の集合とミドルウェアの並びを比べた。Rails 8.1.4・Solid Queue 1.7.0 は Gemfile の版の制約の中の最新で、`bundle update` で変わらなかった。違いは、使っていない部品を外して消えた Active Storage の購読 2 つだけで、増えたものは無かった。

> 本番の環境（`RAILS_ENV=production`）を初期化し、`ActiveSupport::LogSubscriber.log_subscribers`・`Rails.event.subscribers`・`Rails.application.middleware` を出力して比べた（上げる前は `b2e8f2a`、上げた後は `e0035e9`）。
