# 004. GraphQL は 1 つのスキーマで型を視点ごとに分け、汎用の `node` を置かない

## ステータス

承認。GraphQL のスキーマ設計（`../architecture/graphql-schema.md`）で採用する。

この決定は、GraphQL 層をルートパッケージに置き、各コンテキストの公開 API だけを使う判断（`../architecture/context-map.md`「疎結合を守る規則」5）を前提にする。

## コンテキスト

### 決めること

1 つのテナントが、ある取引では発注側、別の取引では受注側になる。GraphQL で両方の視点をどう表すかを決める。あわせて、ID から任意のレコードを引く入口（Relay の `node(id:)`）を置くかを決める。

### 本デモの事情

GraphQL は、型のフィールドをたどって別のデータへ届く。発注の型に受注へのフィールドが 1 つでもあれば、発注側は相手の受注・在庫・対応表へたどれてしまう。本デモの見せどころの 1 つは、この経路が無いことである（`../handoff.md`「目的」）。

`decisions.md` 2 章は、同じデータを「自社として見る」と「取引先として見る」で見せ方が変わるとき、次のどちらかを初月に決めるよう求めている。

- 視点ごとに型を分ける
- 1 つの型にフィールド単位の認可を入れる

本デモでは、相手テナントのデータを読む経路が 3 つに限られている（カタログ・取引関係・自社の発注に連結した出荷）。相手側の型で見せるべきフィールドは、受注側の型のごく一部である。

`node(id:)` は、ID さえ分かれば型を問わずレコードを返す。相互アクセス型では、イベントで渡った ID（出荷実績 ID・請求書 ID）を相手テナントが持っている。そのため、`node` を置くと、型の経路とは別の入口から相手のデータへ届く穴になる。

## 決定

1. スキーマは 1 つ、エンドポイントは `/graphql` の 1 つにする。
2. ルートの `Query` に、視点ごとの入口 `buyer: BuyerView!` と `supplier: SupplierView!` を置く。各視点の読み取りはこの下にだけ置く。
3. 型は視点ごとに分け、各型に視点（`buyer`・`supplier`・`shared`）を宣言させる。相手テナントのデータを返す型は、受注側の型を流用せず、発注側の視点の型として別に作る（`PublishedCatalogItem`・`SupplierPartnership`・`SupplierShipment`）。
4. `shared` の型は、スカラーと enum と他の `shared` の型だけをフィールドに持つ。
5. 型の到達可能性をテストで固定する。`Query` のフィールドは `viewer` と 2 つの視点の入口に限り、`Mutation` のフィールドは視点を宣言した mutation に限る。`BuyerView` と発注側の mutation の戻り値からたどれる型は、`buyer` か `shared` に限る。`SupplierView` 側も同様にする。
6. `node` と `nodes` のフィールドを置かない。スキーマの `object_from_id` を実装せず、呼ばれたら例外にする。ID でレコードを引くフィールドは、各視点の下に型ごとに置き（`buyer.purchaseOrder(id:)` など）、公開 API の policy scope を通す。

## 結果

### 得られるもの

- **相手側へたどれないことを、テストで確かめられる。** 到達可能性のテストが、発注側の型から受注側の型へのフィールドを 1 本でも足した時点で落ちる。
- **相手側のデータを返す型が一覧になる。** 3 つの型だけが相手テナントのデータを返し、それぞれが読む経路の 1 つに対応する。
- **ID の推測で相手へ届かない。** ID からレコードを引く入口は、すべて視点と型が決まったフィールドで、policy scope を通る。

### 引き受けるコスト

- **同じ業務の物が複数の型になる。** 出荷実績は、受注側の `Shipment`、発注側の `SupplierShipment`（経路 3）、購買の写しの `InboundShipment` の 3 つの型になる。
- **Relay の `node` に頼るクライアント機能が使えない。** 再取得には、視点ごとの ID 指定のフィールドを使う。フロントエンドは factory-ops-demo の Next.js を流用し、Relay を前提にしないので影響は小さい。
- **到達可能性のテストを保守する。** 型を足すたびに視点の宣言が要る。宣言の無い型は、テストと実行時の両方で拒否される。

### 見直す条件

- **取引先システムなど、発注側だけのクライアントが現れた場合。** 発注側のスキーマを別に切り出し、エンドポイントを分ける。型が視点ごとに分かれているので、切り出しは型の移動で済む。
- **相手テナントのデータを読む経路が増え、相手側の型が受注側の型とほぼ同じになった場合。** 型を分ける利点が薄れるので、フィールド単位の認可へ寄せることを検討する。

## 代替案

### A. 視点ごとにスキーマとエンドポイントを分ける

不採用。分離はスキーマの構造で保証され、到達可能性のテストは要らない。しかし、認証・テナントの設定・クエリの上限・基底クラスを 2 つのスキーマで共有する仕組みが別に要る。フロントエンドも 2 つのスキーマからコードを生成することになる。1 つのスキーマでも到達可能性は CI で同じ強さで確かめられるので、分ける利点がコストに見合わない。

### B. 1 つの型にフィールド単位の認可を入れる

不採用。たとえば `Shipment` 型を両方の視点で使い、受注側だけのフィールドに認可を付ける。型のグラフ上は、発注側から受注側のデータへのフィールドが存在することになり、守りがフィールドごとの認可の付け忘れの有無に依存する。「たどれない」ことを型の構造で示せない。

### C. `node(id:)` を置き、解決時に policy scope を通す

不採用。scope を正しく通せば漏れはしない。しかし、型を問わない入口が 1 つ増え、その入口の正しさを全型について確かめるテストが要る。本デモのクライアントは `node` を使わないので、置かないほうが守る面が小さい。
