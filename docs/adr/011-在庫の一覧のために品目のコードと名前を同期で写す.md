# 011. 在庫の一覧のために、品目のコードと名前を在庫へ同期で写し、写しの抜けを一致の spec で守る

## ステータス

承認。受注の公開 API が、品目を書くのと同じトランザクションで在庫の公開 API `Inventory::ItemLabels.put` を呼び、品目のコードと名前を在庫のパッケージの写しの表（`item_labels`）に書く。写しに外部キーは張らず、写しを保つ経路と元から作り直すタスクが同じ写しを作ることを、一致の spec で確かめる。

裏返る条件：品目の保存を、在庫の書き込みの失敗や遅れから切り離す必要が出る。在庫の行を作る経路が、品目の保存を経ない形で増える（「見直す条件」）。

## コンテキスト

### 決めること

作者は、在庫の画面を品目のコードと名前で並べ、品目で検索することを、サーバーで行うと決めた（`../plans/open-items.md` の OI-144）。在庫の一覧は 1 ページずつ読むので、並べ替えと検索は在庫の一覧を読む SQL の中で行う。品目のコードと名前は受注のコンテキストの品目の表にあるので、次の 2 つを決める。

- 品目のコードと名前を、在庫の SQL にどう渡すか
- 写しを持つなら、写しの抜けを何で守るか

### 本デモの事情

- 受注は在庫の公開 API（`Inventory::Allocation`）にすでに依存している。在庫が受注に依存すると循環になるので、受注の取引先の名前（`010` 決定 2）と違い、在庫は受注の公開 API が返す副問い合わせを結べない。
- 品目のコードか名前を書く受注の公開 API は、品目の保存（`Sales::Catalog.save`）と取り込みの品目の書き込み（`Sales::Catalog.bulk_upsert`）の 2 つだけで、mutation・品目の CSV の取り込み・シードと E2E の世界（`DemoWorld`）はどれもこの 2 つを呼ぶ。品目は消さない。
- 在庫の行は、品目の保存より後の入出庫か引当で作られる。在庫の spec と factory の多くは、品目を作らずに乱数の品目 ID で在庫を作る。
- 公開の配置の migrate の Job は、未適用のマイグレーションを 1 回で流す（`009`）。データの移行はマイグレーションに入れない（`001` 決定 4）。

## 決定

1. **受注の公開 API が、品目を書くのと同じトランザクションで在庫の公開 API を呼んで写す（同期）。** `Sales::Catalog.save` と `Sales::Catalog.bulk_upsert` が、書いた品目のコードと名前で `Inventory::ItemLabels.put` を呼ぶ。`put` は操作者を取らず、テナントの設定を求め、所有テナントを `Current` のテナントで明示して upsert し、足した数と書き直した数だけを返す。衝突の対象は所有テナントと品目 ID の組の一意索引なので、他社の写しには当たらない。値の同じ写しは書き直さない。元から作り直す `Sales::Catalog.rebuild_item_labels`（rake タスク `read_models:rebuild` が呼ぶ）は、自社の品目を品目コードの順に `FOR SHARE` で読んでから同じ `put` を呼ぶ。保存と取り込みは品目の行ロックを取るので、作り直しが古い名前を読んだ後に保存が新しい名前の写しを書き、作り直しがそれを古い名前で上書きする順は起きない。在庫の一覧は、写しを所有テナントと品目 ID の組で外部結合して並べ、絞る。
2. **写しに外部キーを張らず、一致の spec で写しを書く経路の抜けを捕まえる。** `spec/scenarios/read_model_copies_spec.rb` が、`DemoWorld` の E2E の世界を作った後と、品目を `saveItem` と品目の CSV の取り込みで変えた後に作り直しのタスクを流し、どのテナントも足した数と書き直した数が 0 であることを確かめる。写しの無い在庫は、一覧で消さずに、品目のコードと名前で並べると最後に置き、検索には当てない。

## 結果

### 得られるもの

- **写しは品目と同じトランザクションでコミットされる。** 古い名前で並ぶ間も、届く順の入れ替わりも無い。在庫の引当と同じく、同じテナントの中の値を同じトランザクションで書く（`../architecture/context-map.md`「コンテキスト間の関係」）。
- **在庫の一覧は在庫のパッケージの表だけで並び、絞る。** 受注の表の名前と列が在庫に出ず、写しの列に索引を張れる。
- **在庫の spec と factory は、品目と写しを作らずに書ける。** 写しの無い在庫は一覧の最後に並ぶだけで、拒まれない。

### 引き受けるコスト

- **品目の保存が在庫の表への書き込みを含む。** 写しの書き込みが失敗すると、品目の保存も失敗する。
- **写しを書く経路を足した人が `put` を呼び忘れると、一覧が古い名前で並ぶ。** 一致の spec が `DemoWorld` の全経路で捕まえるが、`DemoWorld` を通らない経路は捕まえない。
- **既存の DB の写しは、マイグレーションの後に作り直しのタスクを流すまで空である。** その間は、在庫の品目のコードと名前での並べ替えと検索が当たらない。

### 撤退コスト

- 決定 1 は中。品目の変更のイベントと、在庫の受け手と、届く順を比べる品目の版の列を足す（代替案 A）。
- 決定 2 は小。外部キーを `NOT VALID` で張り、作り直しの後に検証するマイグレーションを置く（代替案 B）。

### 見直す条件

- 品目の保存を、在庫の書き込みの失敗や遅れから切り離す必要が出る（在庫を別の DB に分ける、品目の取り込みの 1 回の件数が増えて同じトランザクションに収まらない） → 代替案 A に移る。
- 在庫の行を作る経路が、品目の保存を経ない形で増える（品目を別の入口で作る、在庫を先に作る取り込み） → 代替案 B に移る。

## 代替案

### A. 受注が「品目の変更」のイベントを出し、在庫の受け手が写す（非同期）

不採用。品目の保存が在庫の書き込みから切り離される。しかし、在庫に `contracts` の依存を足し、届く順が入れ替わっても古い名前で上書きしないよう、品目に版の列を足して受け手が比べることになる。写しが届くまでの間は、在庫の一覧の並びと検索が古い名前で動く。作者は、同期で写す形を選んだ（`../plans/open-items.md` の OI-189）。

### B. 在庫の行から写しへの外部キーを張り、写しの無い在庫を DB が拒む

不採用。写しの抜けを DB が止める。しかし、在庫の spec の多くは品目を作らずに乱数の品目 ID で在庫を作るので、20 を超える spec のファイルに写しを置く補助が要る。既存の DB では、写しを埋める前に外部キーを張れず、公開の配置の migrate の Job が止まる。

### C. 在庫の一覧で並べ替えと検索をせず、品目の一覧から在庫を引く

不採用。受注の一覧は在庫を一括で引けるが、在庫の安全在庫の絞り込みと品目の検索を同じページで重ねると、ページの中だけを絞ることになり、並びと件数が嘘になる（`010` 代替案 C と同じ）。

## 確認した事項

> `spec/scenarios/read_model_copies_spec.rb` で、`Sales::Catalog.bulk_upsert` か `Sales::Catalog.save` から `put` の呼び出しを外すと、世界を作った後の作り直しが 0 でない数を返して落ちた。`packs/sales/spec/concurrency/sales/item_labels_rebuild_lock_spec.rb` で、`rebuild_item_labels` の `FOR SHARE` を外すと、作り直しが読んだ古い名前が保存の後の写しに残って落ちた。

`put` は Active Record の `upsert_all` に、衝突の後の更新の SQL（`on_duplicate:`）と返す列（`returning:`）を渡して組む。`on_duplicate:` に SQL を渡すと、`upsert_all` はそれを `ON CONFLICT (...) DO UPDATE SET` の後にそのまま置き（activerecord 8.1.4 の `connection_adapters/postgresql_adapter.rb` の `build_insert_sql`）、`updated_at` を足すのは `on_duplicate: :update` のときだけである（同じ版の `insert_all.rb` の `touch_model_timestamps_unless`）。そのため `updated_at` も SQL に書く。足した行は `xmax = 0` で見分ける（`Sales::Catalog.bulk_upsert` と同じ形）。
