# 010. 状況の導出を SQL の式 1 つにし、別のコンテキストの値は scope を掛けた副問い合わせで渡す

## ステータス

承認。受注・発注・出荷依頼の状況を、各コンテキストの状況のモジュールが返す SQL の `CASE` 式 1 つで導出し、Ruby の導出を消した。受注の式が読む在庫の引当数量は、在庫の公開 API が scope を掛けた後に SQL の文字列にした副問い合わせ（`SqlSubquery`）で渡す。受注・発注・出荷依頼の一覧を取引先の名前で並べるときも、取引関係の公開 API が返すテナントの名前の副問い合わせを結び、名前を伝票に写さない。

裏返る条件：導出表のどれかの行を 1 つの SQL の式で書けなくなるか、式を足した一覧がクエリ数の予算を超えるか、副問い合わせを結んだ一覧の SQL が遅くなって予算の spec の時間を大きく延ばす。テナントの名前を変える入口を足すか、テナントの表を別の DB に分ける（「見直す条件」）。

## コンテキスト

### 決めること

画面は、受注・発注・出荷依頼の一覧を状況のタブで分け、タブごとの件数を出し、1 ページずつ読む。ダッシュボードは受注の状況ごとの件数を出し、そこから一覧へ飛ぶ。状況は保存せず、時刻列と子の行から導出する（`../architecture/data-model.md`「状態は保存せず、時刻列から導出する」）ので、次の 2 つを決める。

- 一覧を読む SQL の中で状況を絞り、数えるために、導出をどこに書くか
- 受注の状況が読む引当数量は在庫の表にある。別のコンテキストの値を、受注の SQL の中へどう渡すか
- 作者は、一覧を取引先の名前で並べることを求めた。名前は取引関係のテナントの表にある。名前を伝票の側に写すか、副問い合わせで結ぶか

### 本デモの事情

- 導出はこれまで Ruby の `derive` にあり、行を読んだ後でしか状況が決まらなかった。ダッシュボードの件数は全件を読んで Ruby で数えていた。
- 公開 API は値を返し、AR のモデルと relation をパッケージの外に出さない（`002`「AR モデルは公開しない」）。packwerk は定数の参照しか見ないので、relation を受け取った側が何を呼ぶかは止められない。
- 受注はすでに在庫の公開 API（`Inventory::Allocation`）に依存している。在庫は受注に依存しない。
- 公開 API は所有の条件を RLS に任せず、policy の scope を自分で掛ける（`../architecture/graphql-schema.md`「認可：宣言の無い型・リゾルバ・mutation は拒否する」）。
- テナントの表は RLS も所有テナントも無い表で、名前を変える入口が無い（`Partnerships::Onboarding.register` が作るだけ）。受注・購買・出荷はどれも取引関係に依存している。

## 決定

1. **状況の導出を、導出表と同じ優先順の SQL の `CASE` 式 1 つにする。** `Sales::SalesOrderStatus`・`Purchasing::PurchaseOrderStatus`・`Fulfillment::ShipmentRequestStatus` が式（Arel のノード）を返す。公開 API の一覧・1 件は行と一緒にこの式を読み、状況の絞り込みは同じ式の `IN`、ダッシュボードの件数は同じ式の `GROUP BY`、出荷期限は同じ式の絞り込みで行う。受注の取消は、取消できるかを時刻列（取消済か出荷済か）で決め、取消の前に「出荷可能」を出していたか（引当済だったか）を、ロックした受注の状況をこの式で読んで決める。取消できるかを時刻列で決めても、CHECK 制約（取消済と出荷済を同時に持たない、検収は出荷の後）があるので、式の取消済・検収済・出荷済で除くのと同じ結果になる。Ruby の `derive` は置かない。
2. **別のコンテキストの値は、相手の公開 API が scope を掛けた後に SQL の文字列にし、列の名前と一緒に値で返す。** 在庫の公開 API `Inventory::Allocation.active_quantities_sql(actor)` が、操作者の scope を掛けた「受注明細 ID と有効な引当数量」の副問い合わせを `SqlSubquery`（`packs/platform`）で返し、受注の式はそれを外部結合するだけにする。条件（解除した引当を除く）は、明細の引当数量を返す `Inventory::Allocation.quantities_for` と同じ relation から作る。受け取る側は、在庫の表の名前と列を書かない（列の名前は値が持つ）。取引先の名前も同じ形で渡す。取引関係の公開 API `Partnerships::Directory.tenant_names_sql(actor)` が、テナントの ID と名前だけの副問い合わせを返し、取引用コードを含めない。操作者が取引関係の操作者であることは確かめるが、scope は掛けない。テナントの表は RLS も所有テナントも無く、名前は取引の相手にすでに見せている値で、結ぶ側の伝票の相手のテナント ID で 1 行に絞られるからである。受注・購買・出荷の一覧は、副問い合わせから伝票の相手のテナント ID の行の名前を、行ごとに 1 つ引くスカラーの副問い合わせ（`SqlSubquery#lookup`）で並べる。外部結合にしないのは、結ぶ条件を書き誤って 2 行以上が当たったときに、伝票の行が黙って増えずに SQL のエラーになり、ページと件数が同じ relation のまま並べ替えの式だけで済むからである。
3. **式の中で子の行を読む副問い合わせは、親の行と同じ所有テナントの行だけを読む。** 所有テナントと親の組の外部キーがある表（受注明細・入荷・検収・出荷指示・出荷実績）は、外部キーがそれを守る。外部キーの無い出荷停止（受注の ID を参照するだけ）は、式が所有テナントを出荷依頼にそろえる。
4. **入口の行列で捕まらない scope の抜けは、式の側の単体が RLS を開いて確かめる。** 他社の引当と出荷停止は他社の親を指し、自社の親には結ばれないので、副問い合わせから scope を外しても、RLS を開いた入口の行列の比較は変わらない。`allocation_spec.rb` と `shipment_request_status_spec.rb` が、共有の文脈「RLS の SELECT と UPDATE を開く」で他社の名義で自社の親を指す行を作り、引当数量と状況に入らないことを確かめる（`../guides/testing.md`「行列テストとの分担」）。

## 結果

### 得られるもの

- **表示・絞り込み・件数と、取消の前に出荷可能を出していたかの判定が同じ式を読む。** 導出表を変えたときに直す箇所が 1 つで、ダッシュボードの数と、そこから飛ぶ一覧の件数が食い違わない。
- **件数だけを読む問い合わせが、行を読まない。** タブの件数は、状況の式で絞った `COUNT(*)` の 1 つの SQL で済む。
- **在庫の scope と書き込みの入口が、受注のパッケージに出ない。** 受け取るのは文字列と列の名前だけなので、条件を外すことも書き込むこともできない。
- **取引先の名前で並べても、名前の写しと、写しを書く入口が要らない。** 並びと画面に出す名前（`Partnerships::Directory.tenants`）が同じ表を読むので、食い違わない。

### 引き受けるコスト

- **状況の spec が DB を使う。** 式は DB でしか評価できないので、導出表の行ごとに行を作って絞る。Ruby の値を渡すだけの spec より遅い。
- **副問い合わせの文字列は、受け取った時点の scope で固まる。** 受け取る側が操作者を変えても、文字列は変わらない。公開 API は呼ぶたびに作り直す。
- **SQL の文字列を結ぶので、静的解析が SQL の埋め込みを警告しうる。** `Arel.sql` で包んだ Arel のノードとして結び、Brakeman が警告を出したら `config/brakeman.ignore` に指紋と、値が scope を掛けた公開 API の戻り値だけであるという理由を書く。

### 撤退コスト

- 決定 1 は中。3 つの状況のモジュールに Ruby の導出を戻し、件数と取消の可否を元の読み方に戻す。絞り込みの引数は、状況ごとの SQL の条件（代替案 A）で残せる。
- 決定 2 は小。値と公開 API を 1 つ消し、受注の式を受注明細 ID の配列で引当数量を受け取る読み方（代替案 C）に戻す。取引先の名前は、副問い合わせの公開 API を 1 つ消し、並べ替えの enum の値を非推奨にする。

### 見直す条件

- 導出表のどれかの行を、1 つの SQL の式で書けなくなる → 代替案 A に移る。
- 式を足した一覧がクエリ数の予算を超えるか、副問い合わせを結んだ一覧の SQL が遅くなり、予算の spec の時間を大きく延ばす → 引当の有無を受注の側に写す列を足し、受け手で写しを保つ。
- テナントの名前を変える入口を足すか、テナントの表を別の DB に分ける → 取引先の名前を代替案 D の写しにする。名前を変える入口なら、取引関係から名前の変更のイベントを出し、受注・購買・出荷の受け手が写しを書き直す（取引関係に `contracts` の依存を足す）。

## 代替案

### A. Ruby の導出を残し、状況ごとの SQL の条件を足して、両者の一致を spec で確かめる

不採用。いまの導出のコードを変えずに済むが、同じ意味を 2 か所に持つ。一致の spec は世界にある状況の組み合わせしか確かめないので、片方だけを直しても通ることがある。

### B. 在庫の公開 API が relation をそのまま返す

不採用。受け取る側が `unscope`・`rewhere`・`update_all` を呼べ、在庫の scope と書き込みの入口がコンテキストの境界を越える。packwerk はこれを止められない。

### C. 受注明細 ID の配列を受け取り、引当数量を返す（これまでの `quantities_for` だけ）

不採用。行を読んだ後でしか状況が決まらず、SQL の中で絞り込めない。1 ページずつ読む一覧で状況のタブを分けると、ページの中だけを絞ることになり、並びと件数が嘘になる。

### D. 受注・購買・出荷に、取引先ごとの名前の写しの表を置き、伝票を作るトランザクションで写す

不採用。一覧が自分のパッケージの表だけで並び、名前の列に索引を張れる。しかし、3 つのパッケージに写しの表と、写しを書く入口（伝票を作る 3 か所）と、既存の行を埋める作り直しが要る。テナントの名前は変わらず、テナントの表に RLS も所有テナントも無いので、写しを持っても守る値が増えない。

## 確認した事項

> `c38eea2` で、3 つの状況の spec が導出表の行ごとに 1 件ずつ作った行を `statuses` で絞り、その 1 件だけが返ることを確かめた。式の優先順の隣り合う 2 つを入れ替えると、両方の条件に当たる行の example が落ちた（取消済と出荷済、受注側による取消と取消済は、DB の CHECK 制約で同時に持てないので組まない）。`bin/brakeman` は警告を出さず、`config/brakeman.ignore` は足していない。

式は Arel のノードで組み、次の振る舞い（activerecord 8.1.4 の `lib/arel/`）に依存する。`Arel::Nodes::Case#when`・`#then`・`#else` は、文字列の値を `Arel::Nodes.build_quoted` で引用する（`nodes/case.rb`）。`Arel::Nodes::TableAlias#[]` は、別名を表の名前にした列を返す（`nodes/table_alias.rb`）。`Arel::Nodes::NamedFunction` は、関数の名前と引数をそのまま並べる（`visitors/to_sql.rb` の `visit_Arel_Nodes_NamedFunction`）。`In` に空の配列を渡すと `1=0` を書く（同じファイルの `visit_Arel_Nodes_In`）ので、`statuses` の空の配列は 0 件になる。
