# 007. 非同期処理の型を、ジョブを失ったときの影響で選ぶ

## ステータス

承認。外部サービスの呼び出し（`../implementation-plan.md` M28）と大量データの取り込み（M29）で実装する。コンテキスト間のイベント（`005`）は、この決定の型の 1 つとして含める。

この決定は、Solid Queue を業務 DB と同じ DB・同じ接続に置くこと（`005` 決定 1）を前提にする。

## コンテキスト

### 決めること

非同期で行う処理ごとに、次の 4 つを決める。

- ジョブを登録する時機（業務のトランザクションの中か、コミットの後か）
- 再試行の回数と間隔
- 重複して実行されたときに結果を 1 つにする方法（冪等の取り方）
- 再試行を使い切ったときの扱い

処理ごとに個別に決めると、同じ種類の処理が別々の保証で作られ、読む人がジョブごとに保証を調べ直すことになる。そこで処理を場面で型に分け、型ごとに仕組みを 1 つに決める。

### 本デモの事情

本デモの非同期処理は、次の 5 つの場面に分かれる。

| 場面 | 例 | ジョブを失ったとき |
|---|---|---|
| テナントをまたぐ業務の連結 | 発注登録・出荷計上・請求書発行 | 2 社の伝票が食い違ったまま戻らない。誰も気づかない |
| 失うと困る外部への通知 | 発注側の `admin` への「請求書が届きました」のメール | 支払いの手配が遅れる。発注側も受注側も、届かなかったことに気づかない |
| 失ってもよい外部への通知 | 受注側の担当者への「新しい受注」のお知らせメール | 受注は画面の一覧に出るので、業務は進む |
| 外部からの通知の受け取り | SendGrid のイベント Webhook（配信・不達・拒否） | 送信記録の状態が古いまま残る |
| 重い一括処理 | 品目・単価・在庫の CSV の取り込み（数万行） | 取り込みが「待機中」のまま進まない。利用者は画面で気づき、やり直せる |

外部のメール配信サービス SendGrid には、次の性質がある。

- **送信の API は冪等キーを受け付けない。** 同じ送信を 2 回呼べば、2 通届く。
- **流量の上限を超えると 429 を返す。** 待つべき時間をヘッダで示す。
- **イベント Webhook は、同じイベントを複数回送ることがある。** イベントごとに一意の ID（`sg_event_id`）を持つ。

## 決定

### 1. 型の選び方と一覧

非同期の処理を足す人は、作る前に次の問いに上から順に答え、最初に当てはまった型で作る。どれにも当てはまらない処理が要るときは、この ADR を改めてから作る。

1. **処理のきっかけは外部から届くか。** Webhook のように、相手が送り直すかどうかを自社が決められない入力である。→ inbox
2. **1 回の実行が長く、ワーカーの停止やデプロイをまたぐか。** → 再開できる長時間のジョブ
3. **作用先は自社の DB で、別のテナントか別のコンテキストの業務データを書くか。** → トランザクション内のイベント
4. **作用先は外部のサービスで、失ったときに利用者も運用者も気づけず、業務が止まるか。** → 確実な外部送信
5. **作用先は外部のサービスで、失っても画面など別の経路で業務が進むか。** → 撃ちっぱなし

| 型 | 採用する条件 | 保証 | 仕組み |
|---|---|---|---|
| inbox | きっかけが外部から届き、相手が送り直すかを自社が決められない。受け取った時点では宛先のテナントや処理の可否が決まらない | 受け取ったイベントは必ず残る。処理は少なくとも 1 回、結果は 1 つ | 受信の表 `webhook_inbox_events`（提供元のイベント ID で一意）に生のまま書いてすぐ応答し、ジョブと定期のジョブが後から処理する |
| 再開できる長時間のジョブ | 1 回の実行が分の単位を超え、途中で止まっても最初からやり直すと無駄が大きい。利用者が進み具合を画面で見られる | 途中で止まっても、終えたチャンクを捨てずに続きから再開する。行の結果は 1 つ | Active Job Continuations、チャンクごとのトランザクション、専用のキュー |
| トランザクション内のイベント | 自社の業務データの確定に合わせて、別のテナントか別のコンテキストの業務データを書く。失うと 2 つの伝票が食い違ったまま戻らない | 業務データが確定すればジョブも必ずある。受け手は少なくとも 1 回動き、結果は 1 つ | `Contracts::EventJob`（トランザクションの中で登録）、受け手ごとの冪等キー（`005`） |
| 確実な外部送信 | 外部のサービスへの作用で、失うと誰も気づけず業務が止まる。相手のサービスに冪等キーが無い | 業務データが確定すれば送信記録とジョブも必ずある。少なくとも 1 回送る。送信を受け付けられた後は送り直さない。再試行を使い切ったら運用者に知らせる | 送信記録 `email_deliveries`（通知キーで一意）と `Notifications::CriticalDeliveryJob`（トランザクションの中で登録）、429 の待ち時間に従う再試行、`limits_concurrency` |
| 撃ちっぱなし | 外部のサービスへの作用で、失っても画面など別の経路で業務が進む | 業務データが確定した後に、届けようとする。失っても誰にも知らせない | `Notifications::BestEffortMailJob`（コミットの後に登録）、少ない回数の再試行の後に捨てる |

型を選ぶときに取り違えやすいのは、次の 3 つである。

- **確実な外部送信と撃ちっぱなしは、送り先ではなく通知の種類で分ける。** 同じ SendGrid へのメールでも、失ったときの影響で型が変わる。
- **コンテキスト間のイベントの受け手は、inbox にしない。** ジョブを登録するのが自社の業務のトランザクションなので、ジョブの行が受け取りの記録を兼ねる。重複は受け手が書く表の冪等キーで捨てる。
- **外部からの通知を、受け取ってすぐジョブに積むだけでは inbox にならない。** Solid Queue のジョブには提供元のイベント ID で重複を捨てる一意の制約が無く、処理を終えたジョブは残らないので、後から受け取った内容を確かめて処理し直せない。受信の表を別に持つのは、この 2 つのためである。

transactional outbox は、どの型にも使わない。キューが業務 DB と同じ接続にあるので、ジョブの表そのものが outbox の役を果たす（`005`）。確実な外部送信の送信記録は outbox ではない。別のプロセスが読み出して送り出すことはなく、重複を避けることと、Webhook の結果を書き戻すことのための状態の記録である。

### 2. 登録の時機は「失ったことに誰かが気づけるか」で決める

ジョブの基底クラスの作成者は、次の規則で `enqueue_after_transaction_commit` を決め、基底クラスに明示する（`../architecture/decisions.md` 5 章）。

- **ジョブを失ったとき、利用者も運用者も気づけないなら、トランザクションの中で登録する（`false`）。** イベントと確実な外部送信がこれに当たる。
- **気づけて、やり直せるなら、コミットの後に登録する（`true`）。** 撃ちっぱなし・inbox のきっかけのジョブ・取り込みがこれに当たる。inbox は受信の表の行が残るので、ジョブを失っても定期のジョブが拾う。取り込みは、取り込みの行が「待機中」のまま残り、画面に出る。

`false` にしたクラスは、`spec/jobs/event_job_atomicity_spec.rb` を広げたガードテストが、キューの接続が業務 DB と同じであることと合わせて確かめる。

### 3. 外部へ作用するジョブは `ExternalEffectJob` を継承し、登録口を 1 つにする

- **基底クラス**：`ExternalEffectJob`（`packs/platform`、`ApplicationJob` を継承）。サブクラスは、`enqueue_after_transaction_commit` と、保証（`external_effect :at_least_once` か `:best_effort`）を自分のクラスに書く。書かなければ、読み込みの時点で例外にする。
- **登録口**：外部への作用は、`Notifications::Email.deliver_critical` と `deliver_best_effort`（`packs/notifications` の公開 API）だけが登録する。カスタム Cop `FactoryOps/ExternalEffectEnqueue` が、`ExternalEffectJob` のサブクラスの `perform_later`・`perform_now`・`set` と、Action Mailer の `deliver_later` を、この公開 API のファイルの外で禁止する。
- **呼び出し元は通知の種類ごとに 1 か所**：通知の種類は `Notifications::Catalog` に登録する。`spec/notifications/call_sites_spec.rb` が `packs/` を走査し、通知の種類ごとに `deliver_*` の呼び出しが 1 か所だけで、登録された種類であることを確かめる。再送や手動の再実行のために 2 か所目の呼び出しを足すと、このテストが落ちる（`decisions.md` 5 章）。

### 4. 確実な外部送信

1. 呼び出し元（「請求書発行」の購買の受け手）は、業務データを書くのと同じトランザクションで `Notifications::Email.deliver_critical(:received_invoice, key:, ...)` を呼ぶ。公開 API は送信記録の行を書き、ジョブを登録する。通知キー（例：`received_invoice:<受領請求書 ID>`）は所有テナントの中で一意で、同じイベントが 2 回届いても送信記録は 1 件になる。
2. ジョブは送信記録の行をロックし、受け付けの時刻（`accepted_at`）があれば何もしない。無ければ宛先を読み、SendGrid に送る。宛先のメールアドレスは送信記録に保存せず、送るときに自社の `users` から引く。
3. 応答の扱いは次のとおり。

   | 応答 | 扱い |
   |---|---|
   | 202 | `accepted_at` と提供元のメッセージ ID を書く |
   | 429 | 応答が示す待ち時間の後に、もう一度登録する。待ち時間は 1 時間で頭打ちにする。回数は他の再試行と合わせて数える |
   | 5xx・タイムアウト・接続の失敗 | 間隔を延ばしながら再試行する（`retry_on ... wait: :polynomially_longer, attempts: 8`） |
   | 400・401・403・413 | 再試行しない。`failed_at` と理由を書き、運用者に知らせる。401・403 は自社の設定の誤りなので、他の送信も止まっている |
   | 再試行を使い切った | `failed_at` と理由を書き、運用者に知らせる |

   「運用者に知らせる」は、`Rails.event` に `notification.delivery_failed` を出すことである。ログとメトリクスの経路（M18・M30）が、これを警報にする。
4. SendGrid に冪等キーが無いので、ちょうど 1 回の送信は保証しない。SendGrid が受け付けた後、`accepted_at` をコミットする前にプロセスが落ちると、再実行で 2 通目が送られる。この隙間はロックの内側の数ミリ秒で、受け入れる。

### 5. 撃ちっぱなし

`Notifications::BestEffortMailJob` はコミットの後に登録し、送信記録を作らない。5xx・タイムアウトと 429 を 3 回まで再試行し、使い切ったら警告のログを出して捨てる（`discard_on`）。運用者には知らせない。

### 6. inbox

1. SendGrid のイベント Webhook は `POST /webhooks/sendgrid/events` に届く。コントローラは、署名と時刻を検証し、合わなければ 401 を返す。
2. 検証を通った配列の各イベントを、`webhook_inbox_events` に `insert_all` で書く。`(provider, provider_event_id)` の一意で、2 回目に届いたイベントは捨てる。書く前に、ペイロードからメールアドレスを取り除く。書き終えたら 200 を返す。
3. コミットの後に `Notifications::ProcessInboxJob` を登録する。1 分ごとの定期のジョブ（`config/recurring.yml`）も、未処理の行を拾う。
4. 処理は、未処理の行を `FOR UPDATE SKIP LOCKED` で取り、送信のときに付けた `custom_args` のテナント ID で `Tenancy.with_tenant` を開き、送信記録の時刻列（`delivered_at`・`bounced_at`・`dropped_at`）を空のときだけ書く。最後に `processed_at` を書く。送信記録が見つからないイベントは、`processed_at` を書いて捨てる。
5. 受信の表はテナントの表ではない。届いた時点ではテナントが決まらないからである。テナント列の列挙テストの除外宣言に理由を書き、処理を終えた行は 30 日で消す。

### 7. 再開できる長時間のジョブ

1. 取り込みのジョブは `ActiveJob::Continuable` を取り込み、「置き場へ写す」「反映する」「締める」の 3 つの段階（step）に分ける。各段階は、カーソル（処理を終えた行の番号）を進めながらチャンクごとに処理する。
2. `ApplicationJob` は実行全体を `Tenancy.with_tenant` のトランザクションで包むが、取り込みのジョブはこれを使わない。Continuations は、トランザクションが開いたままの中断点で `ActiveJob::Continuation::CheckpointError` を投げるからである。取り込みのジョブは `tenant_transaction :per_chunk` を宣言し、チャンクごとに `Tenancy.with_tenant` を開く。
3. Solid Queue は停止の合図（`stopping?`）を Continuations に伝えるので、デプロイでワーカーが止まると、ジョブは次の中断点で止まり、続きから再登録される。プロセスが落ちて中断点を通らなかった場合は、最後に保存したカーソルからやり直す。そのため、チャンクの処理は、同じ行を 2 回反映しても結果が 1 つになるように書く。

### 8. キューとワーカーを、型ごとに分ける

重い処理が、イベントの配送を待たせないようにする。`config/queue.yml` に、キューごとに別のワーカーを置く。

| キュー | 載せるジョブ | ワーカーのスレッド | 同時実行の上限 |
|---|---|---|---|
| `events` | `Contracts::EventJob` | 3 | 付けない（`005` 決定 3） |
| `external_mail` | `CriticalDeliveryJob`・`BestEffortMailJob` | 2 | 2 つのクラスで合わせて 2（`limits_concurrency key: "sendgrid", group: "sendgrid"`） |
| `imports` | 取り込みのジョブ | 1 | テナントごとに 1 |
| `default` | inbox の処理・定期のジョブ・その他 | 2 | — |

各ワーカーのプロセスの DB の接続プールは、そのスレッド数より大きくする。

## 結果

### 得られるもの

- **ジョブを読む人は、型を見れば保証が分かる。** ジョブごとに再試行と冪等の取り方を調べ直さなくてよい。
- **失ったことに気づけない処理だけが、トランザクションの中で登録される。** `false` の基底クラスが増え続けない。
- **外部への作用の呼び出し元が、通知の種類ごとに 1 か所に保たれる。** 二重送信の経路を足すと CI が落ちる。
- **重い取り込みが走っていても、イベントの配送とメールは自分のワーカーで進む。**

### 引き受けるコスト

- **確実な外部送信でも、SendGrid の受け付けと記録のコミットの間で落ちると、2 通届く。** 提供元が冪等キーを持たない限り、閉じられない。
- **ワーカーの数が増える。** キューごとのワーカーは、1 つの `*` のワーカーより接続とプロセスを多く使う。
- **inbox の表は RLS の外にある。** メールアドレスを取り除いてから書き、30 日で消す。

### 撤退コスト

小さい。型は基底クラスとキューの設定の組なので、ある処理の型を変えるのは、継承する基底クラスと `queue_as` を変える作業で済む。高くつくのは、型を決めずにジョブを書き溜めた後で揃え直すことで、ジョブごとに既存の重複と欠落を調べることになる。

### 見直す条件

- **キューを業務 DB と別の DB か Redis に移す。** トランザクションの中で登録する型（イベント・確実な外部送信）を、コミットの後の登録と transactional outbox に切り替える（`005`「見直す条件」）。
- **メールの提供元が冪等キーを受け付けるようになる、または提供元を替える。** 通知キーを冪等キーとして渡し、決定 4 の 4 の隙間を閉じる。
- **429 が続き、ジョブごとの待ち時間では送信が詰まる。** 提供元の単位で送信を止める仕組み（止める時刻を共有する行）を足す。それまでは、運用者が `external_mail` のキューを止める（`../implementation-plan.md` M31 の手順書 `sendgrid-outage.md`）。
- **取り込みの行が互いに依存する（親の品目と子の行を同じファイルで送る）。** 行ごとに独立に反映する方式をやめ、ファイル全体を 1 つの結果にする（`../implementation-plan.md` M29 の判断）。

## 代替案

### A. すべての非同期処理を、イベントと同じトランザクション内の登録にする

不採用。仕組みは 1 つで済む。しかし撃ちっぱなしの通知まで、業務のトランザクションの成否と結び付ける理由が無い。`false` の基底クラスは、キューを別の DB に移すときにすべて見直しになるので、少ないほうがよい。

### B. 外部への送信に transactional outbox を置く

不採用。キューが業務 DB と同じ接続にある間は、ジョブの表が outbox を兼ねる。outbox の表と送り出しのプロセスを二重に持つことになる。

### C. Action Mailer の `deliver_later` をそのまま使う

不採用。`ActionMailer::MailDeliveryJob` は `ExternalEffectJob` を継承しないので、登録口の制限と送信記録の外に出る。テンプレートは Action Mailer で書き、送信はジョブの中で `deliver_now` を呼ぶ。

## 未確認の事項

- SendGrid の 429 が待ち時間を示すヘッダの名前（`Retry-After` か `X-RateLimit-Reset` か）。両方を読み、無ければ再試行の間隔に従う形で実装し、着手時に SendGrid の文書で確かめる。
- SendGrid の署名付きイベント Webhook の、署名と時刻のヘッダの名前と、署名の方式。
- SendGrid の送信の API が、冪等キーを受け付けないこと。受け付けるなら、決定 4 の 4 を改める。

## 確認した事項

- **Continuations とトランザクション**：Rails 8.1 の `ActiveJob::Continuation` は、DB のトランザクションが開いたままの中断点で `CheckpointError` を投げる。中断点は、段階の始まりと、カーソルを進めるたび（`step.advance!`・`step.set!`・`step.checkpoint!`）に置かれる。
- **Solid Queue の停止の合図**：solid_queue 1.7.0 のアダプタは `stopping?` を実装し、ワーカーの停止を Continuations に伝える。
- **同時実行の上限の共有**：solid_queue 1.7.0 の `limits_concurrency` は `group:` を受け取り、別のクラスのジョブで同じ上限を共有できる。

> Rails 8.1.3 の API 文書（`ActiveJob::Continuation`・`ActiveJob::Continuation::CheckpointError`）と、手元の solid_queue 1.7.0 の `lib/active_job/queue_adapters/solid_queue_adapter.rb`・`lib/active_job/concurrency_controls.rb` で確かめた。
