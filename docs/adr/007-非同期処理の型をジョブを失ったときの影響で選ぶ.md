# 007. 非同期処理の型を、ジョブを失ったときの影響で選ぶ

## ステータス

承認。外部サービスの呼び出し（`../implementation-plan.md` M28）で A-2・A-3・B-1 と決定 4・7 を実装し、大量データの取り込み（M29）で A-4 を実装した。コンテキスト間のイベント（`005`）は、この決定の型 A-1 として含める。外部への作用の扱いのうち C-3 は、規則として定めるだけで、本デモでは実装しない。

この決定は、Solid Queue を業務 DB と同じ DB・同じ接続に置くこと（`005` 決定 1）を前提にする。

## コンテキスト

### 決めること

非同期で行う処理ごとに、次の 4 つを決める。

- ジョブを登録する時機（業務のトランザクションの中か、コミットの後か）
- 再試行の回数と間隔
- 重複して実行されたときに結果を 1 つにする方法（冪等の取り方。外部への作用では、重複を閉じるか受け入れるか）
- 再試行を使い切ったときの扱い

処理ごとに個別に決めると、同じ種類の処理が別々の保証で作られ、読む人がジョブごとに保証を調べ直すことになる。そこで処理を場面で型に分け、型ごとに仕組みを 1 つに決める。

### 本デモの事情

本デモの非同期処理は、次の 5 つの場面に分かれる。

| 場面 | 例 | ジョブを失ったとき |
|---|---|---|
| テナントをまたぐ業務の連結 | 発注登録・出荷計上・請求書発行 | 2 社の伝票が食い違ったまま戻らない。誰も気づかない |
| 失うと困る外部への通知 | 発注側の `admin` への「請求書が届きました」のメール | 支払いの手配が遅れる。発注側も受注側も、届かなかったことに気づかない |
| 失ってもよい外部への通知 | 受注側の担当者への「新しい受注」のお知らせメール | 受注は画面の一覧に出るので、業務は進む |
| 外部からの通知の受け取り | SendGrid のイベント Webhook（配信・不達・拒否） | 送信記録の状態が古いまま残る |
| 重い一括処理 | 品目・単価・在庫の CSV の取り込み（数万行） | 取り込みが「待機中」のまま進まない。利用者は画面で気づき、やり直せる |

外部のメール配信サービス SendGrid には、次の性質がある。

- **送信の API は冪等キーを受け付けない。** 同じ送信を 2 回呼べば、2 通届く。
- **流量の上限を超えると 429 を返す。** 待つべき時間をヘッダで示す。
- **イベント Webhook は、同じイベントを複数回送ることがある。** イベントごとに一意の ID（`sg_event_id`）を持つ。

## 決定

### 1. 型の体系と選び方

非同期の処理を足す人は、作る前に次の問いに上から順に答え、最初に当てはまった型で作る。どれにも当てはまらない処理が要るときは、この ADR を改めてから作る。

1. **処理のきっかけは外部から届くか。** Webhook のように、相手が送り直すかどうかを自社が決められない入力である。→ A-3
2. **1 回の実行が長く、ワーカーの停止やデプロイをまたぐか。** → A-4
3. **作用先は自社の DB で、別のテナントか別のコンテキストの業務データを書くか。** → A-1
4. **作用先は外部のサービスで、失ったときに利用者も運用者も気づけず、業務が止まるか。** → A-2。あわせて、外部への作用の重複の扱いを C から選ぶ（決定 6）
5. **作用先は外部のサービスで、失っても画面など別の経路で業務が進むか。** → B-1。重複の扱いは C から選ぶ（決定 6）

答えの型は、処理すべきことを先に記録するかで 2 つに大きく分かれる。

- **A. 記録してから処理する**：処理すべきことを DB の行として先に確定させ、ジョブが後からその行を取って処理する。ジョブを失っても、行が残るので処理すべきことは失われない。
- **B. 記録しない**：記録を作らず、ジョブだけを登録する。ジョブを失えば、処理すべきことも失われる。

| 型 | 採用する条件 | 保証 | 仕組み |
|---|---|---|---|
| A-1 トランザクション内のイベント | 自社の業務データの確定に合わせて、別のテナントか別のコンテキストの業務データを書く。失うと 2 つの伝票が食い違ったまま戻らない | 業務データが確定すればジョブも必ずある。受け手は少なくとも 1 回動き、結果は 1 つ | `Contracts::EventJob`（トランザクションの中で登録）、受け手ごとの冪等キー（`005`） |
| A-2 確実な外部送信 | 外部のサービスへの作用で、失うと誰も気づけず業務が止まる | 業務データが確定すれば送信記録とジョブも必ずある。少なくとも 1 回送る。再試行を使い切ったら運用者に知らせる | 送信記録 `email_deliveries`（通知キーで一意）と `Notifications::CriticalDeliveryJob`（トランザクションの中で登録）、429 の待ち時間に従う再試行、`limits_concurrency` |
| A-3 inbox | きっかけが外部から届き、相手が送り直すかを自社が決められない。受け取った時点では宛先のテナントや処理の可否が決まらない | 受け取ったイベントは必ず残る。処理は少なくとも 1 回、結果は 1 つ | 受信の表 `webhook_inbox_events`（提供元のイベント ID で一意）に処理に使う項目だけを書いてすぐ応答し、ジョブと定期のジョブが後から処理する |
| A-4 再開できる長時間のジョブ | 1 回の実行が分の単位を超え、途中で止まっても最初からやり直すと無駄が大きい。利用者が進み具合を画面で見られる | 途中で止まっても、終えたチャンクを捨てずに続きから再開する。行の結果は 1 つ | 取り込みの行とカーソル、Active Job Continuations、チャンクごとのトランザクション、専用のキュー |
| B-1 撃ちっぱなし | 外部のサービスへの作用で、失っても画面など別の経路で業務が進む | 業務データが確定した後に、届けようとする。失っても誰にも知らせない | `Notifications::BestEffortMailJob`（コミットの後に登録）、少ない回数の再試行の後に捨てる |

A-2 と B-1 は、外部を呼ぶので、同じ作用が 2 回起きうる。その扱いを、相手が冪等キーを持つかと、重複の代償で次の 3 つから選ぶ（決定 6）。

| 規則 | 選ぶ条件 | 重複の扱い |
|---|---|---|
| C-1 冪等キーを渡す | 相手が冪等キーを受け付ける | 自社の通知キーを渡し、相手に重複を捨てさせる。重複の隙間は閉じる |
| C-2 重複を受け入れる | 相手に冪等キーが無く、重複の代償が小さい（メール） | 受け付けの後、記録のコミットの前に落ちると 2 回起きる。この隙間を受け入れる。本デモの SendGrid はこれ |
| C-3 結果不明にして照会してから呼び直す | 相手に冪等キーが無く、重複の代償が大きい（決済など） | 呼ぶ前に「呼び出し中」を確定させ、再試行は相手に照会して成否を確かめてから呼び直すかを決める |

**A-2 と B-1 は、送り先ではなく通知の種類で分ける。** 同じ SendGrid へのメールでも、失ったときの影響で型が変わる。

### 2. A の型に共通する土台

A の型を作る人は、次の 6 つの部品をそろえる。型による違いは、各部品を何で作るかだけである。

| 部品 | A-1 イベント | A-2 確実な外部送信 | A-3 inbox | A-4 取り込み |
|---|---|---|---|---|
| 処理すべきことの行 | Solid Queue のジョブの行そのもの（記録の表を別に持たない） | 送信記録 `email_deliveries` | 受信の表 `webhook_inbox_events` | `imports`・`import_rows` とカーソル |
| 一意キーで重複を捨てる | 受け手が書く表の冪等キー | `(owner, notification_key)` | `(provider, provider_event_id)` | `import_file_id`・`(import_id, row_number)` |
| ジョブが行を取って処理する | Solid Queue がジョブを取り、受け手が自社の行をロックする | 送信記録の行をロックする | 未処理の行を `FOR UPDATE SKIP LOCKED` で取る | テナントごとに 1 つ（`limits_concurrency`）、チャンクごとに処理する |
| 完了の時刻を書く | 受け手が業務の行と時刻を書く | `accepted_at` | `processed_at` | 行ごとの `applied_at`、全体の `finished_at` |
| 取りこぼしを拾い直す | 再試行と、失敗したジョブのやり直し | 再試行と、再送の操作 | 登録したジョブと、1 分ごとの定期のジョブ | 中断点からの再登録と、再登録の操作 |
| 使い切ったら知らせる | 失敗したジョブがキューの警報に出る | `failed_at` を書き、運用者に知らせる | 処理のジョブの失敗がキューの警報に出る。未処理の行は定期のジョブが拾い続ける | 行の失敗と取り込み全体の失敗は、`error`・`failed_at` で画面の状況に出す。続きから登録し直されないジョブの例外は、失敗したジョブとしてキューの警報に出て、取り込みは「置き場へ写し中」か「反映中」のまま残る |

再送の操作と再登録の操作（`notifications:redeliver`・`imports:reenqueue`）は、新しい行を作らず、残っている行のジョブを登録し直す。行が残っていることが、A の型でジョブを拾い直せる根拠だからである。

### 3. 型どうしの違い

新しい処理が既存の型に当てはまるか迷った人は、次の表の各行に答え、答えがそろう列の型で作る。A の型どうしの違いは、表の太字の 4 つの軸で決まる。3-1〜3-4 で、各軸と、そこから決まる行を説明する。

| 観点 | A-1 イベント | A-2 確実な外部送信 | A-3 inbox | A-4 取り込み | B-1 撃ちっぱなし |
|---|---|---|---|---|---|
| きっかけ | 自社の業務データの確定 | 自社の業務データの確定 | 外部から届いた HTTP リクエスト | 利用者が取り込みを始める操作（`startImport`） | 自社の業務データの確定 |
| 向き | 自社 → 自社（別のテナントか別のコンテキスト） | 自社 → 外部 | 外部 → 自社 | 自社 → 自社 | 自社 → 外部 |
| 守るもの | 2 つの伝票が食い違わないこと | 送るべきものの漏れと、送り過ぎ | 届いたものの取りこぼしと、二重の処理 | 終えたチャンクを捨てずに続けること | 守らない。届けようとするだけ |
| **記録を書くトランザクション**（3-1） | 業務と同じ | 業務と同じ | 単独。届いた直後に確定させ、すぐ 200 を返す | 単独。取り込みを始める操作で確定させる | 記録を書かない |
| ジョブを登録する時機（3-1） | トランザクションの中 | トランザクションの中 | コミットの後 | コミットの後 | コミットの後 |
| **処理の作用先**（3-2） | 自社の DB | 外部 | 自社の DB | 自社の DB | 外部 |
| 冪等にできる範囲（3-2） | 全体 | 自社の側だけ。外部への作用は C で扱う | 全体 | 全体（行ごと） | 自社の側にも記録が無い。C-2 で扱う |
| **重複を判定する ID の持ち主**（3-3） | 自社（受け手の冪等キー） | 自社（通知キー） | 相手（提供元のイベント ID） | 自社（ファイルと行番号） | 判定しない |
| 記録の表を別に持つか（3-3） | 持たない。ジョブの行が記録 | 持つ | 持つ | 持つ | 持たない |
| 行を書く時点のテナント | 発行元。受け手はペイロードの宛先で動く | 決まっている（RLS の内側） | 決まらない（RLS の外） | 決まっている（RLS の内側） | 決まっている |
| **進み具合**（3-4） | 一括 | 一括 | 一括 | チャンクごと | 一括 |

#### 3-1. 記録を書くトランザクションと、登録の時機

ジョブの基底クラスの作成者は、「ジョブを失ったことに誰かが気づけるか」で `enqueue_after_transaction_commit` を決め、基底クラスに明示する（`../architecture/decisions.md` 5 章）。

- **気づけないなら、トランザクションの中で登録する（`false`）。** 記録を業務と同じトランザクションで書く A-1・A-2 がこれに当たる。A-1 はジョブの行が記録そのものなので、ジョブを失えば記録も失う。A-2 は送信記録が残っても、待機中の送信記録を拾い直すものが無いので、ジョブを失えば送信は始まらず、誰も気づかない。
- **気づけて、やり直せるなら、コミットの後に登録する（`true`）。** 記録を単独のトランザクションで確定させる A-3・A-4 と、記録を持たない B-1 がこれに当たる。A-3 は受信の表の行が残るので、ジョブを失っても定期のジョブが拾う。A-4 は取り込みの行が「待機中」のまま残り、画面に出る。

`false` にしたクラスは、`spec/jobs/event_job_atomicity_spec.rb` を広げたガードテストが、キューの接続が業務 DB と同じであることと合わせて確かめる。

A-1 と A-2 は、処理すべきことを業務と同時に確定させる点で、transactional outbox と同じ役を担う。outbox の表と、そこから送り出すプロセスは置かない。A-1 はジョブの表が outbox を兼ねる（`005`）。A-2 の送信記録は送信の意図の記録で、業務と同時に確定する点は outbox と同じだが、別のプロセスが読み出して送り出すのではなく、同じトランザクションで登録したジョブがその行を取って送る。送信記録は、重複を捨てることと、Webhook の結果を書き戻すことにも使う。

#### 3-2. 処理の作用先

作用先が自社の DB なら、受け手が書く表の一意キーで、同じ処理を 2 回流しても結果を 1 つにできる。作用先が外部なら、2 回目を捨てられるかは相手しだいなので、決定 6 の C から扱いを選ぶ。

#### 3-3. 重複を判定する ID の持ち主

ID が自社のものなら、処理する側の表の一意キーで重複を捨てられるので、受け取りの記録を別に持たなくてよい。**A-1 の受け手を inbox にしないのはこのためである。** ジョブを登録するのが自社の業務のトランザクションなので、ジョブの行が受け取りの記録を兼ね、重複は受け手が書く表の冪等キーで捨てる。

ID が相手のものなら、受け取った時点で相手の ID の一意制約で重複を捨てる表が要る。**外部からの通知を、受け取ってすぐジョブに積むだけでは A-3 にならない。** 受信の表を別に持つのは、次の 2 つのためである。

- Solid Queue のジョブの表には、提供元のイベント ID で重複を捨てる一意の制約が無い。
- ジョブの行を残す期間はキュー全体の設定で、受け取った内容を残す期間（30 日）を通知ごとに決められない。行の形も gem のものなので、受け取った内容の記録として使えない。

#### 3-4. 進み具合

A-1〜A-3 は、1 回の実行を 1 つのトランザクションで終える。A-4 は、チャンクごとにトランザクションを閉じ、進み具合をチャンクごとに記録する。途中で止まっても、記録した進み具合から続けるためである（決定 5 の A-4）。

### 4. 外部へ作用するジョブは `ExternalEffectJob` を継承し、登録口を 1 つにする

- **基底クラス**：`ExternalEffectJob`（`packs/platform`、`ApplicationJob` を継承）。サブクラスは、`enqueue_after_transaction_commit` と、保証（A-2 は `external_effect :at_least_once`、B-1 は `:best_effort`）を自分のクラスに書く。書かなければ、読み込みの時点で例外にする。
- **登録口**：外部への作用は、`Notifications::Email.deliver_critical` と `deliver_best_effort`（`packs/notifications` の公開 API）だけが登録する。カスタム Cop `FactoryOps/ExternalEffectEnqueue` が、`ExternalEffectJob` のサブクラスの `perform_later`・`perform_now`・`set` と、Action Mailer の `deliver_later` を、この公開 API のファイルの外で禁止する。
- **呼び出し元は通知の種類ごとに 1 か所**：通知の種類は `Notifications::Catalog` に登録する。`spec/notifications/call_sites_spec.rb` が `packs/` を走査し、通知の種類ごとに `deliver_*` の呼び出しが 1 か所だけで、登録された種類であることを確かめる。再送や手動の再実行のために 2 か所目の呼び出しを足すと、このテストが落ちる（`decisions.md` 5 章）。

### 5. 各型の手順

#### A-1 トランザクション内のイベント

`005` の決定 2〜6 に従う。受け手ごとの冪等キーは `../architecture/data-model.md`「イベントの受け口と冪等キー」に書く。

#### A-2 確実な外部送信

1. 呼び出し元（「請求書発行」の購買の受け手）は、業務データを書くのと同じトランザクションで `Notifications::Email.deliver_critical(:received_invoice, key:, ...)` を呼ぶ。公開 API は送信記録の行を書き、ジョブを登録する。通知キー（例：`received_invoice:<受領請求書 ID>`）は所有テナントの中で一意で、同じイベントが 2 回届いても送信記録は 1 件になる。
2. ジョブは送信記録の行をロックし、受け付けの時刻（`accepted_at`）があれば何もしない。無ければ宛先を読み、SendGrid に送る。宛先のメールアドレスは送信記録に保存せず、送るときに自社の `users` から引く。
3. 応答の扱いは次のとおり。

   | 応答 | 扱い |
   |---|---|
   | 202、sandbox mode の 200 | `accepted_at` と提供元のメッセージ ID を書く。メッセージ ID のヘッダが無ければ空のまま書く。sandbox mode は配信しないので、Webhook のイベントは届かず、送信記録は受付済のまま残る |
   | 429 | 応答が示す待ち時間の後に、もう一度登録する。待ち時間は `Retry-After`（秒）を先に、無ければ `X-RateLimit-Reset`（制限が戻る UNIX 時刻）から求め、1 秒から 1 時間に収める。どちらも無ければ 5xx と同じ間隔にする。回数は他の再試行と合わせて数える |
   | 5xx・タイムアウト・接続の失敗（TLS・ソケット・応答の読み取りの失敗を含む） | 間隔を延ばしながら再試行する。間隔は Active Job の `:polynomially_longer` と同じ式（実行の回数の 4 乗に 2 秒と揺らぎを足す）で、8 回目の実行で使い切る |
   | 400・401・403・413 | 再試行しない。`failed_at` と理由を書き、運用者に知らせる。401・403 は自社の設定の誤りなので、他の送信も止まっている |
   | 再試行を使い切った | `failed_at` と理由を書き、運用者に知らせる |

   「運用者に知らせる」は、`Rails.event` に `notification.delivery_failed` を出すことである。ログとメトリクスの経路（M18・M30）が、これを警報にする。

   再試行は `retry_on` で例外を上げずに、ジョブの中で送信記録の試行回数（`attempts`）を書いたトランザクションの中で、同じジョブを登録し直す（`retry_job`）。`ApplicationJob` は実行全体をテナントのトランザクションで包むので、例外を上げると送信記録への書き込みが戻り、試行回数も失敗の時刻も残らない。トランザクションの中で登録するので、試行回数と次の登録は一緒に確定する。

   送信の途中でワーカーのプロセスが落ちたときと、どの応答にも当たらない例外でジョブが失敗したときは、送信記録が待機中のまま残り、Solid Queue の失敗したジョブとエラー通知に出る。運用者は、原因を取り除いてから失敗したジョブをやり直す。待機中の送信記録は再送の操作（`redeliver_failed`）の対象にならない。
4. 重複の扱いは C-2 による（決定 6）。

#### A-3 inbox

1. SendGrid のイベント Webhook は `POST /webhooks/sendgrid/events` に届く。コントローラは、署名と時刻を検証し、合わなければ 401 を返す。署名は「時刻のヘッダの文字列 + 本文の生のバイト列」の SHA-256 に対する ECDSA で、公開鍵は credentials に置く。時刻は、受け取った時刻から前後 10 分の内でなければ拒む。SendGrid は送り直すたびに時刻を付け直して署名するので、送り直しはこの幅に入る。
2. 検証を通った配列の各イベントを、`webhook_inbox_events` に `insert_all` で書く。`(provider, provider_event_id)` の一意で、2 回目に届いたイベントは捨てる。ペイロードは、処理に使う項目（`sg_event_id`・`sg_message_id`・`event`・`timestamp` と、送信のときに付けた `custom_args` の `tenant_id`・`email_delivery_id`）だけを残す。宛先のメールアドレスと、不達の理由のようにアドレスを含みうる自由記述は残さない。書き終えたら 200 を返す。
3. コミットの後に `Notifications::ProcessInboxJob` を登録する。1 分ごとの定期のジョブ（`config/recurring.yml`）も、未処理の行を拾う。
4. 処理は、未処理の行を `FOR UPDATE SKIP LOCKED` で取り、送信のときに付けた `custom_args` のテナント ID で `Tenancy.with_tenant` を開き、送信記録をロックしてから、時刻列（`delivered_at`・`bounced_at`・`dropped_at`）を空のときだけ書く。同じ送信記録を指す別の行を別の処理が取っても、先に書いた時刻を上書きしない。最後に `processed_at` を書く。送信記録が見つからないイベントは、`processed_at` を書いて捨てる。
5. 受信の表はテナントの表ではない。届いた時点ではテナントが決まらないからである。テナント列の列挙テストの除外宣言に理由を書き、処理を終えた行は 30 日で消す。

#### A-4 再開できる長時間のジョブ

1. 取り込みのジョブは `ActiveJob::Continuable` を取り込み、「置き場へ写す」「反映する」「締める」の 3 つの段階（step）に分ける。各段階は、カーソル（処理を終えた行の番号）を進めながらチャンクごとに処理する。
2. `ApplicationJob` は実行全体を `Tenancy.with_tenant` のトランザクションで包むが、取り込みのジョブはこれを使わない。実行全体を包むと、終えたチャンクがジョブの終わりまでコミットされず、進み具合が画面に見えず、プロセスが落ちれば終えたチャンクも戻るからである。取り込みのジョブは `tenant_transaction :per_chunk` を宣言し、チャンクごとに `Tenancy.with_tenant` を開いて閉じ、中断点（カーソルを進める `set!`）はトランザクションの外に置く。activejob 8.1.4 の Continuations は、トランザクションが開いたままの中断点を拒まない（`ActiveJob::Continuation::CheckpointError` は定義だけで、投げる箇所が無い）ので、この置き方はコードの形で守る。
3. Solid Queue は停止の合図（`stopping?`）を Continuations に伝えるので、デプロイでワーカーが止まると、ジョブは次の中断点で止まり、続きから再登録される。プロセスが落ちて中断点を通らなかった場合は、最後に保存したカーソルからやり直す。そのため、チャンクの処理は、同じ行を 2 回反映しても結果が 1 つになるように書く。各段階は続きの位置をカーソルではなく置き場から作り直す（`stage` は置き場の最大の行番号の次から、`apply` は結果の無い最小の行番号から）ので、継続の情報を持たない新しいジョブ（`imports:reenqueue`）でも続きから進む。

#### B-1 撃ちっぱなし

`Notifications::BestEffortMailJob` はコミットの後に登録し、送信記録を作らない。5xx・タイムアウトと 429 を合わせて 3 回目の実行まで試し、使い切るか再試行しない応答なら、警告のイベント（`notification.best_effort_dropped`）を出して捨てる。運用者には知らせない。待ち時間の決め方は A-2 と同じである。重複の扱いは C-2 による（決定 6）。

### 6. 外部への作用の重複の扱い（C）

A-2 か B-1 のジョブの作成者は、作る前に、相手が冪等キーを受け付けるかと、同じ作用が 2 回起きたときの代償を調べ、C-1〜C-3 の 1 つを選ぶ。C-3 は送信記録の状態を使うので、記録を持たない B-1 では選べない。B-1 にした作用の重複の代償が大きいと分かったら、A-2 にして C-3 を選ぶ。

#### C-1 冪等キーを渡す

相手が冪等キーを受け付けるなら、A-2 の通知キーをそのまま冪等キーとして渡す。受け付けの後、記録のコミットの前に落ちて再実行しても、相手が 2 回目を捨てるので、重複の隙間は閉じる。

#### C-2 重複を受け入れる

相手に冪等キーが無く、重複の代償が小さいなら、ちょうど 1 回の作用は保証しない。相手が受け付けた後、`accepted_at` をコミットする前にプロセスが落ちると、再実行で 2 回目が起きる。この隙間は送信記録のロックの内側の短い間で、受け入れる。本デモの SendGrid のメールは、A-2・B-1 ともにこれを選ぶ。

#### C-3 結果不明にして照会してから呼び直す

相手に冪等キーが無く、重複の代償が大きいなら、呼び出しの結果が分からない行を「呼び出し中」として残し、確かめてから呼び直す。

1. ジョブは、相手を呼ぶ直前に記録の状態を `sending` にして、そのトランザクションをコミットする。相手を呼ぶときは、自社の ID（通知キーか記録の ID）を相手の参照番号の項目に入れる。
2. 応答を受けたら、結果を記録に書く。
3. 再試行のジョブは、`sending` の記録を見たら相手を呼び直さない。相手の照会の API で参照番号を引いて成否を確かめ、成功していれば結果を書き、相手に無ければ呼び直す。
4. 照会できない（照会の API が無い、照会しても結果が決まらない）ときは、呼び直さずに運用者の突合へ回し、運用者に知らせる。
5. 相手からの結果の通知は A-3 で受けて記録に書き戻す。定期の突合のジョブが、`sending` のまま一定の時間を過ぎた記録を拾い、3 の照会を行う。

本デモには決済が無い（入金消込は範囲外、`../architecture/context-map.md`）ので、C-3 は規則として定め、実装しない。

### 7. キューとワーカーを、型ごとに分ける

重い処理が、イベントの配送を待たせないようにする。`config/queue.yml` に、キューごとに別のワーカーを置く。

| キュー | 載せるジョブ | ワーカーのスレッド | 同時実行の上限 |
|---|---|---|---|
| `events` | A-1 `Contracts::EventJob` | 3 | 付けない（`005` 決定 3） |
| `external_mail` | A-2 `CriticalDeliveryJob`・B-1 `BestEffortMailJob` | 2 | 2 つのクラスで合わせて 2（`limits_concurrency key: "sendgrid", group: "sendgrid"`） |
| `imports` | A-4 取り込みのジョブ | 1 | テナントごとに 1 |
| `default` | A-3 inbox の処理・定期のジョブ・その他 | 2 | — |

各ワーカーのプロセスの DB の接続プールは、そのスレッド数より大きくする。

## 結果

### 得られるもの

- **ジョブを読む人は、型を見れば保証が分かる。** ジョブごとに再試行と冪等の取り方を調べ直さなくてよい。A の型どうしは共通の土台を持ち、違いは 4 つの軸と、そこから導かれる観点の表で言える。
- **失ったことに気づけない処理だけが、トランザクションの中で登録される。** `false` の基底クラスが増え続けない。
- **外部への作用の呼び出し元が、通知の種類ごとに 1 か所に保たれる。** 二重送信の経路を足すと CI が落ちる。
- **外部への作用を足すとき、重複の扱いを選ぶ問いが決まっている。** 重複の代償が大きい作用が来ても、C-3 の手順で作れる。
- **重い取り込みが走っていても、イベントの配送とメールは自分のワーカーで進む。**

### 引き受けるコスト

- **A-2 でも、SendGrid の受け付けと記録のコミットの間で落ちると、2 通届く（C-2）。** 提供元が冪等キーを持たない限り、閉じられない。
- **ワーカーの数が増える。** キューごとのワーカーは、1 つの `*` のワーカーより接続とプロセスを多く使う。
- **inbox の表は RLS の外にある。** 処理に使う項目だけを書き（宛先のメールアドレスと、アドレスを含みうる自由記述は残さない）、30 日で消す。

### 撤退コスト

小さい。型は基底クラスとキューの設定の組なので、ある処理の型を変えるのは、継承する基底クラスと `queue_as` を変える作業で済む。高くつくのは、型を決めずにジョブを書き溜めた後で揃え直すことで、ジョブごとに既存の重複と欠落を調べることになる。

### 見直す条件

- **キューを業務 DB と別の DB か Redis に移す。** トランザクションの中で登録する型（A-1・A-2）を、コミットの後の登録と transactional outbox に切り替える（`005`「見直す条件」）。
- **メールの提供元が冪等キーを受け付けるようになる、または提供元を替える。** 決定 6 の C-2 を C-1 に改め、通知キーを冪等キーとして渡して隙間を閉じる。
- **429 が続き、ジョブごとの待ち時間では送信が詰まる。** 提供元の単位で送信を止める仕組み（止める時刻を共有する行）を足す。それまでは、運用者が `external_mail` のキューを止める（`../implementation-plan.md` M31 の手順書 `sendgrid-outage.md`）。
- **取り込みの行が互いに依存する（親の品目と子の行を同じファイルで送る）。** 行ごとに独立に反映する方式をやめ、ファイル全体を 1 つの結果にする（`../implementation-plan.md` M29 の判断）。

## 代替案

### 案 1. すべての非同期処理を、イベントと同じトランザクション内の登録にする

不採用。仕組みは 1 つで済む。しかし B-1 の通知まで、業務のトランザクションの成否と結び付ける理由が無い。`false` の基底クラスは、キューを別の DB に移すときにすべて見直しになるので、少ないほうがよい。

### 案 2. 外部への送信に transactional outbox を置く

不採用。キューが業務 DB と同じ接続にある間は、ジョブの表が outbox を兼ねる。outbox の表と送り出しのプロセスを二重に持つことになる。

### 案 3. Action Mailer の `deliver_later` をそのまま使う

不採用。`ActionMailer::MailDeliveryJob` は `ExternalEffectJob` を継承しないので、登録口の制限と送信記録の外に出る。テンプレートは Action Mailer で書き、送信はジョブの中で `deliver_now` を呼ぶ。

## 未確認の事項

- SendGrid の sandbox mode の成功の応答が、メッセージ ID のヘッダを返すか。文書に記述が無い。実装は、ヘッダが無ければメッセージ ID を空のまま受け付けとして扱う（決定 5 の A-2 の表）。

## 確認した事項

- **Continuations とトランザクション**：activejob 8.1.4 の `ActiveJob::Continuation` は、DB のトランザクションが開いたままの中断点を拒まない。`CheckpointError` は定義されているが、投げる箇所が無い。中断点は、その実行で 2 つ目以降の段階の始まりと、カーソルを進めるたび（`step.advance!`・`step.set!`・`step.checkpoint!`）に置かれる。中断点をトランザクションの外に置くことは、ライブラリの例外に頼れないので、取り込みのジョブのコードの形で守る（決定 5 の A-4）。段階かカーソルを進めた実行の例外は、中断と同じく続きから登録し直す（`resume_errors_after_advancing` の既定は真）。進めていない実行の例外は、失敗したジョブになる。
- **Solid Queue の停止の合図**：solid_queue 1.7.0 のアダプタは `stopping?` を実装し、ワーカーの停止を Continuations に伝える。
- **終えたジョブの保持**：solid_queue 1.7.0 は既定で `preserve_finished_jobs = true`・`clear_finished_jobs_after = 1.day` で、終えたジョブの行はキュー全体で同じ期間だけ残ってから消える。
- **同時実行の上限の共有**：solid_queue 1.7.0 の `limits_concurrency` は `group:` を受け取り、別のクラスのジョブで同じ上限を共有できる。
- **SendGrid の 429 の待ち時間**：文書が示すヘッダは `X-RateLimit-Limit`・`X-RateLimit-Remaining`・`X-RateLimit-Reset` で、`X-RateLimit-Reset` は制限が戻る時刻の UNIX 時刻である。`Retry-After` は文書に無い。
- **SendGrid の署名付きイベント Webhook**：署名は `X-Twilio-Email-Event-Webhook-Signature`、時刻は `X-Twilio-Email-Event-Webhook-Timestamp` のヘッダで届く。署名は「時刻 + 本文の生のバイト列」の SHA-256 に対する ECDSA の ASN.1（DER）を Base64 にしたもので、検証の公開鍵は Base64 の DER である。
- **SendGrid の送信の API の冪等キー**：v3 の送信の API（`POST /v3/mail/send`）の文書に、冪等キーを受け付ける項目もヘッダも無い。決定 6 の C-2 のままにする。
- **SendGrid の sandbox mode の応答**：sandbox mode の要求が検査を通ると、202 ではなく 200 を返す。

> 前の 4 つは、手元の activejob 8.1.4 の `lib/active_job/continuable.rb`・`lib/active_job/continuation.rb`・`lib/active_job/continuation/step.rb` と、手元の solid_queue 1.7.0 の `lib/active_job/queue_adapters/solid_queue_adapter.rb`・`lib/active_job/concurrency_controls.rb`・`lib/solid_queue.rb` で確かめた。SendGrid の 4 つは、SendGrid（Twilio）の文書「Rate Limits」「Signed Event Webhook Technical Specifications」「Mail Send」「Sandbox Mode」と、公式の Ruby のライブラリ sendgrid-ruby の `lib/sendgrid/helpers/eventwebhook/eventwebhook.rb`（2026-10-12 に読んだ main）で確かめた。
