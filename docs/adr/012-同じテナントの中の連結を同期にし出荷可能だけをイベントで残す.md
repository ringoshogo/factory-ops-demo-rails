# 012. 同じテナントの中の受注と出荷・請求を同期の呼び出しでつなぎ、「出荷可能」だけをイベントで残す

## ステータス

承認。出荷が受注を読み、呼ぶ（`fulfillment` → `sales`）。受注が請求を呼ぶ（`sales` → `billing`）。出荷依頼の取消済と出荷停止中は、受注の公開 API `Sales::OrderShipping.status_sql` が返す副問い合わせから導出し、出荷指示の作成と計上は `Sales::OrderShipping.lock` で受注の行をロックしてから進み、計上は同じトランザクションで `Sales::OrderShipping.mark_shipped` を呼ぶ。検収完了の受け手は、検収の記録と同じトランザクションで `Billing::BillableItems.confirm` を呼ぶ。出荷停止の表と出荷依頼の取消の時刻、イベントの「出荷停止」「出荷停止解除」「出荷取消」「請求対象確定」と、「出荷計上」の受注への配送を消した。受注から出荷へは「出荷可能」のイベントだけで渡す。

裏返る条件：出荷依頼の写しを無くし、出荷が受注の行から出荷可能を読む形（代替案 C）に移る（「見直す条件」）。

## コンテキスト

### 決めること

同じテナントの中で、受注と出荷・請求の間に 6 つのイベントの経路があった。受注から出荷への「出荷可能」「出荷停止」「出荷停止解除」「出荷取消」、出荷から受注への「出荷計上」、受注から請求への「請求対象確定」である。`architecture/context-map.md`「コンテキスト間の関係」は、同期を在庫の不変条件と同じテナントの中の写しに、非同期をテナントをまたぐ連結に使うとしており、この 6 つは分け方から外れていた。作者は、出荷が受注を読み、呼ぶ形を選んだ（`../plans/open-items.md` の OI-211）。次の 3 つを決める。

- どちらがどちらを呼ぶか。依存を循環させずに、どのイベントを残すか
- ロックをどの順に取るか
- 出荷依頼の状況と、出荷指示を読む画面を、受注の取消と審査からどう導出するか

### 本デモの事情

- イベントでつなぐと、届く順の入れ替わりに備える仕組みが要った。解除が停止より先に届いたら解除済みの停止を先に作る upsert、出荷取消が出荷可能より先に届いたら失敗させる道と、そのために出荷取消が運ぶ「出荷可能を出したか」、出荷依頼がまだ無い受注のための受注ごとの勧告ロック、検収完了が出荷計上より先に届いたら失敗させる例外である。
- 流用元（`../factory-ops-demo`）は、計上と受注の出荷済みの書き込み、受注の取消と出荷指示の取消を、1 つのトランザクションで行う。
- 依存の向きは、受注が `platform`・`partnerships`・`contracts`・`inventory`・`notifications` に、出荷が `platform`・`partnerships`・`contracts`・`inventory` に、請求が `platform`・`partnerships`・`contracts` に依存していた。受注は出荷に、請求は受注にも出荷にも依存しない。
- 受注の取消は、受注 → 受注明細 → 在庫 → 引当の順にロックを取る。計上は出荷依頼 → 出荷指示 → 在庫 → 引当の順で、受注と出荷は互いの行をロックしなかった。
- 公開 API は値を返し、別のコンテキストの値を SQL へ渡すときは scope を掛けた副問い合わせ（`SqlSubquery`）で渡す（`010` 決定 2）。

## 決定

1. **出荷が受注に、受注が請求に依存し、同期で呼ぶ。** `packs/fulfillment/package.yml` に `packs/sales` を、`packs/sales/package.yml` に `packs/billing` を足す。受注は出荷に、請求は受注にも出荷にも依存しないので、循環しない。循環は `bin/packwerk validate` が落とす。受注の公開 API `Sales::OrderShipping` は 3 つで、どれも `Scope` の自社の受注だけを読み書きする。`status_sql(actor)` は受注ごとの取消済と審査中の副問い合わせ、`lock(actor, id)` は受注の行の `FOR UPDATE` と取消済・審査中、`mark_shipped(actor, id)` は出荷済の時刻が空のときだけの書き込みである。見えない受注には、`lock` が `nil` を、`mark_shipped` が `NOT_FOUND` を返す。請求の公開 API `Billing::BillableItems.confirm` は、操作者のいない入口（検収完了の受け手）から呼ばれるので操作者を取らず、テナントの設定を求め、所有テナントを `Current` のテナントで書き、出荷実績 ID と受注明細 ID の組の一意索引に冪等を任せる。
2. **「出荷可能」だけはイベントで残す。** 受注が出荷を呼んで出荷依頼を作ると、受注が出荷に依存し、決定 1 と循環する。遅れて届いても害が無い。出荷依頼の状況は受注から導出するので、受注を取り消した後に届いた「出荷可能」が出荷依頼を作っても、状況は取消済になる。
3. **出荷依頼の取消済と出荷停止中を、受注の副問い合わせから導出する。** 優先順（取消済 → 出荷済 → 出荷停止中 → 出荷指示済 → 出荷可能）と GraphQL の値は変えない。出荷依頼が見えない受注を指すときは、副問い合わせに行が無いので、取消済でも出荷停止中でもない側に倒れる。受注は出荷に依存しないので、受注の取消は出荷指示を書き換えず、出荷指示の行は `active` のまま残す。有効な出荷指示を読む 2 か所（出荷指示の読み込みと出荷予定日の並べ替え）は、取消済の受注の出荷依頼の指示を除く。
4. **ロックは、受注 → 出荷依頼 → 出荷指示 → 在庫（`item_id` 昇順）→ 引当の順に取る。** 出荷指示の作成と計上は、出荷依頼をロックせずに引いて受注 ID を読み、受注をロックしてから出荷依頼をロックして読み直す。受注の取消は受注 → 受注明細 → 在庫 → 引当のまま変わらない。どちらも受注を最初に取るので、取消・審査の作成と決着・出荷指示の作成・計上が受注の行ロックで直列になる。受注の行の無い出荷依頼は、受注の出荷済を書けないまま出荷実績ができるので、出荷指示の作成も計上も何も書かずに `NOT_FOUND` にする。

## 結果

### 得られるもの

- **届く順の入れ替わりに備える仕組みが消える。** 停止の表、先回りの upsert、出荷取消の先着の失敗と「出荷可能を出したか」の項目、受注ごとの勧告ロック、検収完了の先着の例外が要らない。
- **受注側の操作の直後から、出荷依頼の状況と操作に効く。** 取消・審査の作成と決着・計上の結果が、イベントの配送を待たずに出荷と受注の両方に見える。
- **ロックの順が 1 本になる。** 受注の取消と出荷の計上がどちらも受注を最初に取るので、どこで直列になるかを 1 つの順で説明できる。在庫と引当の行ロックは、受注の行ロックの後ろの二重の守りとして残る。

### 引き受けるコスト

- **出荷の状況の式と出荷指示を読む箇所が、受注の副問い合わせを結ぶ。** 式は操作者を受け取る形になり、式を呼ぶ箇所すべてに操作者を渡す。出荷依頼の状況の spec は受注と審査の行を作る。
- **計上と出荷指示の作成が、受注の行ロックを待つ。** 同じ受注の取消・審査の作成と決着と並ぶと、後の操作は先のコミットまで待つ。
- **出荷の factory は受注の行を作る。** 出荷依頼は受注の行が無いと計上も出荷指示の作成もできないので、出荷の spec と入口の行列の世界は、出荷依頼の数だけ受注の行を作る。
- **消したイベントの型のジョブは、配置の時点でキューに残ると失敗し続ける。** 公開の配置は毎日 DB ごと作り直し（`009`）、手元は `db:reset` で消えるので、互換は持たない。
- **「出荷計上」は受注 ID と受注明細 ID を運び続ける。** 読む受け手はいないが、消すと、消す前に登録したジョブのペイロードを `from_payload` が読めなくなる。

### 撤退コスト

- 決定 1・3 は大。消したイベントの型と受け手と配送表の行、出荷停止の表と出荷依頼の取消の時刻、届く順の入れ替わりに備える仕組みを戻し、依存の 2 行を消す。
- 決定 4 は中。出荷が受注をロックしない形に戻すと、取消と計上の直列化は在庫と引当の行ロックだけになる。

### 見直す条件

- 出荷依頼の写しを無くし、出荷が受注の行から出荷可能を読む形（代替案 C）に移る → 「出荷可能」のイベントも消える。出荷依頼の受注番号の写しも受注の副問い合わせに替えられる（`011` 代替案 D）。
- 受注から出荷へ、「出荷可能」のほかに同期で渡したい値が出る → 受注が出荷に依存すると循環するので、ルートパッケージで束ねるか（代替案 D）、代替案 C を先に行う。

## 代替案

### A. 受注が出荷を呼ぶ

不採用。受注の取消が出荷の公開 API を呼んで出荷依頼と出荷指示を閉じる形である。出荷計上の受注への分は非同期のまま残り、上流（受注）が下流（出荷）に依存する。取消は在庫より前に出荷依頼をロックするよう順を変えないと、計上（出荷依頼 → 在庫）とデッドロックする。

### B. 出荷が受注の行を出荷依頼より後にロックする

不採用。順は出荷依頼 → 出荷指示 → 受注 → 在庫 → 引当になる。受注は出荷の行をロックしないので循環はしないが、計上は受注を待つ間も出荷依頼と出荷指示のロックを持ち続け、取消済と審査中の確かめが出荷のロックの後になる。順が受注の取消（受注が先頭）と食い違い、2 本の順を文書で説明し続けることになる。

### C. 出荷依頼の写しを無くし、出荷が受注の行から出荷可能を読む

不採用。「出荷可能」のイベントも消え、受注と出荷のイベントが無くなる。しかし、出荷依頼の表と明細を読むすべての公開 API・GraphQL の型・E2E の世界を受注の行に結び替えるので、作業が大きい。ロックの順の問題は決定 4 と同じで、デッドロックの対策にもならない。

### D. ルートパッケージで束ねる

不採用。GraphQL の mutation が受注と出荷の公開 API を両方呼んで、受注の取消と出荷依頼の取消を同じトランザクションで行う形である。`architecture/context-map.md`「疎結合を守る規則」5 の、GraphQL 層がコンテキスト同士の依存を代わりに作らない規則に反する。「出荷停止」は `Sales::PurchasingEventReceiver`（操作者のいない入口）の中から出るので、mutation では束ねられない。

### E. `Contracts.publish` が、同じテナントの受け手をすぐに呼ぶ

不採用。イベントの型と受け手を残したまま、宛先が発行元と同じテナントなら、ジョブにせずに同じトランザクションで受け手を呼ぶ形である。受注の取消は受注 → 在庫 → 引当の後に出荷の受け手で出荷依頼をロックし、計上は出荷依頼 → 在庫 → 引当の後に受注の受け手で受注をロックするので、2 つが逆の順でロックを取り、デッドロックする。

## 確認した事項

> `spec/concurrency/cancel_vs_ship_spec.rb` で、後の操作が待つ先が受注の行であることを、待つ側の `pg_locks` の `locktype = 'tuple'` の行の表で確かめた。`Instructions.create` と `Shipping.post` から受注のロックを外すと、`packs/fulfillment/spec/concurrency/fulfillment/shipping_lock_spec.rb` の審査の作成が先の example が落ちた。
