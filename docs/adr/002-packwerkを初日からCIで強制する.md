# 002. packwerk を初日から CI で強制し、`packs/` 構成で始める

## ステータス

承認。

## コンテキスト

### 既定の判断

設計の決定事項（`../architecture/decisions.md` 1 章）は、境界を 3 段階で固めることを既定にしている。

1. 初日は Rails 標準の `app/` に名前空間を切り、依存の向きは文書で決める。
2. 6 か月後に packwerk で実際の依存と照合する。
3. 2 チーム目ができたら `packs/` へ移し、CI で強制する。

この既定の前提は、次の 2 つである。
- 立ち上げ直後は境界が仮説にすぎず、早く強制すると切り直しのたびに設定とディレクトリを動かすことになる。
- 新しく加わった人が、Rails ガイドどおりの場所でコードを探せることが、担当者の入れ替わりに効く。

### 本デモの事情

本デモは、境界が機械的に守られていることを見せることを目的とするポートフォリオである。既定の前提は、次のとおり本デモには当てはまらない。

- **境界は仮説ではなく、設計の成果物として先に示す。** コンテキストマップ（`../architecture/context-map.md`）で、6 つのコンテキストと許可する依存の向きを先に定めている。
- **境界を守る仕組みが、見せたい対象そのものである。** 文書だけで守ると、「境界が守られている」ことを読み手が確かめる手段が無い。
- **切り直しのコストが小さい。** コードベースが小さく、開発者は 1 人なので、境界を切り直しても影響範囲は限られる。

### 強制を始めると決まること

強制を初日から始めると、ディレクトリ構成も初日に決まる。

- **公開 API は `packs/` 構成でないと置けない。** 公開 API を置くには、パッケージごとに `app/public/` を持つ構成が要る。Rails の自動読み込み（Zeitwerk）は `app/` 直下の各ディレクトリを名前空間の起点として扱う。そのため、`app/inventory/public/allocation.rb` は `Inventory::Allocation` にならない。
- **packs-rails で自動読み込みを通す。** `packs/<パッケージ>/app/` の構成にし、packs-rails（`packs/*/app/*` を自動読み込みの対象に加える gem）を使う。

### プライバシーチェックの扱い

公開 API 以外への参照を禁止する検査（プライバシーチェック）は、packwerk 本体から外れている。現在は packwerk-extensions（https://github.com/rubyatscale/packwerk-extensions ）が提供する。

Shopify は、このチェックを packwerk 本体から外した経緯を振り返りに書いている（https://railsatscale.com/2024-01-26-a-packwerk-retrospective/ ）。理由は 2 つある。
- Rails の規約に無い `app/public` を強いたこと
- 依存を管理するツールが、API を設計するツールに変質したこと

## 決定

1. 初日から `packs/` 構成で始める。対象は、6 つのコンテキスト（`partnerships`・`purchasing`・`sales`・`inventory`・`fulfillment`・`billing`）と `contracts` である。GraphQL などコンテキストに属さないコードは、ルートパッケージに置く。ただし Rails の基底クラスとテナントの仕組みは `packs/platform` に置く。各パッケージが参照する基底クラスをルートパッケージに置くと、パッケージからルートへの依存が循環になる。
2. 各パッケージは `enforce_dependencies: strict` にする。許可する依存は、コンテキストマップの「許可する依存の向き」の表に限る。
3. packwerk-extensions のプライバシーチェックを有効にし、各パッケージの公開 API を `app/public/` に限る。
4. 公開 API に置くのは、他パッケージから呼ばれるサービスと読み取り用の型だけにする。AR モデルは公開しない。他パッケージは、公開 API が返す値を通してだけデータに触れる。
5. CI で `packwerk check` を実行し、違反があれば落とす。`package_todo.yml`（既存違反の一時的な許容リスト）は作らない。違反は許容せず、その場で直す。

## 結果

### 得られるもの

- **境界が守られていることを、読み手が確かめられる。** 読み手は、`package.yml` と CI の結果から、コンテキストマップの依存の向きがコードで守られていることを確認できる。
- **購買と受注の非依存を、CI が保証する。** 購買と受注が直接依存しないことは、規約ではなく CI で保証される。
- **公開 API の一覧が、コンテキストの約束になる。** 公開 API が `app/public/` に集まるので、その一覧がそのままコンテキスト間の約束の一覧になる。

### 引き受けるコスト

- **新しく加わった人は、Rails ガイドどおりの場所でコードを探せない。** `packs/` 構成の読み方を README で案内する。
- **プライバシーチェックで、Shopify が書いた問題を引き受ける。** 公開 API の形を考える作業が、パッケージを作るたびに発生する。
- **境界を切り直すと、`git mv`・`package.yml`・公開 API の移動が要る。** この作業は、文書だけで守る場合より重い。

### 見直す条件

- **境界の切り直しが繰り返される場合。** 同じ境界の切り直しが 2 回以上起きたら、そのパッケージだけ強制を外し、境界が安定するまで文書で守る。
- **プライバシーチェックの違反を避けるためだけの公開 API が増えた場合。** 公開 API が業務の約束ではなく、抜け道として増えていくなら、プライバシーチェックを外して依存チェックだけを残す。

## 代替案

### A. 既定どおり、初日は文書だけで守る

不採用。境界が守られていることを示す手段が無く、デモの目的を満たさない。

### B. `packs/` 構成にし、依存チェックだけを強制する（プライバシーチェックなし）

不採用。依存の向きは守れるが、許可された依存先のどのクラスでも参照できてしまう。たとえば受注が在庫の AR モデルを直接書き換えられ、在庫の不変条件を守る公開 API を迂回できる。これを止めることが本デモの見せどころの 1 つである。

### C. `app/` 構成のまま、名前空間ごとに packwerk のパッケージを宣言する

不採用。依存チェックはできるが、公開 API の置き場（`app/public/`）を Rails の自動読み込みと両立させられない。

## 確認した事項

- packs-rails は Rails 8.1 で動く。`packs/*/app/*` を自動読み込みと eager load の対象に加え、`.rspec` の `--require packs/rails/rspec` で `packs/*/spec` のテストも走らせる。
- 依存チェックとプライバシーチェックが違反を実際に落とすことは、`spec/packwerk/enforcement_spec.rb` が一時ファイルで違反を作って確かめる。

> packs-rails 0.1.0・packwerk 3.3.1・packwerk-extensions 0.4.0・Rails 8.1.4 で、`bin/rails runner 'Rails.autoloaders.main.eager_load'` が `packs/platform` の基底クラスを読み込むことを確かめた。
