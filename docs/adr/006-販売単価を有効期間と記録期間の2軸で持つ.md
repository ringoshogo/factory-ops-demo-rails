# 006. 販売単価を、有効期間と記録期間の 2 つの時間軸で持つ

## ステータス

承認。販売単価の履歴（`../implementation-plan.md` M27）で実装し、`items.unit_price` を消した。既存の単価は、rake タスク `sales:backfill_item_prices` が有効期間 `(,)` の行に写す。

## コンテキスト

### 決めること

受注側の品目の販売単価を、どの形で履歴として持つかを決める。

### 本デモの事情

販売単価には、2 種類の「いつ」が関わる。

- **有効期間**（valid time）：その単価が業務で効いている期間。受注側の担当者は「11 月 1 日から 1,200 円」のように、改定を前もって登録する。
- **記録期間**（transaction time）：その単価が正しいとシステムが信じていた期間。担当者が入力の誤りを後から訂正すると、訂正の前と後で「10 月の単価」の答えが変わる。

受注は、受注日に有効な単価を写して持つ（`../architecture/data-model.md`「テナントの持ち方」の金額と数量）。写した後に単価が訂正されると、請求書の単価といまのマスタの単価が食い違う。取引先から「この請求書の単価はどこから来たのか」と問われた担当者は、次の 2 つを区別して答える必要がある。

- 請求書を発行した時点で、システムは受注日の単価をいくらだと信じていたか
- いま分かっている受注日の単価はいくらか

単価を上書きする 1 列では、どちらにも答えられない。有効期間だけの履歴では、改定の予約はできる。しかし訂正が過去の行を書き換えるので、1 つ目の問いに答えられない。

## 決定

1. **単価は `item_prices`（`packs/sales`）に、品目ごとの行の集まりとして持つ。** `items.unit_price` は、値を移した後に消す。
   - `valid_period daterange`：有効期間。日単位で、下限を含み上限を含まない。上限なしは「次の改定まで」を表す。
   - `recorded_period tstzrange`：記録期間。行を書いた操作の記録の時刻（決定 3）から始まる。上限なしは「いまも正しいと信じている」を表す。
   - ほかに `unit_price`（0 以上）・`reason`（訂正では必須）・`recorded_by_user_id` を持つ。
   - テナントの表なので、`create_tenant_table` で作り、品目へは `add_tenant_reference` の複合外部キーでつなぐ。
2. **記録期間が終わっていない行（現在の行）同士は、同じ品目で有効期間が重ならない。** これを DB の排他制約で守る。記録期間は始まりを含み終わりを含まない形に CHECK 制約で限り、閉じた行の終わりと、同じ時刻に足した行の始まりを重ねない。

   ```sql
   CREATE EXTENSION IF NOT EXISTS btree_gist;
   ALTER TABLE item_prices ADD CONSTRAINT item_prices_current_no_overlap
     EXCLUDE USING gist (owner_tenant_id WITH =, item_id WITH =, valid_period WITH &&)
     WHERE (upper_inf(recorded_period));
   ```

   `btree_gist` は、`uuid` の等しさを GiST の索引で扱うために入れる。
3. **行を書き換えない。** 単価の変更は「現在の行の記録期間を閉じる」と「新しい行を足す」の 2 つの操作だけで表す。閉じる操作は、`recorded_period` の上限を記録の時刻にすることである。トリガーが、それ以外の UPDATE と、すべての DELETE を拒む。記録の時刻は、操作が品目の行をロックした後に、アプリが 1 回だけ取る（`Time.current`）。閉じる行と足す行に同じ値を使うので、閉じた行の終わりと足した行の始まりは隙間なく接する。DB の `now()` はトランザクションの始まりの時刻なので使わない。ロックを待った操作が、先にコミットした操作の行を、その行の始まりより前の時刻で閉じようとして失敗するからである。請求書の発行時刻もアプリの時刻なので、決定 5 の請求書の説明は同じ時計で比べられる。アプリの時計が、閉じる行の記録の始まりより前に戻っていると、操作は例外で失敗し、何も書かない。
   - **改定の予約**（`Sales::ItemPrices.schedule`）：改定日を含む現在の行を閉じ、2 行を足す。1 行は元の行の始まりから改定日の前日までの元の単価、もう 1 行は改定日から元の行の終わりまでの新しい単価である。
   - **訂正**（`Sales::ItemPrices.correct`）：対象の現在の行を閉じ、同じ有効期間で正しい単価の行を足す。
   - どちらの操作も、品目の行をロックしてから行う。同じ品目への改定と訂正を直列にするためである。
4. **単価の問い合わせは、有効日と記録時点の 2 つを引数に取る 1 つの公開 API に集める。** `Sales::ItemPrices.price_at(actor, item_ids, valid_on:, as_of: nil)` は、`valid_period @> valid_on AND recorded_period @> as_of` で引く。`as_of` を省けば、記録期間の終わっていない行で引き、いま信じている単価を返す。パッケージの中では、現在の行を `ItemPrice.current` の scope で引く。
5. **単価を使う場所ごとに、有効日と記録時点を次のように決める。**

   | 使う場所 | 有効日 | 記録時点 |
   |---|---|---|
   | カタログ（`Item.unitPrice`・`PublishedCatalogItem.unitPrice`） | 今日 | いま |
   | 受注の作成（ACL が受注明細に写す） | 受注日 | いま |
   | 請求書の説明（`BillableItem.priceExplanation`） | 受注明細が単価を写したときの有効日 | 請求書の発行時刻と、いま |

   受注明細は、写した単価に加えて、そのときの有効日 `priced_on` を持つ。請求対象明細は受注明細 ID を持つので、ルートパッケージが受注の公開 API で説明を引ける。
6. **有効日は、受注日と同じ日付にする。** カタログの今日は、ACL が受注日に使う `Date.current` と同じ値を、アプリが引数で渡す。カタログで見た単価と、同じ時点に登録した発注の受注明細の単価が食い違わないようにするためである。SQL の `current_date` は使わない。セッションのタイムゾーンで値が変わるからである。
7. **テナントの境界は、他の表と同じ規則に従う。** 発注側に見せるのは、経路 1 のカタログでの今日の単価だけである。改定の予定と訂正の履歴は見せない。RLS は、子の表の形（`../architecture/data-model.md`「RLS」）で `item_prices` に経路 1 の読み取りを足し、現在の行に限る。今日の行に絞る判定は、発注側のカタログの公開 API `Sales::PublishedCatalog` が受け持つ（RLS は粗い判定にとどめる。`../architecture/decisions.md` 2 章）。

## 結果

### 得られるもの

- **改定を前もって登録できる。** 改定日に誰も操作しなくても、カタログと新しい受注の単価が切り替わる。
- **発行済みの請求書の単価を説明できる。** 「発行の時点で信じていた単価」と「いま分かっている単価」の両方を示せる。訂正が請求書の発行の後に入ったかどうかは、記録期間で分かる。
- **単価の変更が、そのまま記録として残る。** 過去の行が変わらないので、誰がいつ何を正しいと信じていたかを、表だけで辿れる。

### 引き受けるコスト

- **1 回の変更で、閉じる更新 1 件と追加 1〜2 件が起きる。** 品目と単価を一括で取り込むときも、既存の品目の単価が変わる行は、行ごとにこの操作を通す。新しい品目は最初の行を足すだけで、単価の変わらない行は何も書かない。
- **単価を引くたびに、範囲の条件が要る。** `price_at` と `ItemPrice.current` を通らずに `item_prices` を引くと、記録期間の条件を書き忘れて過去の行を拾う。パッケージの外からの参照は、packwerk のプライバシーチェックが止める。
- **拡張 `btree_gist` を入れる。** 信頼された拡張なので、スーパーユーザーでない所有ロールで入れられる。`structure.sql` に `CREATE EXTENSION` が載る。

### 撤退コスト

小さい。現在の行のうち今日の単価を `items.unit_price` に戻せば、1 列の形に戻る。逆向きは高い。1 列の形のまま訂正を重ねた後では、過去の値が残っていないので、履歴を取り戻せない。

### 見直す条件

- **取引先ごとの単価（得意先別単価）や数量割引が要件になる。** 排他制約のキーに取引先を足すか、単価を決める業務を別のコンテキスト（価格）へ切り出す。
- **訂正に承認の手順が要る。** 記録期間とは別に、申請と承認の状態を持つ行を足す。記録期間は、承認された時点から始める。
- **期間付きの一意制約（`UNIQUE (..., p WITHOUT OVERLAPS)`）が部分条件を受け付けるようになる。** 排他制約から置き換える。

## 代替案

### A. `items.unit_price` を上書きし、変更を監査ログに残す

不採用。実装はいちばん小さい。しかし改定を予約できず、改定日に担当者が手で書き換えることになる。「請求書の発行時に信じていた単価」は、監査ログを時刻順に読み解かないと答えられない。

### B. 有効期間だけの履歴表

不採用。改定の予約はできる。しかし訂正が過去の行を書き換えるので、訂正の前に発行した請求書の説明ができない。

### C. 現在の表と履歴の表に分ける

不採用。現在の表には PostgreSQL 18 の `UNIQUE (item_id, valid_period WITHOUT OVERLAPS)` が使え、部分条件の付いた排他制約が要らない。しかし、訂正のたびに行を履歴の表へ移す処理が要る。「ある時点で信じていた単価」の問い合わせも、2 つの表の和になる。

### D. 単価の変更をイベントとして積み、単価を毎回組み立てる

不採用。履歴は完全に残る。しかし、カタログと受注のたびに組み立てが要り、組み立ての結果を別の表に持つなら、決定 1 の表を二重に持つことになる。本デモで単価を変える操作は 2 つ（予約と訂正）だけで、イベントの積み上げに見合う種類が無い。

## 確認した事項

- **排他制約と予約の操作**：現在の行と有効期間が重なる行の追加は、排他制約が拒む。現在の行を閉じてから 2 行を足す予約は、同じトランザクションで通る。予約の後、改定日より後の有効日を、いまの記録時点で引くと新しい単価が、予約より前の記録時点で引くと元の単価が返る。
- **拡張を入れるロール**：所有ロール `factory_owner`（`CREATEDB`・`BYPASSRLS`、スーパーユーザーでない）が `CREATE EXTENSION btree_gist` を実行できる。
- **期間付きの一意制約**：PostgreSQL 18 は `UNIQUE (k, p WITHOUT OVERLAPS)` を作れる。制約にも一意索引にも、`WHERE` の部分条件を付けられない。そのため、現在の行に限る判定には排他制約を使う。

> PostgreSQL 18.6（compose の `postgres:18`）に一時 DB を作り、所有ロールで確かめた。
