# Rails で 0 から作るときの設計判断：既定の推奨と、それが裏返る条件

Rails で B2B SaaS を新規に立ち上げる CTO が、最初の 1 か月で何をどの順に決め、何を後回しにするかを示す。各判断について「既定の推奨」「推奨が裏返る条件」「誤ったときの撤退コスト」の 3 点を書く。

前提とするプロダクトは次のとおり。
- 数年単位で保守され、担当者が入れ替わる。エンジニアは 5〜20 人規模へ育つ
- マルチテナントで、2 つの型を両方扱う
  - **完全分離型**：テナント同士のデータが互いに見えない
  - **相互アクセス型**：取引関係にあるテナント同士が、相手のデータの一部を参照・操作する

この前提を外すと推奨も変わる。

本書は 3 者の討論（Rails Way 派・構造化派・Codex）の結論を統合したものである。

## 全体の方針：Rails の構造を使い切り、事故になる 4 か所だけを機械で守る

Rails の生産性の源は Active Record・規約・ジェネレータにある。これは捨てない。人が入れ替わると壊れる箇所のうち、壊れたときに事故になるものだけを、テスト・Cop（RuboCop のカスタムルール）・基底クラスで機械的に守る。対象は次の 4 つである。

1. **認可とテナントの入口**：誰がどのデータに届くか
2. **トランザクションと副作用の順序**：コミット前に外部へ作用しないこと
3. **ジョブの投入経路**：ロールバックした操作のジョブが走らないこと、確定した操作のジョブを失わないこと、冪等であること
4. **コンテキスト間の依存方向**：どのコードがどこを参照してよいか

これ以外は Rails の規約に従う。リポジトリ層で Active Record を包む、ドメインエンティティと AR モデルを二重に持つ、DI コンテナを入れる、層ごとに DTO を詰め替える、の 4 つは採らない。どれも Active Record の関連・scope・バリデーションという Rails の資産を自ら手放し、コード量を増やすからである。

## 最初の 1 か月で決めることと、後回しにすること

CTO が決める順に並べる。前の判断が後の判断の前提になる。

| 順 | 決めること | 決める内容 | 詳細 |
|---|---|---|---|
| 1 | DB 製品 | PostgreSQL か MySQL か。テナント漏洩の防壁の枚数がここで決まる | 8 章・2 章 |
| 2 | テナントの持ち方 | テナント ID 列の名前、全テナントデータのテーブルに付けること、`Current` に設定する場所、未設定なら例外にすること、ジョブ・ログへの伝播 | 2 章 |
| 3 | 相互アクセスの関係モデル | 取引関係を表すモデルの名前と、共有データの「所有テナント」の原則 | 2 章 |
| 4 | 認可の基底クラス | 基底コントローラ・基底リゾルバ・基底型・基底 mutation を、未宣言なら拒否する作りにする | 2 章・7 章 |
| 5 | コンテキストと用語 | コンテキスト 3〜6 個の名前、業務用語集、コンテキスト間の依存方向（文書）、6 か月後の境界レビューの予定 | 1 章・3 章 |
| 6 | トランザクションの規約 | 3 規約と、手続きクラスを作る条件 | 4 章 |
| 7 | ジョブの規約 | Active Job 経由に限ること、キューの置き場所と投入の時機（コミット後か、同じトランザクションか）の明示設定、冪等キー、外部副作用ジョブの呼び出し元制限 | 5 章 |
| 8 | 画面方式 | Hotwire か SPA + API か | 6 章 |
| 9 | デプロイ先 | 運用人員に合わせて選ぶ | 8 章 |

後回しにしてよいもの：
- packwerk の strict 化、`packs/` ディレクトリ、Rails Engine、マイクロサービス
- Sorbet / RBS
- transactional outbox（5 章の条件に当たる場合を除く）、ドメインイベント基盤
- リードレプリカ、シャーディング、テナント単位の DB 分離

これらは、後から入れても撤退コストが小さいか、入れる条件が観測できるまで判断材料が無いかのどちらかである。

## 1. 疎結合：単一アプリで始め、境界は文書 → 照合 → 強制の順に固める

**既定の推奨**：単一の Rails アプリで始め、境界は 3 段階で固める。

- **初日**：Rails 標準の `app/` 構造を保ち、コンテキストごとに名前空間（`Billing::`・`Reservations::`）を切る。コンテキスト間の依存方向（例：`billing → core` は可、逆は不可）を文書に書く。packwerk は入れない。
- **6 か月後**：CTO が境界レビューを行う。この予定は初日にカレンダーへ入れておく。packwerk を一時的に走らせて違反一覧を出し、文書の依存方向と実際の依存を照合する。境界が残ったコンテキストには packwerk を記録モードで入れる。packwerk のパッケージは、名前空間ディレクトリ（`app/models/billing/` など）単位でも宣言できる。
- **2 チーム目ができたとき**：コンテキストを `packs/` へ移し、パッケージ単位で CODEOWNERS を切り、packwerk の依存違反で CI を落とす。

packwerk のプライバシーチェック（公開 API 以外の参照禁止）は使わない。Rails の規約に無いディレクトリを強いるうえ、依存管理のツールが API 設計のツールに変質するからである。

マイクロサービスへの切り出しは、次のどれかが**実測で**確認されたときに、その部分だけ行う。チームの分かれ方ではなく、障害とスケールの独立性で判断する。
- 独立したスケーリング要件がある
- 可用性やコンプライアンスの要件が異なる
- 別の言語ランタイムが必要になる

**裏返る条件**
- エンジニア 3 人以下で、1〜2 年以内に作り直す前提なら、境界の文書化も省いてよい
- ドメインが探索段階で、コンテキストの切り方が週単位で変わるなら、6 か月後のレビューを後ろへずらす
- 契約や監査で境界が最初から強く求められる場合、または相互アクセス型の権限境界がコンテキスト境界と重なる場合は、名前空間と policy scope を初月から切る

**撤退コスト**：小さい。packwerk は設定ファイルを消せば外れ、`packs/` から名前空間ディレクトリへの移動は `git mv` と autoload 設定の変更で済む。逆向きも同じである。高くつくのは、境界の無いまま 3 年育ててから packwerk を入れる場合で、違反 TODO が数千件の負債として残る。

> Shopify は packwerk の振り返りで、プライバシーチェックを v3.0 で削除したこと、名前で切ったドメイン境界は実際のコードの動きを反映しなかったことを書いている（https://railsatscale.com/2024-01-26-a-packwerk-retrospective/ ）。

## 2. マルチテナント：テナントの持ち方と、相互アクセスの関係モデルを初日に決める

### 完全分離型

**既定の推奨**：1 つの DB で行レベル分離を採る。テナントの持たせ方は次のとおり。
- テナントのデータを持つテーブルには、最初から全テーブルにテナント ID 列を持たせる
- リクエストごとのテナントは `Current` に設定する
- テナントが未設定のままテナント表を引いたら、例外にする（fail-closed）

漏洩の防壁は DB 製品で枚数が変わる。

| 手段 | 種別 | 効く範囲 | 抜け道 |
|---|---|---|---|
| テナント経由の関連からだけ引く書き方（`Current.account.projects.find(id)`）と、テナント未設定時に例外を出す既定スコープ | 防止 | ORM 経由のクエリ | `unscoped`・生 SQL・コンソール |
| PostgreSQL RLS（行レベルセキュリティ。DB が行ごとに参照・更新を制限する機能。`ENABLE` と `FORCE` を指定し、テナントはトランザクション内の `SET LOCAL` で渡し、`WITH CHECK` を付ける） | 防止 | ORM・生 SQL・コンソールの全経路 | RLS を迂回できる権限を持つロール |
| SQL 発行の監視（`sql.active_record` を購読し、テスト・ステージングでテナント条件の無いクエリを例外にする） | 検出 | テストとステージングで実行された経路 | 実行されなかった経路 |
| テナント表の静的列挙（全 AR モデルについて、テナント列を持つか理由付きの除外宣言があるかをテストで確かめる） | 検出 | テナント列の付け忘れ | クエリ条件の誤り |
| 本番コンソールを読み取り専用レプリカに限り、操作を監査する | 防止（運用） | 人手のクエリ | 手順違反 |

- **PostgreSQL**：防止 2 枚（アプリ層と RLS）に検出を足す
- **MySQL**：RLS が無く、ビューでも代替できないため、防止 1 枚と検出の組み合わせになる

既定スコープ（`default_scope`）は完全分離型のテーブルだけに付け、相互アクセス型のテーブルには付けない。付けると、相手テナントの行を読むたびに `unscoped` が要り、防壁の穴が日常になる。

テナント文脈は、ジョブ投入時に自動でシリアライズし、実行時に自動で復元する。この処理は `ApplicationJob` の 1 か所に書く。ログとエラー通知にもテナント ID を自動で付ける。伝播の漏れは、テナント条件の書き忘れと同じ漏洩経路になる。全テナントを横断するバッチは `Current` を使わず、テナントを明示的に回すループで書く。

**裏返る条件**
- 顧客契約や監査で、物理分離・顧客単位の削除やバックアップを求められる → その顧客だけ DB 分離（Rails の multi-DB / horizontal sharding）を足す
- 1 テナントの負荷が全体の大半を占める → そのテナントだけ別シャードにする
- 規制や契約で「運用者のクエリミスでも漏れない」ことを求められ、かつ完全分離型テーブルの比重が高い → MySQL を選ぶ理由（既存資産・運用知見）と、防壁が 1 枚減ることを比べて DB 製品を決め直す

**撤退コスト**：全テーブルにテナント ID 列が揃っていれば、行レベルから DB 分離への移行は機械的に切り出せる。逆向き（DB/スキーマ分離から行レベル）は、全テーブルへの列追加と全クエリの書き換えになり高い。RLS は `DISABLE` ですぐ外せる。

> 37signals は Fizzy で顧客ごとに DB を分ける構成を目指し `activerecord-tenanted` を作ったが、グローバル複製とフェイルオーバーの複雑さから共有 DB に切り替えた（https://dev.37signals.com/rails-multi-tenancy/ ）。

### 相互アクセス型

**既定の推奨**：テナント間の取引関係を**第一級のモデル**（`Partnership`、権限付与の `RelationshipGrant` など）として持つ。相手テナントのデータには、必ずこの関係モデルを経由してアクセスする。
- **所有テナント**：共有データは必ず 1 つの所有テナントを持つ。相手テナントから見えるかどうかは、関係モデル経由の権限付与で表す
- **可視範囲**：認可ライブラリの scope（Pundit の `Policy::Scope` / Action Policy の `relation_scope`）の 1 か所に集める
- **scope の付け忘れ**：基底クラスを「未宣言なら拒否」にして、scope を通らないとレコードを取れない入口にする（7 章）。Pundit の `verify_policy_scoped` は付け忘れを検出するだけで、ゲートにはならない
- **監査**：相手テナントに効果が及ぶ書き込みは、必ず監査ログに残す。相手テナントへのイベントを出す操作、相手から見えるデータ（カタログ・取引関係）を変える操作、相手の操作で自社のデータが変わったこと（イベントの受信）がこれに当たる。各テナントが自社の行だけを書く構成では「操作者のテナントとデータの所有テナントが異なる書き込み」が起きないので、所有テナントの食い違いでは対象を決めない。記録は書き込みの入口の基底クラス（mutation の基底クラスとイベントのジョブの基底クラス）の責務にし、個々の操作で `AuditLog.create!` を手書きしない
- **RLS の役割**：PostgreSQL でも RLS は「所有テナントか、関係があるか」の粗い判定にとどめる。閲覧・編集といった操作単位の権限はアプリの policy で判定する

完全分離型と違い、相互アクセス型の正しさは「テナント ID が一致すること」ではない。「2 テナント間に有効な関係があり、その関係が操作を許していること」である。それを表すのが関係モデルである。

**裏返る条件**
- policy scope の OR 条件が 3 本を超えて読めなくなる → 権限を付与レコードとして正規化したテーブル（ACL）へ移す
- 監督者・オブザーバーなど第三者が加わる → 2 者間の関係を n 者間の参加者モデルへ一般化する
- GraphQL を採る場合、同じ型でも「自社として見る」と「取引先として見る」で見せるフィールドが変わる → 視点ごとに型を分けるか、フィールド単位の認可を入れるかを初月に決める

**撤退コスト**：関係モデルを作らずに各テーブルの `host_id` / `supplier_id` の比較で認可を書くと、条件式が policy・GraphQL 型・ジョブに散らばる。関係の種類が増えるたびに全 scope を書き換えることになり、後から関係モデルへ寄せる作業は全クエリの棚卸しになる。

## 3. DDD・クリーンアーキテクチャ：戦略は持ち込み、戦術は選び、層構造は持ち込まない

**既定の推奨**：DDD とクリーンアーキテクチャの要素を、Rails との摩擦で仕分ける。

| 要素 | 判定 | 理由 |
|---|---|---|
| 境界づけられたコンテキスト、コンテキストマップ | 持ち込む | 名前空間・packwerk のパッケージにそのまま対応し、Rails の規約と衝突しない |
| ユビキタス言語（モデル名・メソッド名を業務用語に揃える） | 持ち込む | コストはほぼゼロで、担当者の入れ替わりに効く |
| 値オブジェクト | 持ち込む | `composed_of` や `ActiveModel::Attributes` のカスタム型で書ける |
| 集約 | 考え方だけ持ち込む | 「どの AR モデルを入口に書き換えるか」「どこでロックを取るか」の規約として表す。集約クラスは作らない |
| ドメインイベント | 必要になってから | 5 章 |
| リポジトリ（AR を包む層） | 持ち込まない | AR の関連・scope を失い、コードが倍になる |
| ドメインエンティティと AR モデルの分離 | 持ち込まない | 詰め替えのコストが恒常的にかかる |
| DI コンテナ、依存性逆転の層構造 | 持ち込まない | Ruby はテスト時の差し替えが容易で、interface を必須にする理由が無い |
| ユースケース層の全面導入 | 持ち込まない | 4 章の条件を満たす操作にだけ手続きクラスを作る |

**裏返る条件**
- 計算ロジックが DB と無関係に重い領域（料金計算・配車最適化・在庫引当） → その部分だけ素の Ruby オブジェクト（PORO）のドメインモデルにし、AR は保存の器に徹させる
- 同じドメインロジックを Rails 以外（別言語のサービス・バッチ基盤）からも使う → 同上
- チームの大半が他言語のクリーンアーキテクチャ出身で、Rails の規約を学ぶ時間が取れない → 明示的な層を置いてよい。ただしそれは技術上の理由ではなく、組織の知識分布への措置として記録する。この状況では Rails を選んだこと自体も再検討する

**撤退コスト**：戦略的 DDD は名前とディレクトリの問題なので小さい。全面的な層構造で始めて外す場合は、全機能にリポジトリ・エンティティ・マッパーが残り、剥がすにはほぼ全ファイルの書き換えが要る。Rails の規約で始めて、特定ドメインだけ後から PORO へ抽出するのは局所的な作業で済む。

## 4. ロジックと副作用の置き場所：手続きクラスは条件を満たす操作にだけ作る

**既定の推奨**：ロジックの種類ごとに置き場所を決める。

- **1 レコードで閉じる規則**（バリデーション・状態遷移・導出値）：モデルに置く。モデルが太ったら、関心ごとに concerns へ分ける
- **手続きクラス**（名前は `Usecase` でも名詞でもよい）：次のどちらかに当たる操作にだけ作る。それ以外はコントローラからモデルを直接呼ぶ
  - 2 つ以上のモデルへ書き込む
  - 外部への副作用がある
- **コールバック**：導出値と、モデルの主目的と直交する付随処理にだけ使う。外部への副作用には使わない

トランザクションは、次の 3 規約で扱う。
1. トランザクションと分離レベル（isolation）を指定するのは、最も外側の呼び出し元だけにする
2. 手続きクラス同士は呼び合わない。共有したいロジックはモデルかドメインサービスへ下ろす
3. コミット後の処理は `ActiveRecord.after_all_transactions_commit` で書く

外部への副作用（メール・電話・外部 API・ファイルの外部保存）は、コミット後にジョブで実行する。トランザクション内で実行すると、ロールバックしても外部への作用は戻らない。

**裏返る条件**
- 相互アクセス型の業務（予約・検収など）では、操作の大半が複数モデルに書き込み、「例外」のはずの手続きクラスが多数派になりやすい。CTO は最初の 1 か月で実装した操作のうち、手続きクラスを要した割合を数える。過半なら、既定を手続きクラス側に倒し直す
- 呼び出し元ごとに変わる事前検証の束が 1 つの操作に付く → 呼び出し元ごとの入力検証は手続きクラスか form object に出す。ドメインの不変条件はモデルに残す
- コールバックの連鎖で「保存すると何が起きるか」を誰も説明できなくなった → そのモデルのコールバックを明示的なメソッド呼び出しへ移す

**撤退コスト**：手続きクラスは PORO なので、不要ならコントローラやモデルへ戻すだけで済み安い。コールバックに外部副作用を埋め込んだ後の撤退は高い。どの `save` で何が起きるかを洗い出し、発火条件をテストで固定してから移すことになる。迷ったらコールバックを足さない側に倒す。

## 5. 非同期処理と整合性：ジョブは Active Job 経由・投入の時機を明示・冪等に限る

**既定の推奨**：ジョブ基盤は Active Job と Solid Queue にし、業務 DB と同じ DB・同じ接続に置く。Rails 8 の既定の構成はキュー用の DB を分けるので、同じ DB に置く設定を明示する。同じ接続なら、失うと業務事故になるジョブをトランザクションの中で投入でき、outbox を別に作らずに「データが確定したらジョブも必ず存在する」状態が得られる。

ジョブについて、次の 6 つを初日に決める。

- **投入の時機を、ジョブの基底クラスに真偽値で明示する（必須）**：`ApplicationJob` に `self.enqueue_after_transaction_commit = true` を書く。失うと業務事故になるジョブは、キューが業務 DB と同じ接続にある場合に限り、`false` にした専用の基底クラスから作る（本デモでは `EventJob`。`../adr/005-イベントのジョブをトランザクション内で登録する.md`）
  - `true`：投入をコミットの後に回す。ロールバックした操作のジョブは投入されないが、コミットと投入の間でプロセスが落ちるとジョブを失う
  - `false` で、キューが同じ接続にある：ジョブの行が業務データと同じトランザクションで書かれる。コミット前の行はワーカーから見えないので、確定と投入が一致する
  - `false` で、キューが別のストアにある：コミット前に投入され、ロールバックした操作のジョブが走る。この組み合わせは作らない
  - 既定値は Rails のバージョンで変わり、アプリ全体の設定 `config.active_job.enqueue_after_transaction_commit` は Rails 8.1 で読まれなくなった。基底クラスに書かないと、Rails の更新で投入の時機が黙って切り替わる。`false` の基底クラスを置く場合は、キューの接続が業務 DB と同じであることをテストで確かめる
- **投入経路を Active Job 経由に限る**：`Sidekiq::Client` や `perform_async` による直接投入は、Cop で禁止する。直接投入は投入の時機の設定が効かず、アダプタの差し替えもできなくなる
- **at-least-once 前提で冪等に書く**：ジョブは少なくとも 1 回、場合によっては複数回実行される前提で書く。冪等性は冪等キー列のユニーク制約で DB に担保させ、引数は ID だけにする
- **外部副作用を持つジョブの基底クラスを分ける**：電話・SMS・外部 API・取引先へのデータ送信・メールを行うジョブは、専用の基底クラス（仮に `ExternalEffectJob`）を継承する
  - カスタム Cop で、このジョブを投入できる場所を「手続きクラス」か「モデルの `after_commit` 1 か所」に限る
  - 再送や手動再実行などで 2 本目の呼び出し経路を足すと CI が落ち、手続きクラスへの移設が強制される
  - 発火するだけのアプリ内通知は、`after_commit` からの `deliver_later` / `perform_later` でよい
- **複数 Pod での排他**：Solid Queue の `limits_concurrency` か、DB の行ロック・advisory lock で行う
- **テナント文脈を伝播する**：2 章のとおり `ApplicationJob` で自動化する

transactional outbox（送りたいメッセージを業務データと同じトランザクションで DB の表に書き、別のプロセスが後から送り出す方式）は、次の 2 つを**両方**満たす経路にだけ置く。キューが業務 DB と同じ接続にあるなら、ジョブの表そのものが outbox の役を果たす。
1. ジョブキューが業務 DB と同じ接続に無い（Redis・別 DB）
2. ジョブを失うと業務事故になる（取引先への送信・課金・電話）

outbox が保証するのは「ジョブが必ず投入されること」までである。外部への作用がちょうど 1 回だけ起きることは保証しないので、外部作用の冪等性は別に要る。

**裏返る条件**
- ジョブの流量が業務 DB の書き込み余力を圧迫する、または組織に Redis の運用が既にある → Sidekiq か別 DB の Solid Queue に移る。この時点で同一トランザクションの性質は失われるため、`false` にしていた基底クラスを `true` に戻し、上の 2 条件に当たる経路に outbox を置く
- 外部システムとの厳密な順序保証が要る、または別サービスが同じイベントを購読する → メッセージ基盤・ドメインイベント基盤を検討する

**撤退コスト**：Active Job 経由で書いていれば、Solid Queue と Sidekiq の行き来はアダプタ設定と運用の入れ替えで済む。冪等でないジョブを書き溜めた後の撤退は高い。重複実行の事故が起きるまで気づけないからである。

> Rails 7.2（`load_defaults 7.2`）では設定値が `:default` になり、コミット後に投入するかどうかの判断がアダプタに委ねられる。Sidekiq 7.3.8 のアダプタはここで `true` を返すため、Rails 7.2＋Sidekiq の構成では `perform_later` をトランザクション内で呼んでもコミット後に投入される。Rails 8.0 では `:default` が `false` として扱われ、非推奨の警告が出るだけでコミット前の投入に切り替わる。Rails 8.1 ではクラス属性の既定値 `false` だけが残り、アプリ全体の設定は読まれない。根拠は rails v7.2.2.1 / v8.0.2 / v8.1.0 の `activejob/lib/active_job/enqueue_after_transaction_commit.rb`・`enqueuing.rb`・`railtie.rb` と、sidekiq v7.3.8 の `lib/active_job/queue_adapters/sidekiq_adapter.rb` である。

## 6. API とフロントエンドの境界：クライアント側の状態の重さと、フロントエンド組織の有無で決める

**既定の推奨**：画面方式は、プロダクトの種類（B2B SaaS かどうか）や表の複雑さでは決めない。次の 3 つの軸で決める。

- **クライアント側に重い状態を持つ UI が中心か**：表計算のようなセル編集、ドラッグでの枠操作、オフライン動作などが中心なら SPA が勝つ。表が複雑なだけなら、サーバー描画でも描ける
- **クライアントの数**：同じデータを Web・ネイティブアプリ・取引先システムが異なる形で取りに来るなら、スキーマ駆動の API にする
- **独立したフロントエンド組織がすでにあるか**：あるなら SPA のコストの大半は支払い済みなので、SPA を選ぶのが妥当

どれにも当たらない場合、つまり Web クライアントが 1 つでフロントエンド専任者がいない場合は、Hotwire（Turbo + Stimulus）を既定にする。サーバー描画なら、認可・N+1 対策・テナント制約がコントローラとモデルの 1 か所に集まる。リアルタイム更新は Turbo Streams で配信できるので、SPA を選ぶ理由にはならない。

GraphQL を選ぶ場合は、次の 3 つを初日に入れる。
1. **認可**：基底リゾルバと基底型を、未宣言なら拒否する作りにする（fail-closed）。リスト系フィールドには `scope_items` で scope を掛ける。GraphQL は型をたどって相手テナントのデータへ到達できるため、リゾルバだけで認可すると関連の経路から漏れる
2. **N+1 対策**：`GraphQL::Dataloader` などのバッチロードを全型で使う
3. **クエリの上限**：深さと複雑度の上限を設定する

**裏返る条件**
- Hotwire を選んだ後で、モバイルネイティブや外部 API の提供が要件になる → API を別に作る。その見込みが 1 年以内にあるなら、最初から API を立てる

**撤退コスト**：この論点が最も高い。GraphQL から REST / Hotwire へ戻るには、クライアントのクエリをすべて書き換えることになる。Hotwire から SPA へは画面単位で段階的に移れるが、API 設計を後付けする負担がある。好みではなく、上の 3 つの軸で決める。

## 7. 型・静的解析：「破ると事故になる規約」から順に、機械の置き場を決める

**既定の推奨**：規約ごとに、守る手段を決める。初日に入れるのは、RuboCop（`rubocop-rails-omakase` を起点にする）、速いテスト、下表のカスタム Cop と列挙テストである。

| 規約 | 守る手段 | 導入時期 |
|---|---|---|
| 認可の宣言 | 基底クラスで未宣言なら拒否する（実行時のゲート）。明示的に開放した例外は理由付きで宣言させ、その一覧を列挙テストで保つ | 初日 |
| テナント列の必須 | 全 AR モデルを走査し、テナント列か理由付きの除外宣言があることを確かめる列挙テスト | 初日 |
| ジョブは Active Job 経由、外部副作用ジョブの呼び出し元は 1 か所 | カスタム Cop | 初日 |
| 投入の時機の設定 | `ApplicationJob` と、トランザクションの中で投入する基底クラスの設定。その値と、キューの接続が業務 DB と同じであることを確かめるテスト | 初日 |
| 個社別の差し替え実装が拡張点のメソッドを全部持つこと | 登録された全実装を列挙するテスト。委譲に `method_missing` を使わない | 拡張点を作ったとき |
| コンテキスト間の依存方向 | 文書 → 6 か月後に packwerk で照合 → 2 チーム目で CI | 1 章 |
| 命名・業務用語、集約の線引き、ロック順序 | 人の規律（レビューと設計文書） | — |

実行時のゲートと列挙テストは、防ぐものが違うので両方置く。
- **実行時のゲート**：列挙から漏れた経路にも効く。認可は処理の前に評価されるので、未宣言なら確実に止まる
- **列挙テスト**：何を意図的に開けたかを、CI で一覧として保つ

Sorbet / RBS は既定では入れない。マルチテナントの漏洩や副作用の二重実行は型では防げず、上表の手段で同じ事故を止められるからである。

**裏返る条件**（Sorbet を全ファイル `typed: false` から段階導入する）
- 担当者の入れ替わりで、「このメソッドが何を返すか」の調査が日常的なボトルネックとして実測で目立つ
- エンジニアが 20 人を超える
- チームの多数が他言語の出身で、Ruby の暗黙の規約が共有されない。この場合は、他の条件より早めに点検する

**撤退コスト**：Sorbet・カスタム Cop・列挙テストは、どれも後から入れられ、外すのも安い。最も高くつくのは、規約を README にだけ書いて何も機械化しないことである。人が入れ替わるたびに規約が消える。

## 8. 実行基盤とデータ基盤：PostgreSQL と Solid 系で始め、デプロイ先は運用人員で選ぶ

**既定の推奨**：基盤ごとに次の構成で始める。

- **DB**：PostgreSQL を使う。理由は、RLS・トランザクショナル DDL・advisory lock・部分インデックスが 2 章と 5 章の道具になるから
- **ジョブ・キャッシュ・WebSocket**：Rails 8 の Solid Queue / Solid Cache で Redis を持たずに始める。Solid Cable は Action Cable を使う場合だけ入れる
- **Puma**：スレッド数は 3〜5 を起点にし、計測しながら調整する。DB コネクションプールは、Puma のスレッド数とジョブのワーカー数に合わせて明示する
- **デプロイ先**：運用人員で選ぶ。インフラ専任者がいなければ、既存クラウドのマネージドコンテナ（Cloud Run / ECS）。VM を自分で持つ方針なら Kamal
- **リードレプリカと multi-DB**：必要になってから `connects_to` で足す

**裏返る条件**
- 組織に MySQL の運用知見と監視基盤が既にある、または既存システムとデータを密に共有する → MySQL を選ぶ。その場合、テナント漏洩の防壁は防止 1 枚と検出の組み合わせになる（2 章）
- キャッシュやジョブの負荷が業務 DB を圧迫する → Solid 系を専用 DB へ分け、それでも足りなければ Redis にする。outbox の要否が変わる（5 章）
- 読み取り負荷がプライマリの限界に近づく → リードレプリカを足す。レプリカは非同期で遅れるため、書き込み直後に読み直す経路はプライマリに残す

**撤退コスト**：いちばん高いのは DB 製品の乗り換えで、SQL 方言・ロックの挙動・関数の違いが全面に効く。Solid 系と Redis 系の行き来は、アダプタ設定の変更で済み安い。デプロイ先の変更は、コンテナ化していれば中程度である。

## 個社別カスタマイズ：設定値で吸収し、足りなくなったら名前付きの拡張点にする

B2B SaaS には、必ず「この顧客だけ挙動を変えたい」という要求が来る。CTO は初月に、受け方を次のとおり決めておく。

- **最初の受け方**：テナントの設定カラムかフィーチャーフラグで吸収する
- **拡張点へ移す基準**：コードの分岐が 3 顧客を超えたら、差分を名前付きの「拡張点」として定義し、顧客ごとの実装を Strategy として登録する
- **登録表**：コード内の定数で持つ。テナントへの割り当てだけを DB に持つ
- **漏れの検査**：拡張点ごとに、登録された全実装がメソッドを揃えていることを列挙テストで確かめる（7 章）。委譲に `method_missing` は使わない

**裏返る条件**：顧客別の差分がドメインの大半を占めるなら、それは SaaS ではなく受託開発である。設計ではなく製品戦略の問題として扱う。

**撤退コスト**：拡張点が明示されていれば、不要な実装クラスを消すだけで済む。顧客別の `if` がドメインロジックに散らばった後では、どの顧客がどの挙動かを誰も説明できなくなる。

## CTO が判断すること（討論で決着しなかった点）

- **PostgreSQL で RLS を初日から有効にするか**
  - 構造化派：初日から 2 枚目の防壁にする
  - Rails Way 派：レビューでテナント条件の漏れを止め切れなくなってから足す
  - 判断の軸：完全分離型テーブルの比重と、契約上「運用者のミスでも漏れない」ことを求められるか。テーブル数が少ない初日のほうが、入れるコストは低い
- **「コントローラからモデルを直接呼ぶ」を既定にするか**：4 章の計測（最初の 1 か月で、手続きクラスを要した操作の割合）で決める
- **Sorbet の導入時期**：他言語（Go など）の組織から Rails チームを作る場合、7 章の裏返り条件のうち「他言語出身者が多数」に当たる可能性がある
- **画面方式**：既存の React チームがあるなら SPA が妥当になる（6 章）
