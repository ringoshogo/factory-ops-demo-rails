# サイクル末と改善の探索の手順

取りまとめ役が、サイクルの最後のマイルストーンの実装レビューを通した後に、この文書の手順を上から順に回す。取りまとめ役・実装者・サイクル・証跡・残件・改善の候補・正本・レビュアーの意味と、全体の中での位置は `guides/dev-cycle.md` にある。文書のパスは、`docs/` からの相対で書く。

各段階は、読むもの・すること・証跡に出すもの・終えてよい条件を持つ。終えてよい条件を満たさないまま、次の段階へ進まない。証跡は `plans/cycle-NN/` に置く。

## 流れ

```
開始の確認
  → 1. 振り返り        retrospective.md   計画の精度と、指摘・手戻り・詰まり
  → 2. 知見の収穫      harvest.md         実装で分かったことを正本へ
  → 3. 逸脱検査        conformance.md     成果物と正本の食い違いを裁定する
  → 4. 再発防止        recurrence.md      指摘と食い違いの原因から、仕組みを足す
  → 5. 台帳の棚卸し    inventory.md       残件の読み直しと、改善の探索の起動判定
  → サイクル末の PR
  →（起動したときだけ）改善の探索   improvement.md
```

順序には理由がある。振り返りで挙げた想定外が、収穫と再発防止の入力になる。逸脱検査で実装の誤りと裁定した食い違いが、再発防止の入力になる。再発防止は、収穫で書いた知見と突き合わせて、同じものを 2 度書かない。

## 開始の確認

取りまとめ役は、次をすべて確かめてから振り返りに入る。満たさなければ、満たすまでマイルストーンの実装に戻る。

- サイクルのすべてのマイルストーンに、`implementation-reviews.md` の節がある。作者の判断を待って着手できないマイルストーンは、`guides/dev-cycle.md`「全体の流れ」のとおり次のサイクルへ移してから数え、移したことを振り返りに書く。実装レビューまで終えたが作者を待つ残りがあって `--due` を通せないマイルストーンは、今のサイクルに数え、残りだけを次のサイクルへ移したことを振り返りに書く
- Critical と High の指摘を直し終えている。再発防止は、直し終えた指摘の予防だけを扱う

## 1. 振り返り

**読むもの**：`plan-review.md`、`implementation-reviews.md`、サイクルの commit の履歴、計画の節を直した記録

**すること**：取りまとめ役が、計画が実装にどれだけ合っていたかと、回し方そのものが働いたかを評価する。

1. マイルストーンごとに、次の 5 つを評価する
   - 大きさ：1 回の作業に収まったか。分けるべきだった、まとめてよかったものは無いか
   - 完了条件：機械で確かめられたか。実装の途中で足した条件は無いか
   - 変更の予測：計画が挙げなかった表・設定・ファイルを変えたか
   - 依存と順序：隠れた依存で、順序を入れ替えたり待ったりしなかったか
   - 計画との食い違い：計画の節を直した回数と、その原因が計画にあったか設計文書にあったか
2. 計画から実装へ、逆向きに照合する。設計文書か計画が特定のマイルストーンに割り当てた制約が、そのマイルストーンの完了条件と実装に落ちているか。複数の箇所に当てるべき修正を、一部にだけ当てていないか（修正の前の形を `git grep` で数え、0 件であることを確かめる）
3. レビューの指摘を種類ごとに数える。同じ種類が 2 回以上出たものに印を付ける
4. 回し方の各段階が成果物を出したかを確かめる。観点ごとの判定、違和感の転記、RED の記録、台帳への登録、分岐の網羅率の警告の件数が、証跡か台帳にあるか。無ければ、どの段階のどの成果物が欠けたかを書く。警告の件数とそのうち example を足した件数をサイクルで合計し、同じサイクルの実装レビューの「確かめる example が無い」指摘と並べて、警告が抜けを見つけたかを評価する
5. 想定外だったことを、原因を添えて並べる

改善の提案は、`guides/dev-cycle.md` か本書への変更として書く。クラス名やメソッド名ではなく、「出荷の競合を止める行ロック」のように型で書く。名前は変わるからである。業務の知識はここに書かない（収穫の担当）。

**出すもの**：`retrospective.md`（評価・逆向きの照合・指摘の数・欠けた成果物・想定外・回し方の改善の提案）

**終えてよい条件**：すべてのマイルストーンを評価した。想定外を原因付きで並べた（無ければ「なし」と書いた）。回し方の改善を 1 つ以上提案したか、要らないと書いた。

## 2. 知見の収穫

**読むもの**：サイクルの diff（サイクルの最初のブランチの base から、最後のブランチまで）、振り返りの想定外、正本

**すること**：取りまとめ役が、実装で分かったことのうち正本に無いものを、正本へ書く。マイルストーンの中で設計文書に書き足した分（`implementation-plan.md`「1 つのマイルストーンの進め方」2）は済んでいるので、ここではその漏れを拾う。

1. diff を層ごとに見る：表とマイグレーション、公開 API、policy、GraphQL、ジョブとイベント、テスト、CI と設定、画面（`frontend/`）、配置（`deploy/`）。見せどころ（`showcase.md`）も、サイクルで足した仕組みが載っているかを読む
2. 拾った項目ごとに、業務の文脈（なぜ・いつ・何を）か、実装の手段（どうやって）かを分ける。その記述を消しても、コードだけで同じ意図を正確に見つけ直せるなら、実装の手段なので書かない
3. 残した項目を、`guides/dev-cycle.md`「書く前の振り分け」の 4 つの問いで振り分け、分類を付ける。確信を持てない項目は書かずに次のサイクルへ送る
4. 正本と突き合わせる。すでにあれば書かない。不正確なら直す。無ければ足す
5. 正本の文体と粒度に合わせて書く。業務の流れと規則の文書（`architecture/context-map.md`）には、クラス名・メソッド名・SQL を書かない。作り方の文書には書いてよいが、引数の並びと行番号は書かない

**出すもの**：`harvest.md`（項目ごとの分類・書いた文書と節・内容・根拠の commit、書かなかった項目と理由）と、正本の変更

**終えてよい条件**：diff のすべての層を見た。すべての項目に分類が付いている。分類を決められない項目を作り方の文書に書いていない。書かなかった項目に理由がある。

## 3. 逸脱検査

**読むもの**（レビュアーに渡すもの）：サイクルの diff、正本（収穫で足したものを含む）、サイクルのマイルストーンの節

**すること**：取りまとめ役が、2 系統のレビュアーに、成果物が正本から外れていないかを検査させる。観点は次の 5 つである。

1. 業務の流れと規則（`architecture/context-map.md`）
2. 表とテナントの境界（`architecture/data-model.md`。RLS とテナントの列を含む）
3. API と到達できる範囲（`architecture/graphql-schema.md`）
4. 決定（`adr/`。決定と、裏返る条件に当たっていないか）
5. 規約（`guides/`。コメント・パッケージの境界）

レビュアーは、見つけた食い違いごとに、どちらが正しいかを裁定する。1 つの食い違いが複数に当てはまって見えることがあるので、上から順に当て、最初に当たったものに確定する。

| 順 | 裁定 | 目安 | 行き先 |
|---|---|---|---|
| 1 | 要確認 | 実際の挙動を確かめていない | 正本も実装も変えない。確かめるテストを書く作業を残件に積む |
| 2 | 文書が正 | 業務の規則・完了条件・テナントの境界に反する | 実装を直す。再発防止の入力にする |
| 3 | 作者の判断 | 業務の振る舞いが変わる。範囲の判断が要る。解釈が割れる | 正本も実装も変えず、残件に `blocked-user` で積む |
| 4 | 実装が正 | 上のどれでもなく、実装が文書を根拠のある形で具体化した | 正本を実装に合わせて直す |

「実装が正」は、レビュアーが出した裁定に限る。取りまとめ役は、自分のまとめた実装を正と裁定しない。そうしないと、実装の誤りが正本に書き込まれ、次からは正しい規則として読まれる。

**出すもの**：`conformance.md`（観点ごとの判定、食い違いごとの裁定と行き先）

**終えてよい条件**：5 つの観点すべてに判定がある。すべての食い違いに裁定と行き先がある。「実装が正」の裁定がすべてレビュアーから出ている。

## 4. 再発防止

**読むもの**：実装レビューの指摘（Critical・High・Medium と、振り返りで 2 回以上と数えた Low）、逸脱検査で「文書が正」と裁定した食い違い、振り返りの想定外、`harvest.md`

**すること**：取りまとめ役が、直し終えた指摘と食い違いの原因をたどり、同じ種類が再び起きない仕組みを足す。直すこと（是正）は済んでいる前提で、ここでは予防だけを設計する。指摘や修正が起きたものを扱い、知見が増えただけのものは収穫に任せる。`harvest.md` にすでにある知見は書かない。

1. 指摘ごとに、種類を 1 つに決める。上から順に当て、最初に当たったものに確定する
   1. 範囲の逸脱：計画に無い変更が混ざった
   2. 生成物のずれ：`structure.sql` やスキーマの書き出しが、コードとずれた
   3. 規則の違反：正本に規則があるのに従わなかった
   4. 文書との食い違い：設計文書に書いてあることと実装が違った
   5. 暗黙の知識：規則は無かったが、知っていれば避けられた
2. 指摘ごとに 3 つを問う：なぜ起きたか。なぜ防げなかったか。計画レビュー・実装・実装レビューのどこで捕まえるべきだったか
3. 原因から修正先を選ぶ。機械で判定できるものを最初に考える

   | 原因 | 修正先 | 分類 |
   |---|---|---|
   | 機械で判定できる形の誤り | Cop・spec・基底クラス・DB の制約・`bin/` の検査 | （仕組み） |
   | 規約が曖昧か欠けている | `guides/` か設計文書の該当する節。先に、その行に ADR が添えられていないかを確かめる。添えられていれば欠けではなく決定なので、修正先は ADR になる | 作り方 |
   | 決定の理由が失われ、規則を外してよいか判断できない | ADR を起こす | 決定 |
   | 手順が無いか古い | `guides/dev-cycle.md`・本書・`guides/bin.md` | 手順 |
   | レビューが見逃した | その段階の観点の中に、必ず見る項目を足す。観点の数は 5 のままにする | 手順 |
   | 何を満たすべきかの認識がずれた | `architecture/context-map.md` と完了条件を直接書き換えず、逸脱検査の裁定か作者の判断に回す | 満たすこと |
   | 担当と期限が無かったために流れた | 残件に、引当先を付けて積む | （台帳） |

4. 仕組みにするか文書だけにするかを、次で決める

   | 条件 | すること |
   |---|---|
   | 同じ種類が 2 回以上出た | 機械の検査にする |
   | 1 回だが、影響が大きい（テナントの越境・データの消失・CI の破壊） | 機械の検査にする |
   | 1 回で、影響が小さいか中くらい | 文書だけを直す |
   | 文書を直さなくても防げる | 何も足さない |

**出すもの**：`recurrence.md`（指摘ごとの種類・3 つの問いの答え・修正先と分類・再び起きたらどの段階で捕まるか）と、正本と検査の変更。指摘が 1 件も無ければ「指摘なし」と書いて出す

**終えてよい条件**：すべての指摘に種類と修正先がある。分類を決められないものを作り方の文書に書いていない。すべての修正に、再び起きたら捕まる段階が書いてある。

## 5. 台帳の棚卸し

**読むもの**：`plans/open-items.md`、`plans/improvement-backlog.md`、直近の `improvement.md`

**すること**：取りまとめ役が、台帳を全部読み直す。マイルストーンを終えるときの検査は、登録の漏れと取りこぼしを止めるが、要らなくなった行が残り続けることは止めないので、ここで読み直して見つける。

1. `open` を全部読み、要らなくなったものを理由を添えて `decided` にする
2. 引当先のマイルストーンを終えたのに残っている行を、片付けるか引当先を書き換える
3. `judgment` と `blocked-user` を一覧にし、サイクル末の PR の本文の冒頭に ID と 1 行の要約で並べる。作者は、ここを読んで判断する。作者の答えが要る行には、`guides/dev-cycle.md`「1. 計画レビュー」の形の説明の文書を `plans/cycle-NN/` に置いて添える
4. 改善の候補の台帳を読み、改善の探索を回すかを次で決める

   | 台帳の状態 | 動き |
   |---|---|
   | `未着手` が 3 件以上ある | 改善の探索を「検証」で回す |
   | `未着手` が無く、直近 2 サイクルの証跡に `improvement.md` が無い | 改善の探索を「発見」で回す |
   | `試行中` があり、判定するマイルストーンを終えた | 改善の探索で、試行の効き目を確かめる |
   | どれにも当たらない | 回さない |

5. `bin/check-open-items` を流し、通ることを確かめる

**出すもの**：`inventory.md`（閉じた行、引当先を書き換えた行、作者への一覧、改善の探索の起動判定とその根拠）

**終えてよい条件**：すべての `open` を読んだ。作者への一覧を PR の本文に載せた。起動判定を書いた。

## サイクル末の PR

取りまとめ役は、5 つの段階の証跡と、正本・検査・台帳の変更を 1 本の PR にまとめる。本文の冒頭に作者への一覧を置き、その後に正本への変更を表で並べる（変えた文書と節・内容・どの段階から来たか・根拠）。作者のマージを、正本への変更の承認とする。

## 改善の探索

台帳の棚卸しが起動したときだけ回す。サイクル末の 5 段階は、すでに起きた指摘と食い違いから学ぶ。改善の探索は、指摘されていないが、いまより良いやり方が無いかを探す。対象は設計と実装のやり方（使う gem・言語の機能・構造・書き方の型）に限り、回し方の改善は振り返りに任せる。

**読むもの**：検証なら改善の候補の `未着手` と、振り返りの想定外。発見なら、次の観点でのコードベースと文書

| 観点 | 見るもの |
|---|---|
| 重複 | 同じ形の実装が並んでいないか。早すぎる共通化にならないか |
| 例外の多い規則 | `guides/` と設計文書のうち、例外の書き足しが続いている節。例外が多い規則は、規則そのものが古い |
| 繰り返す指摘 | 証跡に、同じ種類の指摘や失敗が繰り返し出ていないか |
| 依存 | gem・Ruby・PostgreSQL のメジャー更新とサポートの終わり |
| 薄いテスト | 実装の広さに対して、境界の値と失敗の経路のテストが薄い領域 |
| 生成物のずれ | 生成物と手で書いたもののずれ |
| 不要なファイル | 読む人や AI を誤らせる、使われていないファイル |

**すること**：取りまとめ役が候補を調べ、レビュアーが裁定する。

1. モード（検証か発見か）を宣言する。発見では、観点ごとに「見つかった」か「該当なし」を書く
2. 違和感をテーマに直す。「この規則どおりだと読みにくい」は違和感で、「この書き方の型を見直すべきか」がテーマである。テーマごとに、なぜ今か（シグナルの出どころ）を書く。書けないテーマは捨てる
3. すでに `見送り` の行があるテーマは、記録した理由との差分だけを調べる
4. 優先度の高い順に 3〜5 件だけを調べる。いまの形との比較、このリポジトリへの合い方、移す費用、何をもって効いたとするかを明らかにする。扱わなかった件数を必ず書く
5. レビュアーが、テーマごとに `採用`・`監視`・`見送り` を裁定する。迷ったら `監視` ではなく `見送り` にする。`監視` を多用すると、台帳が判断の先送りの置き場になる。取りまとめ役は、裁定の前に、再発防止の証跡・計画・`guides/dev-cycle.md` に採用を前提にした文を書かない。書くなら「改善の探索に送った」と書き、裁定の後に直す。前に書くと、裁定が推奨と違ったときに、採用されていない形が正本と証跡に残る
6. 採用したテーマを、行き先で 2 つに分ける。どちらも正本を直接書き換えない
   - **規則の変更**：次のサイクルの 1 つのマイルストーンで試す。状態を `試行中` にし、何をもって効いたとするかと、判定するマイルストーンを書く
   - **実装を伴う変更**：`implementation-plan.md` に、目的・作るもの・判断・完了条件を持つマイルストーンを起こし、次の計画レビューに通す。状態を `起票済み` にする
7. `試行中` で判定するマイルストーンを終えたテーマは、効き目を確かめる。効いたら正本に書き（`反映済み`）、効かなければ戻して理由を書く（`見送り`）

続けて、回し方が効き続けているかを、すでにある証跡と台帳だけで点検する。

| 指標 | 見るもの | 効いていないときの手当て |
|---|---|---|
| 再発 | 再発防止で足した規則に当たる指摘が、また出ていないか | 文書では止まらない種類なので、機械の検査にする |
| レビューの漏れ | 後の段階（逸脱検査・作者のレビュー）で見つかった指摘のうち、前の段階の観点に当たるもの | その観点の中に、必ず見る項目を足す |
| 正本の太り方 | 正本の行の増え方と、棚卸しで減らした行 | 増える一方なら、下の文書の棚卸しを今回回す |
| 攻めの発火 | 改善の候補の `未着手` が何サイクル残っているか | 起動の条件を見直すか、発見のモードで回す |

指摘を 1 件も捕まえていない観点やレビューは、効いていないのか、対象が無かったのかを見分けてから、外すかを決める。

最後に、正本（`architecture/`・`adr/`・`guides/`）を棚卸しする。参照先が消えた記述は削る。同じことを書いた記述は 1 か所にまとめる。1 つのマイルストーンでしか使われなかった記述は、削る候補にする。削ることとまとめることは、足すことより影響が大きいので、PR にまとめて作者のマージを承認とする。

**出すもの**：`improvement.md`（モード、発見の観点ごとの結果、テーマごとの調査と裁定、扱わなかった件数、試行の効き目、回し方の点検、文書の棚卸しの提案）と、改善の候補の台帳の更新

**終えてよい条件**：扱ったすべてのテーマに裁定がある。扱わなかった件数を書いた。`見送り` の理由を台帳に書いた。4 つの指標すべてに結果がある。
