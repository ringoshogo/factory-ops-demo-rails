# コードのコメント

コードを書く人が、コメントを書こうとしたときに読む。レビュー担当は、差分のコメントをこの文書で確かめる。対象は Ruby のコード・マイグレーション・spec・設定ファイルのコメントで、`docs/` の文書は対象外である。

## コメントを読むのは、経緯を知らない人である

コメントを読むのは、数か月後にそのコードを初めて開く人である。その人は、どの順で作られたか、レビューで何を言われたかを知らないし、知る必要も無い。知りたいのは次の 3 つである。

- このコードは、いま何をしているか（コードから読み取りにくい場合だけ）
- なぜこの書き方なのか。素直な書き方に直すと何が壊れるか
- 根拠はどこに書いてあるか（設計文書・ADR の節）

そのため、コメントには、いまの振る舞いと、その理由だけを書く。

## 書くこと

コメントを書く人は、次のどれかに当たるときにだけ書く。

1. **制約・不変条件**：守らないと壊れる条件。「有効在庫が負にならない」「このメソッドの外で数量を書き換えない」
2. **素直な書き方を選ばなかった理由**：読む人が「こう直せばよい」と考えて壊しそうな箇所。ライブラリや DB の挙動が理由なら、その挙動を 1 文で書く
3. **根拠への参照**：判断が設計文書か ADR にあるなら、ファイル名と節の名前で指す。`（docs/architecture/data-model.md「RLS」）`、`（docs/adr/005 決定 2）`
4. **置かないものと、その理由**：生成のままなら入る行を消した・設定を外した・ライブラリの機能を使わないと決めた変更は、コードに跡が残らないので、後から読む人は理由が分からないまま元に戻す。消した場所に最も近い、残った行に、何を置かないかと理由を書く。`# extra_types で型を足さない。書き出しが同じ型を 2 回書く`

コードを読めば分かることは書かない。メソッド名と引数で言えていることを、日本語で言い直さない。

## 書かないこと

コメントを書く人は、次のものをコメントに書かない。どれも、読む時点では古くなっているか、読む人に要らない情報である。

| 書かないもの | 例 | 置き場 |
|---|---|---|
| 作った経緯・直した経緯 | 「レビューで直した」「M3 の指摘で〜にした」「以前は〜だった」 | commit メッセージと PR の説明 |
| マイルストーンの番号 | 「M14 の経路 3」「（M12 の完了条件）」 | 指したいのが設計なら設計文書の節で指す。番号は計画の都合で付け替わる |
| 台帳の ID | 「（OI-35）」「上限ちょうども書く（IB-25）」 | 理由はコメントに文で書き、判断の記録は台帳に置く。台帳の行は片付けば閉じるが、コメントは残り、閉じた行を指し続ける |
| これから作る予定 | 「〜は M15 で足す」「TODO: あとで直す」 | `docs/implementation-plan.md` か issue |
| 消したコード | コメントアウトしたままのコード | git の履歴 |

機能が欠けていて、それを書かないと読む人が誤解する場合は、いまの振る舞いを事実として書き、いつ足すかは書かない。「出荷停止中は M15 で足す」ではなく「出荷停止中は導出しない」と書く。

## このリポジトリの例

**良い例**：素直に書くと壊れる理由を、ライブラリの挙動で書いている。

```ruby
# role IN (...) と書くと、structure.sql を読み込み直したときに式の表記が変わり、差分検査が落ちる
t.check_constraint "role::text IN ('admin', 'member')", name: "users_role_check"
```

```ruby
# graphql-ruby は FORBIDDEN などの GraphQL::ExecutionError を拾って errors に載せるので、例外としては届かない
raise ActiveRecord::Rollback if result["errors"].present?
```

**良い例**：設定の理由と、根拠の節を書いている。

```ruby
# 投入の時機を基底クラスに明示する。Rails の更新で既定値が変わっても黙って切り替わらない（docs/adr/005 決定 2）
self.enqueue_after_transaction_commit = true
```

**悪い例と直し方**：マイルストーンの番号で設計を指している。

```ruby
# ✗ 受注側が所有する出荷実績。発注側が読む SupplierShipment（M14）とは別の型にする
# ○ 受注側が所有する出荷実績。発注側が経路 3 で読む SupplierShipment とは別の型にする
#   （docs/architecture/graphql-schema.md「視点ごとに型を分ける」）
```

**悪い例と直し方**：これから作る予定を書いている。

```ruby
# ✗ 出荷依頼の状況を…優先順で導出する（data-model.md「状態は保存せず…」）。「出荷停止中」は M15 で足す
# ○ 出荷依頼の状況を…優先順で導出する（data-model.md「状態は保存せず…」）
```

**悪い例と直し方**：spec の冒頭で、計画のマイルストーンを根拠にしている。

```ruby
# ✗ 受注の引当（docs/implementation-plan.md M12 の完了条件、docs/architecture/data-model.md「取消と出荷の競合を止める場所」）
# ○ 受注の引当。有効在庫が負にならず、引当のたびに移動履歴が残る（docs/architecture/data-model.md「在庫（`inventory`）」）
```

spec の冒頭のコメントには、その spec が守る規則と、規則が書かれた設計文書の節を書く。

## 機械で止めるもの

カスタム Cop `FactoryOps/NoHistoryComment`（`lib/rubocop/cop/factory_ops/`）が、Ruby のファイルのコメントに次の語が現れたら落とす。`bin/rubocop` が CI で流す。Ruby 以外のファイルは Cop の外にあり、下の検索とレビューで確かめる。

- マイルストーンの番号（`M` に続く数字）。和文に挟まった「停止中はM15で足す」も止め、前後に英数字が続く `M2M` は止めない
- 台帳の ID（`OI-` か `IB-` に続く数字）
- 経緯の語（「以前は」「レビューで」「指摘で」「を直した」「当初は」）。「直した」を「を直した」で見るのは、「読み込み直した」のような複合動詞を止めないためである
- `TODO`・`FIXME`

Cop は語でしか判定しないので、規則に沿っていても止まる文がありうる。その場合は文を言い換える。Cop を無効にするコメントで黙らせない。

Cop が見るのは、RuboCop が読む Ruby のファイル（`.rb`・`.rake` など）のコメントだけである。YAML・SQL・ERB などのコメントは Cop の外にあるので、それらを変えた人とレビュー担当は、同じ語を次の検索で確かめる。検索は文字列の中の語も拾うので、当たった行がコメントかどうかは人が見て判断する。

```sh
git grep -nP "(?<![A-Za-z0-9_])(M|OI-|IB-)\d+(?![A-Za-z0-9_])|以前は|レビューで|指摘で|を直した|当初は|(?<![A-Za-z0-9_])(TODO|FIXME)(?![A-Za-z0-9_])" -- ':!*.rb' ':!*.rake' ':!*.md' ':!*.enc'
```
