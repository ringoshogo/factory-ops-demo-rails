# 開発の回し方

このリポジトリでは、AI が実装し、作者（リポジトリの持ち主の人間）が要求と検収を握る。PR をマージするのは作者だけである。AI の役は 2 つに分かれる。**取りまとめ役**は、マイルストーンを実装者に割り振り、レビューと台帳を回し、成果物をまとめる。**実装者**は、取りまとめ役から 1 つのマイルストーンを受け取って実装するサブエージェントである。作者は不在のことが多いので、取りまとめ役は、作者を待たずに進められるところまで進め、作者の判断が要る事項は台帳に積んで先へ進む。

この文書は、そのための開発の回し方を決める。実装を再開する人（AI を含む）は、`handoff.md` の次にこれを読む。文書のパスは、`docs/` からの相対で書く。

## 全体の流れ

開発は、いくつかのマイルストーンをまとめた**サイクル**で回す。1 つのサイクルは次の順に進む。

```
1. 計画レビュー       サイクルに入るマイルストーンの計画を、実装の前に判定する
2. マイルストーンの実装  マイルストーンごとに：残件を読む → テストから実装 → 完了の判定 → PR → 実装レビュー
3. サイクル末         振り返り → 知見の収穫 → 逸脱検査 → 再発防止 → 台帳の棚卸し
4. 改善の探索         改善の候補が溜まったときだけ、サイクル末の後に回す
```

各段階の結果は、サイクルごとの**証跡**として `plans/cycle-NN/` に残す。証跡はその時点の記録で、後から書き換えない。いまの正しい状態は、設計文書・ADR・`guides/` などの**正本**に書く（「文書の置き場と、書く前の振り分け」）。

サイクルをまたいで残る事項は、2 つの台帳に積む。

- **残件**（`plans/open-items.md`）：その場で片付けず、決まったマイルストーンまでに決着させる事項。ID は `OI-NN`
- **改善の候補**（`plans/improvement-backlog.md`）：期限は無いが、いまのやり方より良くできるかもしれない事項。ID は `IB-NN`

境界は、決着させないと先へ進めないかどうかである。進めないなら残件、良くできるかもしれないだけなら改善の候補にする。

取りまとめ役は、サイクルのマイルストーンが作者の判断（`blocked-user`）を待って着手できず、ほかのマイルストーンを終えたら、そのマイルストーンを表で次のサイクルへ移し、サイクル末に入る。待つ間は、終えたマイルストーンで分かったことが正本へ戻らないからである。移したマイルストーンは、計画レビューを済ませていても、次のサイクルの計画レビューに含め直す。サイクル末で正本が変わり、計画の節が古くなりうるからである。

着手して実装レビューまで終えたが、作者の判断・作者の受け入れ・作者の実機の確かめが残って `bin/check-open-items --due` を通せないマイルストーンも、待たずにサイクル末に入る。取りまとめ役は、そのマイルストーンを実装レビューの節がある今のサイクルのものとして数え、作者を待つ残りだけを「<マイルストーン> の残り」として次のサイクルの表に移す。待つ行の引当先は変えない。残りは、計画レビューで作者の答えに合わせて節を直してから片付ける。

## 独立したレビュアー

計画レビュー・実装レビュー・逸脱検査・改善の探索の裁定は、取りまとめ役や実装者とは別のコンテキストのレビュアーが行う。作った本人の思い込みを、次の段階へ流さないためである。レビュアーは次の 2 系統で、同じモデルの盲点を減らすために両方へ同じ依頼を渡す。

- **Codex**：`codex exec -s read-only "<依頼>" < /dev/null`。標準入力を閉じないと、入力待ちのまま止まる。
- **Claude**：取りまとめ役とも実装者とも別のサブエージェント。

レビュアーを立てる者（取りまとめ役か、取りまとめ役から依頼を受けた実装者）は、結果を自分で受け取る形で立て、レビュアーが終わるまで自分の作業を終えない。Codex は、標準出力を一時ファイルの置き場のファイルへ書き出す。Claude は、名前を付けずにサブエージェントとして立て、依頼に書いた一時ファイルの置き場のファイルへ結果を書かせる。名前を付けたチームメイトとして立てると、終わりの知らせが立てた者ではなくチームの取りまとめ役に届き、結果を待っている者に届かない。立てた者は、どちらの系統の結果も、そのファイルから読む。サブエージェントの最終報告は、実行の環境の受け渡しの道具を呼んだときだけ届き、文章を書いて終えただけでは届かないので、正の受け取り口にしない。依頼には、結果をファイルに書いて終えることだけを書き、受け渡しの道具を呼ぶことを求めない。立てた者が先に終わると、道具を呼んだレビュアーは戻す先の無い受け渡しを繰り返して止まらないからである。ファイルが無いか途中で切れていれば、同じサブエージェントにメッセージで書き終えさせる。レビュアーに、結果をメッセージで別の者へ送らせない。名前を指定した送り先は実行の環境が解決するので、届かないか、送り主自身に届くことがある。結果を受け取った者は、証跡に写してから次へ進む。写したら、立てたレビュアーを止める（実行の環境のタスクを止める道具に、サブエージェントの ID を渡す）。止めないと、終わったサブエージェントが一覧に残り続け、作者からはまだ動いているように見える。

Codex を読み取り専用で立てると、DB にも一時ファイルにも書けないので、DB を使う spec を流せない。レビュアーが流さなかった確かめは、実装者が証跡に書いた実行の記録で補う。取りまとめ役は、どちらの系統も spec を流さなかったときは、そのことを実装レビューの節に書き、証跡の冒頭の説明をそれに合わせる。

Codex が混み合いなどの一時の失敗で結果を返さなかったときは、同じ依頼で 1 回だけ出し直す。出し直しても失敗したときと、利用上限などで使えないときは、Claude の系統だけで判定して先へ進める。取りまとめ役は、出し直したこととその結果を証跡に書く（OI-05）。

### レビュアーに渡すもの

取りまとめ役は、リポジトリにある成果物だけをレビュアーに渡す。計画の節・設計文書・diff・テストと検査の実行結果・前のマイルストーンの実装レビューの節・台帳である。実装中の会話や、取りまとめ役による補足の説明は渡さない。成果物だけから制約と境界を読み取れないなら、それ自体を指摘にする。

### 依頼の型

取りまとめ役は、レビュアーへの依頼を毎回次の型で書き、2 系統へ同じ文面を渡す。型を外れた依頼では、観点ごとの判定と違和感が出てこない。

1. 対象：段階の名前と、読むもの（計画の節・diff の範囲・設計文書・前のマイルストーンの実装レビューの節・台帳）と、読む版の commit の SHA。レビュアーは作業ツリーではなく、その commit のファイルを読む（`git show <SHA>:<パス>` か、その commit の worktree）。取りまとめ役は、レビューの間に同じ作業ツリーの計画や実装を書き換えるので、作業ツリーを読ませると、直している途中の版への判定が返る
2. 観点：その段階の 5 つの観点を、この文書の文言のまま並べる。マイルストーンに固有の確かめどころは、当てはまる観点の下に足し、観点の数は増やさない
3. 判定の定義：下の「判定の形」の表（Go・Conditional Go・No-Go の意味と、重大度の 4 段階）
4. 出す形：観点ごとの「指摘」か「指摘なし」、重大度付きの指摘、全体の判定、違和感の欄（無ければ「なし」）。複数のマイルストーンを 1 回で渡すときは、観点ごとの結果と判定をマイルストーンごとに出させる。全体の判定だけでは、どのマイルストーンに着手してよいかが決まらない

### 判定の形

レビュアーは、段階ごとに決めた 5 つの観点をすべて評価し、観点ごとに「指摘」か「指摘なし」かを書く。観点を書かずに全体の印象だけで出した判定は、判定として扱わない。そのうえで、全体の判定を次の 3 つから選ぶ。

| 判定 | 意味 | 取りまとめ役がすること |
|---|---|---|
| Go | Critical と High の指摘が無い | 先へ進む |
| Conditional Go | レビュアーが名指しした指摘を直せば Go | 直したことを証跡に書いて先へ進む。再レビューは要らない |
| No-Go | 直した後に、もう一度判定が要る | 直して、同じ観点で再レビューに出す |

指摘には重大度（Critical・High・Medium・Low）を付ける。取りまとめ役は、Critical と High を直してから次へ進む。Medium と Low は、同じマイルストーンで直すか、残件に登録して引当先を書く。

レビュアーが書いた全体の判定と、指摘の重大度が表と合わないことがある（Medium だけで No-Go など）。取りまとめ役は、重大度から表に照らして判定を決め直し、証跡には両方を書く。

No-Go の後の読み直しは、前の指摘が解消したかと、High 以上の新しい指摘だけで判定し、2 回までにする。2 回目の読み直しで High が残ったら、取りまとめ役は直しを読み直しに出さず、直したことと、閉じたことを確かめた壊し方を証跡に書く。同じ守り（1 つの期待や 1 つの検査）に続けて High が出たら、指摘された形を足して直す前に、照らし方そのもの（落とす形を並べるか、許す形を決めるか）を計画の節に戻して決め直す。落とす形を並べる照らし方は、並べた形の外に穴が残り、直すたびに次の形が見つかるからである。読み直しで出た Medium 以下は、そのマイルストーンで直すか残件に積み、もう一度の読み直しには出さない。読み直しのたびに新しい Medium が出て、判定が終わらなくなるからである。

レビュアーは、指摘とは別に**違和感**の欄を書く。判定を左右しないが、記録しておくべき観察（規則どおりだが読みにくい、この領域だけ例外が増えている、など）である。無ければ「なし」と書く。取りまとめ役は、判定を受け取ったら違和感を改善の候補に移す。移さないと、その観察はレビュアーのコンテキストと一緒に消える。移す前に、その観察が正本の規則（この文書の「テストから書く」など）に反していないかを確かめる。反していれば、違和感ではなく指摘として扱い、そのマイルストーンで直すか、残件に引当先を付けて積む。改善の候補に移すと、規則に反したまま期限の無い行になる。

指摘が無くても、判定と観点ごとの「指摘なし」を証跡に残す。

## 1. 計画レビュー

取りまとめ役は、サイクルに入る前に、サイクルに入るマイルストーンの節（`implementation-plan.md`）を 2 系統のレビュアーに渡す。観点は次の 5 つである。

1. **設計文書との整合**：設計文書・ADR と食い違わないか。`guides/packs-and-packwerk.md`「層ごとの責務」の一覧に照らし、判断と不変条件を置く層と、同じテナントの中を同期の呼び出しでつなぎテナントをまたぐ連結だけをイベントにする分け方が、一覧のとおりか。書き込みを足すマイルストーンが、テナントの境界（RLS・policy・行列テストの行）とコンテキストの境界（packwerk の依存）への影響を、影響が無いならその理由を書いているか。役割の制限を足すか変えるマイルストーンが、制限する値（単価など）を書くすべての入口（mutation・取り込み・ジョブ・rake タスク）を挙げ、どの入口も同じ規則を通るかを書いているか。制限を操作の単位で決めると、同じ値を書く別の入口が制限の外に残る
2. **完了条件を機械で確かめられるか**：完了条件が、最初に落とすテスト（spec のパス）と、`implementation-plan.md`「共通の完了条件」と同じ形のコマンドで書けているか。2 つのマイルストーンが、同じ落ちるテストを当てにしていないか（先のマイルストーンが通すと、後のマイルストーンが最初に落とすテストが消える）。壊して落ちる記録の表に、同じ条件を 2 つの守り（RLS と scope など）が持つ行があれば、落ちると書いた example が、壊さない側の守りを通らない経路か（「テストから書く」）。計画の表は流さずに書いた予想なので、もう片方の守りが同じ結果を返して落ちないことがある
3. **実現できるか**：使う gem とその版で実現できるか。外部のライブラリの既定値（検証・時間切れ・例外の階層）に依存するなら、原文を引いているか。このリポジトリの設定（spec を流す順、並行の数など）に依存するなら、設定の実物（`spec/spec_helper.rb` など）を引いているか。生成器が置いた注釈の中の設定は効いていない
4. **順序と依存**：マイルストーン間の順序と、隠れた依存が無いか。あるマイルストーンが作業を後のマイルストーンへ送るなら、送り先の節の作るものと完了条件にその作業があるか
5. **範囲と曖昧さ**：実装者が決めざるを得ない曖昧さが無いか。目的から外れた範囲の広がりが無いか

サイクルのマイルストーンが多く、1 つのサブエージェントで読み切れずに止まったときは、取りまとめ役は同じ依頼で出し直すか、マイルストーンを分けて出し、どちらにしたかを証跡に書く。

取りまとめ役は指摘に沿って計画の節を直し、判定と対応を `cycle-NN/plan-review.md` に残す。判定には、マイルストーンごと・系統ごとに、5 つの観点の「指摘」か「指摘なし」を、観点の名前で書く（「判定の形」）。`bin/check-open-items` が、サイクル 10 からの証跡で、観点の名前が 1 つも無いものを落とす。マイルストーンごと・系統ごとに書いたかは、検査は見ないので、取りまとめ役が証跡を書くときに確かめる。計画レビューが Go か Conditional Go になるまで、サイクルの最初のマイルストーンに着手しない。

計画レビューで作者の判断を待つ行（`blocked-user`）を起こしたら、取りまとめ役は行ごとに、答えで作るものの形が変わるか、値の差し替え・受け入れ・実機の確かめで済むかを行の内容に書き、計画レビューの PR の本文の冒頭に並べて作者に渡す。前者は、答えが来るまでそのマイルストーンに着手しない。答えの無いまま作ると、作り直しになるからである。後者は既定で作り、差し替える場所を節と手順書に書いて、答えが来なければ上の「残り」として次のサイクルへ移す。

取りまとめ役は、作者に答えを求める行ごとに、1 件ずつ説明の文書（`plans/cycle-NN/` に置く）を書いて渡す。説明には、問題の中身、流用元がどう作っているか、答えごとに作るものと費用、答えごとに何が見せ場になるか、既定を書く。作者は、見せ場と費用を比べて選ぶので、境界や制限だけを書いた問いでは選べない。説明に書く費用と作るものは、書く前にコードか担当の調べで確かめる。確かめずに書くと、作者が誤った費用で選び、後で訂正が要る。

> サイクル 06 で作者は、並べ替えの列を限るかの問い（OI-144）に、流用元の作りと見せ場を問い返してから既定を変え、判断を 1 件ずつ仰ぐよう求めた。

> サイクル 05 の M41 は、ホスト名・作り直しの時刻・資源・許す操作が後者で、既定で作ってから答えを待ち、残りをサイクル 06 へ移した。

## 2. マイルストーンの実装

マイルストーンごとの手順は `implementation-plan.md`「1 つのマイルストーンの進め方」にある。この節は、その手順にレビューと台帳をつなぐ。

### 着手の前に

取りまとめ役は、次の 2 つを確かめてから、マイルストーンを実装者に渡す。

- **前のマイルストーンの実装レビューの節が、証跡にある**：判定が Go か、Conditional Go の指摘を直し終えていること。節があるかどうかで、中断した作業をどこから再開するかも決まる。
- **残件のうち、引当先がこのマイルストーンの行を読んだ**：実装者への依頼に、その行の ID を含める。

作業ツリーに書き込む担当（実装者・計画レビューの直しの担当・台帳や証跡の直しの担当・サイクル末の担当）を並行で動かすときは、取りまとめ役は依頼に担当ごとの worktree と一時ファイルの置き場と、作者の判断の受け口のファイル（一時ファイルの置き場の `decisions.md`）を書く。同じ作業ツリーで動かすと、ほかの担当が切ったブランチに commit が載り、一時ファイルが混ざる。取りまとめ役自身が書き込むときも、動いている担当の作業ツリーを使わない。

### ブランチと PR

マイルストーンごとに、前のマイルストーンのブランチから `mNN-...` を切り、main を base にした PR を作る（PR を積み重ねる）。前のブランチを base にすると、前の段をマージしてブランチを消したときに、上の段の PR が閉じる。前の段が未マージの間は、その commit も PR の差分に見えるので、取りまとめ役はレビューの依頼に前の段の先端からの diff の範囲を書く（「依頼の型」）。main への直接の push はフックが拒否し、PR のマージは作者が前から順に行う。

積み重ねた PR の下の段に直しを入れると、上の段は古い土台のまま残る。取りまとめ役は、次の 3 つで衝突と記録のずれを防ぐ。

- 台帳に行を足すのは、積み重ねの最上段に限る。下の段の直しで要る行も、最上段で足す。並行のブランチがそれぞれ「最後の番号の次」を振ると、ブランチの中では番号が続くので `bin/check-open-items` を通るが、載せ直しで番号がぶつかる
- `handoff.md` の rspec の件数のように、マイルストーンごとに必ず変わる行は、最上段だけが書き換える。最上段の担当は、`handoff.md`「リポジトリの状態」の実装の行に、下の段のマイルストーンのうちまだ書かれていないものも書く。下の段の担当は最上段が書くとみて書かず、最上段の担当は自分の分だけを書くので、間の段が抜ける
- 下の段に直しを入れたら、上の段を載せ直し、台帳と証跡に書いた SHA を載せ直した後のものに置き換える。`bin/check-commit-refs` が、HEAD の祖先でない SHA を落とす

担当は、`git push` にも `GH_TOKEN=$(gh auth token -u ringoshogo)` を付けて流す。github.com の資格情報は gh の補助を通り、付けなければ gh の既定のアカウント（このリポジトリに push できないアカウント）で認証して 403 になる。取りまとめ役は、担当への依頼に gh と `git push` の両方を挙げる。

PR を出した担当は、CI の結果を `GH_TOKEN=$(gh auth token -u ringoshogo) gh pr checks <PR の番号> -R ringoshogo/factory-ops-demo-rails --watch` をフォアグラウンドで流して待ち、通るか落ちるかを見てから次へ進む。作業を区切って止まって待たない。止まった担当は、CI が終わっても知らせを受けないので、誰かが起こすまで動かない。コマンドが実行の時間の上限で戻ったら、同じコマンドをもう一度流す。CI のほかのもの（マシンの負荷が下がること、ほかの担当の DB や worktree が空くこと）を待つときも、担当は上限の時間を決めて前景で待ち、上限を過ぎたら待つのをやめて、待った時間と状態を取りまとめ役に返す。終わりの合図を出さない監視を置いて止まると、待っている理由が消えても誰にも知らされない。取りまとめ役は、担当への依頼に待ちの上限を書き、担当から報告が無いまま上限を過ぎたら、担当に状態を問う。

### テストから書く

- 実装者は、テストを先に書き、実行して落ちることを見る（RED）。RED に数えるのは、期待の不一致で落ちたものである。定数やメソッドが無いことによる読み込みの失敗（`NameError`・`NoMethodError`）は、example がどの期待を確かめるかを示さないので、RED に数えない。落ちた出力を、PR の本文か証跡に残す。書いた時点で通ったテストは、仕様を捉えていないので、テストを設計し直す。実装の後に書いた spec と、読み込みの失敗でしか落ちなかった spec は、次の項の壊して落ちる記録で RED に代え、証跡の「実装の記録」に spec ごとにどちらかを残す。
- 実装して通した後（GREEN）、実装をわざと壊して（条件を外す・比較を変える）テストが落ちることを確かめてから戻す。テストの基盤（example の除外・検出の包み・後始末・補助）を足したときは、その防壁を外すと落ちる example（ガードの example）も足す。基盤は業務の実装ではないので壊す対象に挙がりにくく、除外を外しても何も落ちない形で残る。壊す前にファイルを複製し、複製から戻す。`git checkout -- <file>` は未コミットの作業も消す。
- 同じ条件を 2 つの守りが持つとき（RLS と scope、書き込みのポリシーの `WITH CHECK` と SELECT のポリシー、行ロックと一意索引）は、片方ずつ壊す。片方を壊しても、もう片方が同じ結果を返して何も落ちないことがある。落ちなければ、もう片方を通らない経路で確かめる example を足す（RLS は生 SQL で、`WITH CHECK` は `RETURNING` の無い INSERT で）。足せなければ、落ちない守りとして証跡に書き、改善の候補に積む。
- 「届かない」「ならない」「空になる」のような否定を確かめる example は、同じ準備で肯定の側が成り立つこと（相手の行が実在し、絞らなければ自社の行が返り、別の受注なら状態が変わる）を同じ example で先に確かめる（対照）。対照の無い否定は、実装が無くても通る。S1 の一覧の行は spec が対照を機械で確かめる（`guides/testing.md`「S1 の入口の列挙」）が、単体の example には検査が無い
- 規則を守る検査が対象を集めるとき（`admin` に限る操作、テナントの表、受け手）は、規則の正本（設計文書の表、配送表、スキーマ）から集め、規則を実装した側（規則を評価する補助、ある呼び出し元）から集めない。実装した側から集めると、実装に無い対象が検査の外に残り、実装の抜けを検査が写し取る。設定のファイル（ワークフロー・マニフェスト）を照らす検査は、規則が効く場所をすべて集めて照らし（ジョブの段とステップの段、ジョブの既定とステップの値）、集合は不足だけでなく等しいかで比べる。名指しした 1 か所だけを照らすと、同じ規則の別の場所を書き換えても落ちない
- 証跡に件数や再現率を書くときは、流したコマンドと対象の commit を添える。添えないと、後の直しで数が変わったときに、どの時点の数かが分からない。
- 1 回だけ落ちたテストを、再実行で緑にして流さない。繰り返し流して再現率を測り、原因がテストの書き方か製品の競合かを分ける。製品の競合なら、修正の前後の再現率を証跡に残す。

### 前提が崩れたとき

実装者は、実装中に計画の前提が崩れたら、黙って実装を変えない。崩れた先で 3 つに分け、取りまとめ役に返す。

| 崩れた先 | 例 | 取りまとめ役がすること |
|---|---|---|
| 計画 | マイルストーンの分け方・完了条件が合わない | 計画の節を直し、直した理由を証跡に書く |
| 設計文書・ADR | 設計の方針が実装で成り立たない | 先に設計文書か ADR を直してから実装を続ける。方針の変更が大きいなら、計画レビューに戻す |
| 作者の判断 | 業務の振る舞い・範囲そのものが変わる | 残件に `blocked-user` で登録し、そのマイルストーンを止めて、進められる別の作業へ移る |

### 作者が不在の間に決めたこと

計画に書かれておらず、作者に確かめられないまま決めたことは、取りまとめ役が 1 件ずつ残件に `judgment` として登録する。実装者は、証跡の「計画との違い」の項目ごとに、登録した `judgment` の行の ID を書くか、決めたことが無い（計画の文のとおりに直しただけ、前提が実物と合っていた、正本の規則が形を 1 つに決めていた）なら「判断なし」と書く。計画の文から外れた形（計画が挙げた参照先と違う先を指すなど）、計画が書かなかった細部の選択、計画が名指ししない文書に新しい記述を足したことは、規則に照らして選んだものでも決めたことなので、`judgment` で登録する。名指しの外に残った前の形を消す直し（「1 つのマイルストーンの進め方」2）は、規則が形を 1 つに決めているので「判断なし」に当たる。規則が選べる形を 2 つ以上残すなら、どれを選んだかは作者に見えないからである。`bin/check-open-items` が、サイクル 10 からの証跡で、`judgment` か `decided` の行の ID も「判断なし」も無い項目を落とす。作るものの ID のように、決めたことを登録した行でない ID は数えない。実装の途中で前提が崩れて計画の節に書き足した決め（取りまとめ役の判断と、計画が「実装で決める」とした値）も、作者が確かめていなければ同じく登録する。計画の節に書き足しただけでは、作者への一覧に載らない。PR と証跡からは ID で参照する。決めた内容が設計に関わるなら、該当する設計文書の節にも書く。決めた内容が、計画の節（前のマイルストーンの節を含む）か設計文書の書き方と違うなら、前の形を種類で `git grep` し、計画・設計文書・ADR の要約・DB の表の説明・コメントのどこにも残っていないことを確かめる（「実装レビュー」の直しと同じ）。

### 完了の判定

実装者は、`implementation-plan.md` の完了条件と「共通の完了条件」をすべて通す。完了条件の `git grep` は、文書と証跡を書き終えた最後の commit で流し直し、コマンドと件数を証跡の「手元で流したもの」に書く。同じマイルストーンで後から書いた文書の文が、前の形に当たることがあるからである。`bin/check-open-items` が、サイクル 11 からの証跡で、計画の節の囲み（```` ``` ```` か `~~~`）の中の `git grep` が、数字の件数の注釈（`# 0 件` の形）とともにマイルストーンの節の囲みの中に無いものを落とす。件数を後で書くと予告して出すと、この検査で CI が落ちる。そのため、計画を書く者は、機械で確かめる `git grep` を完了条件の囲みに書く。本文に書いた `git grep` は検査が拾わない。「残り」の作るものと完了条件は、計画の節の「残り（サイクル NN）」の段落の後ろに、次の「残り」の段落より前に書き、証跡の節の見出しは「<マイルストーン> の残り（サイクル NN）」の形にする。検査は、その段落から次の「残り」の段落か節の終わりまでを「残り」の分として読み、番号の無い「残り」の見出しを落とす。「1 か所と参照だけ」のように範囲を言う完了条件は、名指しの節の外も含めて、`docs/plans/` を除く全体を数える。共通の完了条件には `bin/check-open-items --due MNN` が含まれ、引当先がそのマイルストーンの `open` と `blocked-user` が残っていれば落ちる。そのため、PR を出す前に、実装者は片付けた残件を `closed`（commit の SHA を添える）にし、取りまとめ役は片付かなかった残件の引当先を後のマイルストーンへ書き換える。実装者は、PR を出す前に、引当先がそのマイルストーンの行を台帳でもう一度読む。着手の後に作者の判断で行が変わっていることがあるからである。

### 実装レビュー

取りまとめ役は、PR を作ったら、2 系統のレビュアーに PR の diff・計画の節・検査の実行結果・前のマイルストーンの実装レビューの節・台帳を渡す。RED と壊して落ちる記録は、実装者が証跡（`implementation-reviews.md` のマイルストーンの節の「実装の記録」）に書いて commit してから、その版をレビューに出す。依頼の本文にだけ書くと、レビュアーが成果物だけを読む規則（「レビュアーに渡すもの」）から外れ、後から証跡に写すときに食い違う。観点は次の 5 つである。

1. **計画への準拠と範囲**：完了条件を満たし、その結果が diff と実行結果に一致するか。計画に無い変更が混ざっていないか。引当先がこのマイルストーンの残件と、前のマイルストーンのレビューで持ち越した指摘を片付けたか。証跡の「計画との違い」で「判断なし」と書いた項目ごとに、計画の文のとおりか、前提が実物と合っただけか、正本の規則が形を 1 つに決めていたかを見る（「作者が不在の間に決めたこと」）。計画の作るものと違う形にした項目は、計画の節も直したかを見る
2. **正しさ**：ロジック・境界の値・失敗の経路・並行の競合
3. **境界と規約**：テナントの境界とコンテキストの境界を守るか。設計文書・ADR・`guides/comments.md` の規則から外れていないか。`guides/packs-and-packwerk.md`「層ごとの責務」の一覧に照らし、判断を置いた層と、同期と非同期の分け方が一覧のとおりか
4. **テストの検出力**：spec ごとに、RED か、それに代わる壊して落ちる記録があるか。2 つの守りが同じ条件を持つなら、片方ずつ壊したか。足した業務の分岐（数量の上限・状況ごとの拒否・導出表の行）に、その分岐を確かめる単体の spec（`packs/*/spec`）があるか。上限には、実装の中で増えた上限を含めて、上限ちょうどと上限 + 1 の両方の example が仕様の値であるか（`guides/testing.md`「層への配分」）。規則を守る検査の対象と期待値を、規則の正本から集めているか（実装の定数や補助から作っていないか）。実装を壊したときにテストが落ちるか。空の集合どうしの比較のように、実装が無くても通るテストになっていないか。テストの基盤（除外・包み・後始末・補助）を外したときに何が落ちるかを必ず見る
5. **参照の維持**：変えた振る舞いに合わせて、設計文書の節を直したか。直した記述と同じものが計画の節にあれば、計画の節も直したか。外部のライブラリの既定値に依存する実装が、原文を引いているか。参照している正本が別の変更で書き換わり、前提が古くなっていないか

取りまとめ役は、指摘か違和感を直すとき、指摘された箇所だけでなく、直す前の形を種類で `git grep` して数え、計画の節・設計文書・コメント・spec のどこにも残っていない（0 件）ことを確かめてから閉じる。指摘の文言だけを直すと、同じ種類の残りが次のサイクルまで残る。

取りまとめ役は、判定・観点ごとの結果・指摘と対応・違和感と、分岐の網羅率の警告の件数とそのうち example を足した件数（`guides/testing.md`「分岐の網羅率の警告」）を、`cycle-NN/implementation-reviews.md` のマイルストーンの節に残す。持ち越す指摘は残件に、違和感は改善の候補に移す。最後に `handoff.md`「リポジトリの状態」の実装の行を更新する。

### 担当を止めるとき

担当は、完了報告の前に、自分が立てたサブエージェントがすべて止まっていることを確かめ、報告に書く。取りまとめ役は、完了報告を受けて、次の順に担当を止める。

1. 担当に終わりの依頼を送り、終わったことを確かめる
2. `RAILS_ENV=test bin/rails temp_databases:list` で一時の DB を読み、その担当が作った DB（依頼に書いた `TEST_DATABASE`・`E2E_DATABASE` の名前）を `RAILS_ENV=test bin/rails "temp_databases:drop[<名前>]"` で消す（`guides/bin.md`「bin/rails で流す運用のタスク」）。一時の DB は作った担当が止まっても残り、照合順序の版を改める手間が残った数だけ増える。ほかの担当の DB と、接続の残る DB は消さない。接続が残って消せなければ、接続を持つプロセス（担当が起こした E2E の Rails や `bin/jobs`）を止めてから流し直し、止められなければ残した DB の名前を作者への報告に書く
3. エージェントの一覧（`ListAgents`）を読み、動いている（running）もののほかに、止まったまま残っている担当やサブエージェントがあれば止める。止まったものは自分からは消えないので、立てた者が止めない限り、何日も一覧に残る

マイルストーンの区切りごとと、作者に進み具合を報告する前にも、3 の一覧を読む。

### マイルストーンに属さない変更

文書の修正・依存の更新・レビューの指摘の修正のように、マイルストーンに属さない変更では、計画レビューを飛ばす。テストから書くことと、共通の完了条件は飛ばさない。コードを変えるなら、実装レビューも通す。

## 3. サイクル末

取りまとめ役は、サイクルの最後のマイルストーンの実装レビューを通した後に、次の 5 つの段階をこの順に回す。前の段階の出力が、後ろの段階の入力になるからである。各段階で読むもの・出すもの・終えてよい条件は `guides/cycle-end.md` にある。

1. **振り返り**：計画の精度と、レビューの指摘・手戻り・詰まりを棚卸しし、同じ種類の指摘を数える
2. **知見の収穫**：実装で分かったことのうち正本に無いものを、置き場を振り分けて正本へ書く
3. **逸脱検査**：独立したレビュアーが、成果物を正本と突き合わせ、食い違いごとにどちらが正しいかを裁定する
4. **再発防止**：指摘と食い違いの原因をたどり、同じ種類が再び起きない仕組み（検査・規則・文書）を足す
5. **台帳の棚卸し**：残件を全部読み直し、作者の判断が要るものを一覧にする。改善の候補の状態から、改善の探索を回すかを決める

正本への変更は 1 本の PR にまとめ、作者のマージを承認とする。作者を待たずに次のサイクルへ進むときは、次のサイクルの最初のブランチをこの PR のブランチから切る。サイクル末の担当は、サイクル末のブランチを `origin/main` の先端から切る。最後のマイルストーンの PR がまだ main に入っていなければそのブランチから切り、取りまとめ役は、main にあってそのブランチに無い変更（`git log <ブランチ>..origin/main`）を、次のサイクルの計画を書く前に数える。計画の作るもののうち、その変更と同じ文書の同じ節を書き換えるものは、その変更を祖先に持つブランチ（main から切るサイクル末のブランチなど）に置く。担当の実行の環境は main のマージを拒むので、担当に main を取り込ませる計画にしない

## 4. 改善の探索

台帳の棚卸しが、改善の候補の台帳を読んで起動を決める。サイクルの数では決めない。取りまとめ役はセッションをまたいで状態を持たず、いま何サイクル目かを覚えていないので、ファイルを読めば判定できる条件にする。手順は `guides/cycle-end.md`「改善の探索」にある。

改善の探索は、正本を直接書き換えない。採用した候補は、規則の変更なら次のサイクルの 1 つのマイルストーンで試し、実装を伴うなら `implementation-plan.md` にマイルストーンとして起こして、計画レビューから通す。

## 文書の置き場と、書く前の振り分け

### どの問いに、どの文書が答えるか

開発の局面ごとに出る問いには、決まった文書が答える。答える文書が決まっていないと、同じ問いの答えが複数の文書に散り、片方だけが古くなる。

| 局面 | 出る問い | 答える文書 |
|---|---|---|
| 計画を書く・レビューする | このマイルストーンで何を満たせば終わりか | `implementation-plan.md` の完了条件 |
| 〃 | 業務の流れと規則はどうなっているか | `architecture/context-map.md` |
| 〃 | 既存の構造を変えてよいか。誰かが理由があって決めたのか | `adr/`・`architecture/decisions.md` |
| 実装する | どう作るか（表・型・境界・コメント・設定） | `architecture/data-model.md`・`architecture/graphql-schema.md`・`guides/comments.md`・`guides/packs-and-packwerk.md`・`guides/config.md` |
| 〃 | 計画に書いていない振る舞いを、何を根拠に決めるか | `architecture/context-map.md`。無ければ作者の判断（残件の `blocked-user`） |
| 〃 | どう動かすか（環境・検査・CI） | `README.md`「開発環境」・`guides/bin.md` |
| 回す | どの順で何をするか | この文書・`guides/cycle-end.md` |
| 引き継ぐ | いまどこにいて、次に何をするか | `handoff.md`・台帳 2 本 |

まとめると、正本は答える問いで次の 4 つに分かれる。

| 分類 | 答える問い | 置き場 |
|---|---|---|
| 満たすこと | 何を満たせばよいか（業務の規則・完了条件） | `architecture/context-map.md`・`implementation-plan.md` の完了条件 |
| 作り方 | どう作るか（構造・規約） | `architecture/data-model.md`・`architecture/graphql-schema.md`・`guides/` の規約と解説 |
| 決定 | なぜそう決まっているか（比べた選択肢・退けた案・裏返る条件） | `adr/`・`architecture/decisions.md` |
| 手順 | どう回すか・どう動かすか | この文書・`guides/cycle-end.md`・`README.md`「開発環境」・`guides/bin.md` |

同じ規則を 2 つの分類に書かない。業務の規則は `architecture/context-map.md` に置き、作り方の文書からはそこを参照する。

手順の文書（`handoff.md`・`README.md`「開発環境」・`guides/bin.md`・`runbooks/`・`deploy/README.md`）にコマンドを書く人は、その実行にだけ効く形（環境変数・コマンドの引数）で書く。ホストの全体の設定を変えるコマンド（gh や git の既定のアカウントの切り替え、全体の git の設定、パッケージのインストール）は書かない。手順を読んだ AI がそのまま流し、作者の環境をほかの作業ごと変えるからである。秘密の値（パスワード・鍵・トークン）は、コマンドの引数に入れず、標準入力か環境変数で渡す。引数はプロセスの一覧と shell の履歴に残るからである。

外部の公式文書や事例を調べるのは自由だが、調べた結果を作り方の文書に直接書かない。このデモでどう決めたかを、計画の節の「判断」か ADR に書く。同じ判断が繰り返されたら、作り方の文書に一般化する。

### 書く前の振り分け

知見の収穫と再発防止で正本へ何かを書くとき、取りまとめ役は書く直前に、その 1 項目をどの分類に置くかを決める。決めないまま書くと、行き場に迷った記述が作り方の文書に溜まり、規約が手順と決定の理由で埋まる。

1 つの項目が複数に当てはまって見えることがあるので、次の問いを上から順に当て、最初に当たったところで確定する。

| 順 | 問い | 当たれば |
|---|---|---|
| 1 | 判断のためではなく、作業のために読むものか | 手順 |
| 2 | コードを消しても残す必要があるか（コードは、いまどう動くかしか語らない） | 満たすこと |
| 3 | 比べた選択肢・退けた案・裏返る条件を含むか | 決定 |
| 4 | どれでもない | 作り方 |

作り方を最後に置くのは、作り方が最も広く、先に問うと何でも吸い込むからである。4 つのどれにも確信を持てない項目は、作り方に落とさず、正本に書かないで次のサイクルへ送る。

決定のうち、次のどれかに当たるものだけを ADR にする。それ以外は、規約の行の中に 1 文で理由を書く。

- 複数の選択肢を実際に比べた
- 戻し方が通常と違う
- 複数のコンテキストかマイルストーンにまたがる

新しい ADR は、冒頭の「ステータス」の節に、決定と裏返る条件を 1 文ずつ書く。読み手の大半はそこで判断が付き、本体を開かずに済む。規約や設計文書の行のうち、ADR の決定から来ているものには `（adr/NNN）` のように ADR を添える。ADR は一覧から読ませず、この参照から読ませる。レビュアーや取りまとめ役は、その行を変えようとしたときだけ、参照先の ADR を開く。

## 残件の台帳

正本は `plans/open-items.md` の 1 つだけである。`handoff.md`・証跡・PR の本文は、残件を ID（`OI-NN`）で参照し、同じ内容を散文で書かない。散文で複数の箇所に書くと、片方だけが古くなり、記録はあるのに誰も拾わない状態になる。コードのコメントには ID を書かない。台帳は片付けば閉じるが、コメントは残るからである（`guides/comments.md`）。

| 状態 | 意味 | 結果の欄 |
|---|---|---|
| `open` | 引当先のマイルストーンで片付ける | 空 |
| `judgment` | 作者が不在の間に取りまとめ役が決めた。作者の確認を待つ | 空 |
| `blocked-user` | 作者の判断が無いと進められない | 空 |
| `decided` | 作者の判断か、要らなくなった理由で閉じた | 閉じた理由 |
| `closed` | 片付けた | commit の SHA |

引当先には、条件ではなくマイルストーンの番号を書く。「〜するとき」のような条件では、マイルストーンを終えるときの `--due` の検査に引っ掛からない。

台帳を読み書きするのは次の時機だけである。

- **取りまとめ役が、マイルストーンに着手する前に読む**：引当先がそのマイルストーンの行
- **取りまとめ役が、レビューの判定を受け取ったときに書く**：持ち越す指摘を `open` で足す。引当先を後のマイルストーンにしたら、その節の作るものに残件の ID と作業を書き足す。節に無い作業は、その節の計画レビューでも実装でも読まれない
- **取りまとめ役が、作者に確かめられないまま決めたときに書く**：`judgment` で足す
- **取りまとめ役が、作者の判断を受け取ったときに書く**：行の結果の欄に判断と理由と反映先を書き、状態を `decided` にしてから、その行を読む担当に伝える。判断を受けても行が `open` のまま残る（判断で作業の形や引当先が決まり、作業はまだ残る）ときは、結果の欄は空のまま、内容の欄の末尾に「作者の判断（日付）：…」と書く。`judgment` の行の一部だけを作者が確かめたときも、行を `judgment` のまま残し、内容の欄の末尾に「作者の確認（日付）：…」と確かめた範囲を書く。`decided` にすると、確かめていない残りが作者への一覧から消える。`bin/check-open-items` は、片付いていない行の結果の欄を落とす。作業中の担当には、伝言ではなく、依頼に書いた受け口のファイルに行の ID と判断を書いて渡す。担当への伝言は担当が道具を呼ぶ切れ目にしか届かず、作業中の担当には届かないことがあるからである。担当は、commit の前と完了の報告の前に受け口のファイルを読み、読んだ ID を完了の報告に書く。取りまとめ役が担当の worktree の台帳を同時に書けないときは、担当が受け口のファイルの判断を台帳の行に書く。完了の報告に ID が無いまま担当が PR を出したら、取りまとめ役は PR の差分がその行の判断に合うかを確かめてから実装レビューに出す。受け口のファイルに台帳の行の状態（`open`・`blocked-user` など）に触れる判断を書くときは、台帳の行を読んでから、その状態をそのまま写す。担当は受け口を台帳より先に読むので、状態を誤って書くと、担当が台帳と食い違う前提で動く
- **実装者と取りまとめ役が、マイルストーンを終えるときに書く**：引当先がそのマイルストーンの行を、実装者が閉じるか、取りまとめ役が引当先を書き換える
- **取りまとめ役が、サイクル末の台帳の棚卸しで全部読み直す**

台帳に秘密の値（鍵・パスワード・設定の中身）を書かない。ファイル名と作業の内容だけを書く。

## 機械で守ること

この文書の規則のうち、機械で判定できるものは `bin/check-open-items` が守る。CI は、毎回の push で台帳の形と ID の参照を、PR では本文の参照も確かめる。

| 規則 | 検査 |
|---|---|
| ID は 01 から 1 ずつ増え、重複しない | 台帳の各行 |
| 残件の状態は 5 つのどれかで、引当先は `implementation-plan.md` に節があるマイルストーンの番号 | 台帳の各行 |
| `closed` は SHA を、`decided` は理由を持ち、片付いていない行は結果を持たない | 台帳の各行 |
| 改善の候補は「なぜ今か」を持ち、判定した行は判定の記録を持つ | 台帳の各行 |
| 証跡・文書・PR の本文に書いた `OI-NN`・`IB-NN` が台帳にある | 追跡しているファイルと PR の本文 |
| マイルストーンを終えるとき、引当先がそれの `open` と `blocked-user` が残っていない | `--due MNN`（共通の完了条件） |
| サイクル 10 からの実装レビューの証跡の「計画との違い」の項目が、`judgment` か `decided` の行の ID か「判断なし」を持つ | 証跡の各項目 |
| サイクル 10 からの計画レビューの証跡が、「1. 計画レビュー」の 5 つの観点の名前を持つ（マイルストーンごと・系統ごとかは見ない） | 証跡の全体 |
| サイクル 11 からの実装レビューの証跡のマイルストーンの節（「<マイルストーン> の残り（サイクル NN）」の節は、計画のその「残り」の段落の分）が、計画の完了条件の囲みの中の `git grep` を、数字の件数の注釈とともに持つ。番号の無い「残り」の見出しを落とす（最後の版で流し直したかは見ない） | 証跡のマイルストーンの節 |

ほかに、次の検査が回し方の記録と参照を守る。

| 規則 | 検査 |
|---|---|
| 台帳・証跡・`handoff.md` に書いた commit の SHA が、HEAD の祖先である | `bin/check-commit-refs`。CI は履歴をすべて取って流す |
| コメントと文書が「<文書>.md「<節>」」で指す節が、その文書の見出しにある | `spec/rubocop/section_references_spec.rb` |
| `bin/` の Ruby のスクリプトにも、コメントの規約の Cop が効く | `spec/rubocop/bin_scripts_spec.rb` |
| コードのコメントに台帳の ID（`OI-NN`・`IB-NN`）を書かない | Cop `FactoryOps/NoHistoryComment`（`guides/comments.md`「機械で止めるもの」） |
| CI のワークフローが流す `bin/` の検査が、`implementation-plan.md`「共通の完了条件」の一覧と `bin/ci` の工程にもある | `spec/platform/ci_checks_spec.rb` |

機械で判定できない規則（置き場の振り分け、観点ごとの判定、違和感の転記）は、サイクル末の振り返りで、証跡に成果物があるかどうかで確かめる。
