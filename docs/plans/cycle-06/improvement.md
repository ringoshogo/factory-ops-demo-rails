### IB-17 分岐の網羅率で拾えない確かめの抜け

- **いまの形**：分岐の網羅率の警告（`guides/testing.md`「分岐の網羅率の警告」）は、一度も通らなかった分岐だけを拾う。サイクル 06 では警告は 6 つのマイルストーンのどれも 0 件だった。抜けを捕まえているのは、実装者の壊して落ちる記録（`guides/dev-cycle.md`「テストから書く」）と、実装レビューの観点 4 である。振り返りで数えた 7 件と、それに数えていない M42 Codex R2 の 1 件は次のとおりで、どれも実装レビューが捕まえた

### IB-77 文字列の並べ替えの照合順序

- **いまの形**：DB の照合順序は、公式の `postgres` のイメージが initdb する既定（`en_US.utf8`）のまま（`compose.yaml`、CI のサービス、`deploy/postgres.yaml`）。`db/structure.sql` に `COLLATE` は無く、どこにも記録が無い。文字列の照合順序に依るのは 2 つの使い方である。並べ替えとキーセットの比較（伝票番号・品目コード・品目名・取引先の名前）は、並べる式と比べる式が同じ列の照合順序を使うので、1 つの DB の中ではページの境目で食い違わない。ロックの順は、取り込み（`Sales::Catalog.bulk_upsert`）と写しの書き込みが Ruby のバイトの順で並べ、作り直しは M46 の High の直し（`1c2a94b`）で `items.code COLLATE "C"` で並べて `FOR SHARE` を取る。ほかのロックの順は UUID で、照合順序に依らない
- **比べた形**：(a) コードの列（`items.code` と写しの `item_labels.code`）を、列の定義で Ruby の比べ方とそろう照合順序にする。候補は `"C"` と `pg_c_utf8` である。PostgreSQL 18 の文書「Collation Support」は、照合順序を列ごとに指定でき、`C` はバイトの値で並べるが ASCII の A〜Z しか文字として扱わず、`pg_c_utf8` はコードポイントの値で並べ、大文字と小文字の対応に Unicode の単純な対応を使うと書く。(b) DB の既定を変える（initdb の引数）。(c) ロックの順だけを決めて記録する（いまの形）
- **合い方**：(a) は、Ruby のバイトの順と DB の並びが、列の定義だけでそろう。作り直しの式の `COLLATE "C"` は要らなくなり、次にコードの順でロックする箇所を書く人が照合順序を知らなくても行き詰まらない。品目コードの一覧と在庫の `ITEM_CODE` の並びはバイトの順に変わるが、世界の品目コード（大文字と数字とハイフンだけ）の並びは変わらない見込み。品目コードの検索（`Keyword` の ILIKE）は列の照合順序で大文字と小文字を比べるので、`"C"` にすると ASCII 以外の文字を含むコードの大文字と小文字を区別するようになる。品目コードに形の検証は無く、取り込みの CSV で任意の文字が入りうるので、`pg_c_utf8` の方が検索の振る舞いを変えない見込み（マイルストーンの中で確かめる）。名前の列は触らないので、作者の確認を待つ OI-190 に依らない。(b) は名前の並びも変え（OI-190 に関わる）、既存のボリューム（手元の DB と公開の配置の PVC）は initdb をやり直さないと変わらない。(c) は費用が最も小さいが、M46 の High と同じ形を次の人が書けば、また実装レビューに頼る
- **移す費用**：(a) はマイグレーション 1 本（2 つの表の `code` の列の照合順序。品目の一意索引が作り直される）、`structure.sql`、作り直しの式とコメント、`data-model.md` と `adr/011` 決定 1 と `showcase.md` の文。大文字と小文字か記号の混ざるコードで、品目コードの並べ替えの spec の期待が変わりうる。ASCII 以外の文字を含むコードの検索の example を足す
- **効いたとする基準**：2 つの列の照合順序が決めたものであることを spec が確かめ、作り直しの式から `COLLATE "C"` を外しても `item_labels_rebuild_lock_spec.rb` の `B-1`・`a-1` の example が通り、列の照合順序を既定に戻すと落ちる
- **推奨**：採用（実装を伴う、小さい）。(a) をコードの列に限り（`"C"` と `pg_c_utf8` はマイルストーンの判断で決める）、名前の列は OI-190 の作者の確認を待って触らない。DB の既定の照合順序を前提にしていることも `data-model.md` に書く

### IB-110 `TEST_DATABASE` を渡した worktree の `bin/ci`

- **いまの形**：`Platform::Logging.events_log_path` は、`TEST_DATABASE` があれば `log/events.<DB の名前>.log`、無ければ `log/events.log` を返す。`spec/platform/logging_spec.rb` の別の DB の子のプロセスの example は、親のプロセスのファイルを `log/events.log` と固定で書いて読むので、`TEST_DATABASE` を渡した worktree では親が別のファイルに書き、`log/events.log` が無く `Errno::ENOENT` で落ちる（M45 の `bin/ci`）。同じファイルのほかの example は、すでに `events_log_path(Rails.root)` を読んでいる
- **比べた形**：(a) その example の親のファイルを `events_log_path(Rails.root)`（自分のプロセスのログ）にする。(b) ファイルが無ければ空として読む。(c) いまのまま、`bin/ci` だけは既定の DB で流す
- **合い方**：(a) は example の意味（別の DB の子のプロセスの行が、自分のプロセスのファイルに混ざらず、DB ごとのファイルに入る）を保ち、既定の DB でも別の DB でも同じに流れる。`events_log_path` が `TEST_DATABASE` を見ない形に壊すと落ちる（サイクル 05 の壊して落ちる記録と同じ壊し方）。(b) は別の DB の worktree で自分のファイルを見ないので、確かめの意味が弱い。(c) は並行の担当が既定の DB を取り合う
- **移す費用**：spec の 1 行とコメント
- **効いたとする基準**：`log/events.log` の無い worktree で `TEST_DATABASE=<別名>` を渡して `logging_spec.rb` と `bin/ci` が通り、`events_log_path` が `TEST_DATABASE` を見ない形に壊すと同じ example が落ちる
- **推奨**：採用（実装を伴う、小さい）。(a)。単独のマイルストーンにせず、IB-77 と同じマイルストーンに入れる

### IB-104 CI の `frontend` のジョブの `npm ls --all`

### IB-101 画面の書体の取り方

- **いまの形**：`frontend/app/layout.tsx` は `next/font/google` の IBM Plex Sans を使う。Next.js の文書（「Font Module」）は、Google Fonts の CSS と書体のファイルを組み立ての時に取ると書く。M42 のブランチの `e2e` 25 回のうち 1 回が `Can't resolve '@vercel/turbopack-next/internal/font/google/font'` で落ちた。この文言が取れなかったときの落ち方かは確かめていない（推定）。直近 100 回の失敗の run に、ほかにこの落ち方は無かった

### IB-93 の残り：PR で `images` を流す条件を外すか
