# サイクル 06 の終わりに作者が決めること

サイクル 06 のサイクル末の PR をマージする作者が、判断の要る点を 1 件ずつ決めるために読む。各項目は、何が問題か、流用元（`factory-ops-demo`）ではどうしているか、選べる形ごとの作るものと費用と見せ場、いまの形（既定）、を書いた。決まった答えは、取りまとめ役が台帳（`open-items.md`）の行の結果の欄に書き、行の ID で担当に渡す（`guides/dev-cycle.md`「残件の台帳」）。

答え方：項目ごとに「既定のまま」か、選ぶ形の記号を書く。全部既定でよければ「全部既定で」。

## 読む順

サイクル 07 の計画レビューの前に決めてほしい問い（1〜3）を先に、作者が手を動かすこと（4・5）を次に、確かめるだけの判断（6）を最後に置いた。1〜3 は、答えで作るものが変わるので、答えが来るまでその部分に着手しない。

## 1. 取り消した伝票の合計金額の欄に何を出すか（OI-192）

- **何が問題か**：作者は OI-179・OI-188 で、単価の決まっていない明細を含む受注（品番照合待ち）と、受注確定の前の発注は、合計金額を出さずに「照合待ち」「確定待ち」と出すと決めた。いまの画面は伝票の状況を見ずにこの規則を当てるので、照合待ちのまま取り消した受注と、受注確定の前に取り消した発注は、取消済のタブ・詳細・かんばんで合計の欄に「照合待ち」「確定待ち」と出る。取り消して終わった伝票に、まだ待っているような表示が出る。逸脱検査で Claude のレビュアーが見つけた（`conformance.md` の D1）
- **流用元では**：すべての明細が単価を持つ（品番照合が無い）ので、取り消した受注にも合計を出す。この問題は起きない
- **選べる形**

  | 形 | 取り消した伝票の合計の欄 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|---|
  | 既定 | いまのまま「照合待ち」「確定待ち」 | 無し | 無し | 無し。待ちの表示が終わった伝票に残る |
  | (a) | 「—」（空の理由を出さない） | 画面の合計の関数（`frontend/lib/format.ts` の `totalAmountText`）に状況を渡し、取消済なら「—」。単体と E2E の期待 | 小さい（画面だけ、M33 の残りに入れる） | 表示が業務の状態と食い違わない |
  | (b) | 「取消」 | (a) と同じで、文言だけが違う | 小さい | (a) と同じ |

  どの形でも、合計で並べるときは合計を持たない伝票を末尾に置いたままにする。明細が 1 つも無い伝票（入口からは作れない。IB-108）を同じ分岐で扱うかは、M33 の残りの計画レビューで決める
- **既定**：いまのまま
- **答えで変わること**：(a)・(b) なら M33 の残り（サイクル 07）に画面の直しを足す

## 2. 取引先の名前と品目の名前の並び順（OI-190）

- **何が問題か**：M45・M46 で、受注・発注・出荷依頼を取引先の名前で、在庫を品目の名前で、サーバーの SQL で並べられるようにした。並び順は DB の既定の照合順序（`en_US.utf8`）で、ひらがな・カタカナは五十音の順に並ぶが、漢字は文字の番号の順に並ぶ。流用元の画面と、漢字を含む名前の並びが変わる
- **流用元では**：画面がブラウザで最大 200 件を受け取り、`Intl.Collator("ja")`（ICU の日本語の照合）で並べる（流用元の `frontend/lib/sort.ts`）。ICU の日本語の照合は、かなを五十音で、よく使う漢字をその漢字の音読みの順で並べる。名前全体の読みの順ではない
- **確かめたこと**：手元の PostgreSQL 18 には ICU の日本語の照合順序（`ja-x-icu`）が入っていて、流用元と同じ並びを SQL で作れる。6 つの名前を並べた結果は次のとおりである

  | 照合順序 | 並び |
  |---|---|
  | いま（`en_US.utf8`） | A社 < あおば製作所 < かもめ工業 < 山田部品 < 東和商事 < 青嵐精機工業 |
  | `ja-x-icu`（流用元と同じ） | A社 < あおば製作所 < かもめ工業 < 山田部品 < 青嵐精機工業 < 東和商事 |

  `ja-x-icu` でも「山田部品」（音読みのサン）が「青嵐精機工業」（セイ）より前に来るので、名前の読み（やまだ）の順ではない
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し | 無し | サーバーで並べ、ページの境目で抜けも重なりも無いこと（M45・M46 で済み） |
  | (a) ICU の照合順序で、流用元と同じ並びにする | 名前の列（テナントの名前・品目の名前と写し）の照合順序を `ja-x-icu` にするマイグレーションと、並びを確かめる example。列に照合順序を持たせるので、並べる式とページの境目の比べ方に別々に書かなくてよい | 小さい〜中くらい（マイグレーション 1 本と spec。M49 の照合順序の直しと同じマイルストーンに入れられる） | 日本語の並べ替えを DB の照合順序で解いたこと。流用元がブラウザで 200 件に限って並べていたことを、件数の上限なしにサーバーで同じ並びにした |
  | (b) 読みの列を持ち、五十音の順にする | テナントと品目に読み（ふりがな）の列、登録と取り込みの入力、シード、並べる式 | 大きい（入力の画面と取り込みの列が変わる） | 名前の読みで並ぶ。流用元より正しい並び |

- **既定**：いまのまま
- **答えで変わること**：(a) なら、サイクル 07 の計画で M49 に名前の列を足すか、別のマイルストーンを起こす。(b) なら、新しいマイルストーンを起こす

## 3. 一覧の見出しで、複数の列を指定して並べる操作を作るか（OI-187）

- **何が問題か**：M47（サイクル 07）で、API が 2 つ目からの並べる列（`thenBy`）を受け取れるようにする。画面でそれを使うのは、ダッシュボードのかんばんの列の中の並び（希望納期の後に受注番号）だけにし、一覧の見出しは 1 つの列で並べる形のままにすると決めた（`judgment`）。複数の列で並べる仕組みは、画面からはほとんど見えない（IB-106）
- **流用元では**：一覧の見出しは 1 つの列で並べ、複数の列はかんばんの並びでだけ使う（流用元の `lib/kanban.ts` が、希望納期と受注番号の 2 つで並べる）。見出しで複数の列を選ぶ操作は無い
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | かんばんの並びだけ | 無し（M47 の計画どおり） | API の土台（列の組の keyset のページング）は作るが、画面では見えにくい |
  | (a) 見出しで 2 つ目からの列を足せる（Shift を押して見出しを押すと、その列を後ろに足す） | URL の `sort`・`dir` を列の並びに広げる関数、見出しの操作、並びの表示、単体と E2E | 中くらい（画面だけ。M47 か M33 の残りに入れる） | 値の同じ行が続く列（状況・取引先）で並べたときに、2 つ目の列で並びが決まり、ページの境目で抜けも重なりも無いことを画面で見せられる |

- **既定**：かんばんの並びだけ
- **答えで変わること**：(a) なら、サイクル 07 の計画レビューで M47 の画面の作るものに足す

## 4. 公開の配置の実機の手順（M41 の残り）

- **何をするか**：`deploy/README.md`「作者の手順」1〜6 を Raspberry Pi で流し、測ったメモリ、取り込みの間の Pod の再起動の回数（`RESTARTS`）、公開の URL で確かめたこと、流用元のデモが動き続けることを、PR か台帳に書く。結果が書かれるまで M41 は閉じず、公開しない
- **このサイクルで変えたこと**：取りまとめ役が確かめた Pi 4（スワップ無し、SD カード）に合わせ、どのプローブも時間切れを 5 秒にし、PostgreSQL の確かめ（`pg_isready`）に 4 秒の待ちを渡した（OI-182）。GHCR には、main の commit の SHA のタグで arm64 のイメージが置かれている（M42）。適用するときは、同じ SHA の `api` と `frontend` の 2 つのイメージがあることを確かめる（`deploy/README.md`「2. 適用」）
- **見るところ**：手順 4 で、5 万行の取り込みを流す間に `RESTARTS` が増えないか。増えたら、取りまとめ役が時間切れか limits を直す

## 5. M33 の画面の細かい指摘（OI-177）

作者が画面を動かした後に出すとした指摘である。出したら、取りまとめ役が指摘ごとに台帳に写し、画面だけで済むか API に及ぶかを書いて、M33 の残り（サイクル 07）で直す。

## 6. 確かめるだけの判断（judgment）

取りまとめ役が、作者に確かめられないまま決めたことである。どれも既定で作ってあり、違う形を求めるときだけ答える。内容と理由は台帳の各行にある。

| ID | 決めたこと | 違う形を求めるなら |
|---|---|---|
| OI-182 | 公開の配置のプローブの時間切れを 5 秒にし、`pg_isready` に 4 秒の待ちを渡す。requests と limits は見積もりのまま | 実機の手順 4 の結果で直す |
| OI-183 | 公開の配置の PostgreSQL のデータを、Raspberry Pi の SD カードの上に置く | USB の SSD に移す |
| OI-184 | CI で GHCR にイメージを置く `publish` が、ほかのジョブの skip を最初のステップで見て止まる（GitHub のジョブの段の条件が、`needs` の先で skip されたジョブも数えたため） | M48 で、条件を簡単にできるかを確かめる |
| OI-186 | 作者が並べ替えを求めた値（取引先の名前・合計・状況・在庫の品目）のほかの列（品目の一覧の単位・単価・安全在庫、出荷依頼の受注番号・出荷予定日）は、並べ替えの列に足さない。流用元はこれらでも並べる | 列ごとに、M39（同じパッケージの列）か M45（式・副問い合わせ）の形で足す。1 列あたり、並べ替えの値・式・行列の行・見出しを足す小さい変更 |
| OI-188 | 発注の合計金額にも、受注と同じ規則（単価の無い明細を含めば合計を出さず「確定待ち」）を当て、発注一覧に「発注合計」の列を足した | 発注だけ一部の合計を出す |
| OI-191 | 取引先の名前で並べるとき、一覧に相手の表を結合せず、行ごとに名前を 1 つ引く形にした。結ぶ条件を誤ったときに、行と件数が黙って増えずに SQL のエラーになる | 無し（作り方の判断で、画面の振る舞いは変わらない） |

サイクル 05 以前から確認を待っている `judgment` は、`cycle-05/inventory.md`「作者への一覧」の表と同じである。
