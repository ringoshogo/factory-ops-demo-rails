## 1. 出荷依頼の受注番号の写しを残すか（OI-226、M54 の残り）

- **何が問題か**：出荷依頼の一覧は、受注番号で並べられる（作者の OI-186）。並べるために、受注番号を「出荷可能」のイベントで運び、出荷依頼の表に写している（M50、ADR 011）。写した理由は、写しを作った時点で出荷が受注に依存しておらず、受注の表を結べなかったことだった。M54 で、出荷は受注の取消と審査を同期で読むようになり、受注に依存した。写した理由は成り立たなくなったが、ADR 011 は写しを持ち続ける理由を書いておらず、コードのコメントは「写しを作った時点では依存しなかった」と経緯で理由を書いている（サイクル 09 の逸脱検査の D6・D7）
- **流用元では**：写さない。出荷指示の一覧は、受注の表を結んで受注番号を引く（`backend/internal/store/shipping_instructions.go` 303〜312 行）。流用元は 1 つのテナントの中の 1 つのデータベースで、受注と出荷を分けていない
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | (a) 写しを残す | ADR 011 に、いま写しを持つ理由（作り直しのタスクと一致の spec がすでにあり、一覧の並べ替えが出荷の表だけで済む）を書き、3 つのコメント（`shipment_requests.rb`・`read_models.rake`・E2E の spec）をいまの契約の短い文にする | 文書 1 つとコメント 3 か所。spec は変えない（小さい） | 見せどころのテーマ 3 の「出荷依頼の受注番号の写し」の行はそのまま載る |
  | (b) 受注から引く | 出荷依頼の表の受注番号の列を消し、出荷の一覧が受注の公開 API の副問い合わせを結んで並べる。「出荷可能」の受注番号の項目は、前に登録したジョブを読めるよう残すかを決める。作り直しのタスクの受注番号の分と、一致の spec の受注番号の列を消し、ADR 011 を裏返す | `sales_order_no` が出るファイルは `docs/plans/` を除いて 15（マイグレーション 1・`structure.sql`・イベントの型・受け手・出荷の公開 API・受注の発行元・spec 6・設計文書 2・計画 1）で、列を消すマイグレーションを 1 つ足す。マイルストーン 1 つ（中くらい） | テーマ 3 の写しの行が 1 つ減り、「依存の向きが変わったら写しをやめる」という設計の見直しの例になる |

- **既定**：(a)
- **おすすめ**：(a)。写しは一致の spec と作り直しのタスクで守られていて、壊れていない。(b) は見せ場になるが、マイルストーン 1 つ分の費用で、画面の振る舞いは変わらない
- **答えで変わること**：(a) なら、サイクル 10 の M54 の残りで ADR 011 とコメントを直す。(b) なら、サイクル 10 かそれ以降に、写しを替えるマイルストーンを起こし、計画レビューに通す

## 2. 発注の進みの「請求書の受領」の日付（OI-228、M53 の残り）

- **何が問題か**：M53 で足した発注の詳細の進みの「請求書の受領」は、受注側が請求書を発行した日（受領請求書の `issued_on`）で並ぶ。発注側が写しを受け取った日ではない。計画の表のとおりだが、名前（受領）と日付の意味（発行）がずれる（M53 の実装レビュー、Claude の違和感。IB-146）
- **流用元では**：無い。流用元には請求書も発注も無い（`backend`・`frontend` を `invoice`・`billing`・`請求` で検索して 0 件）
- **選べる形**
  - (a) いまのまま：作るものは無い
  - (b) 名前を「請求書の発行」に変える：GraphQL の enum の説明（`app/graphql/types/purchase_order_timeline_kind_type.rb`）、画面の名前（`frontend/lib/format.ts`）、スキーマの書き出しと `graphql-schema.md`「発注側の視点」の表。spec は名前を引く example があれば直す（小さい）
  - (c) 受け取った日で並べる：進みの組み立て（`packs/purchasing/app/models/purchasing/purchase_order_timeline.rb`）が、受領請求書の受け手が写しを書いた時刻を読み、日付だけの出来事から時刻のある出来事に変わる。`graphql-schema.md` の表、進みの spec の期待、画面の時刻の表示を直す（小さい〜中くらい）
- **見せ場**：どの形も見せどころのテーマ 4 の「状況の式と同じ行を読んで組み立てる進み」の載り方は変わらない。(c) は「受注側から届く出来事は受注側の発生の時刻で並べる」規則（M53）の例外になり、規則と食い違う
- **既定**：(a)
- **おすすめ**：(a)。進みのほかの受注側の出来事も、受注側で起きた時刻で並べる規則で、請求書だけ受け取った日にすると規則が割れる。名前のずれが気になるなら (b)

### 6. 引当の経路では、在庫が「自社の品目か」を確かめない（OI-219 の一部）

- **何が問題か**：作者は OI-216 で、「在庫は自社の品目にだけできる」の保証を在庫に移すと決めた。M55 で、在庫の調整と在庫数の設定は、自社の品目の写しが無い品目を「見つからない」で拒むようになった（画面の在庫の調整と在庫の CSV の取り込みは、前から同じ品目を拒んでいたので、外から見える結果は変わらない）。一方、受注の引当が在庫の行を作る経路は範囲外にした。引当に渡る品目は、受注側が照合を済ませた受注明細の品目で、作者の判断は調整と在庫数の設定を名指ししたからである（計画の M55「範囲外」）。そのため「在庫は自社の品目にだけできる」を在庫が自分で守るのは、3 つの経路のうち 2 つである
- **流用元では**：在庫の行は品目と同じトランザクションで作る（`backend/internal/store/items.go` 103〜104 行）。在庫の調整は在庫の行が無ければ「見つからない」を返す（`backend/internal/store/stocks.go` 126〜131 行）。引当が在庫の行を作る経路が無いので、穴が無い
- **選べる形**：既定（引当は範囲外）。(a) 引当でも写しの有無を確かめ、無ければ失敗にする：在庫の引当（`packs/inventory/app/public/inventory/allocation.rb`）、受注の側で引当の失敗を受ける処理、ADR 011 の文を直し、乱数の品目で引当を流す spec に写しを置く。写しを置いた spec は M55 で 5 ファイル・約 25 個あり、引当の spec で同じ手当てが要る数は確かめていない（中くらい）
- **見せ場**：既定は、見せどころのテーマ 3 の「在庫の品目の写し」の箇条に載る形のまま。(a) は「在庫は自社の品目にだけできる」が在庫の公開 API のすべての書き込みで成り立つと言えるようになる
- **おすすめ**：既定のまま。引当の品目は受注側が照合済みの明細からしか来ず、穴に届く入口が外に無い。作者が「存在の保証は在庫が持つ」を全経路の意味で決めたのなら (a) を選ぶ

### 8. 発注の詳細の「進み」の色・見出し・並び（OI-220）

- **何が問題か**：M53 で、発注の詳細に、発注がいつ何を経て今の状況になったかを時刻の順に並べる「進み」を足した（作者の OI-210）。計画が書き切らなかった 3 つを実装者が決めた
  1. 色：「取消の承認」「取消の却下」「受注側の取消」の 3 つの名前を灰色（控えめの色）で、ほかの出来事は通常の色で出す。計画は「合計の欄の『取消』と同じ控えめの色」としたが、合計の欄の「取消」は色を持たないので、取り消した伝票の明細の文言（作者の OI-204）と同じ灰色にした。「取消依頼」は発注側が頼んだだけで、まだ取り消していないので通常の色にした
  2. 見出し：「進み」とし、発注の上の欄（取引先・発注日・希望納期）の直後、明細の上に置いた
  3. 同じ時刻の並び：取消の承認と却下が同じ時刻のときは、承認を先に並べる。却下の後の再依頼が承認されたときにしか同じ時刻にならず、実際にはほぼ起きない
