## 調べたテーマ

### IB-60 RLS の UPDATE のポリシーに隠れる所有の条件

- **いまの形**：共有の文脈「RLS の SELECT を開く」は、テナントの表ごとに、設定 `app.matrix_cross_read` が `on` のときだけ全行を読ませる SELECT のポリシーを足す（`spec/support/matrix_cross_read.rb`）。`SELECT ... FOR UPDATE` と UPDATE は、SELECT のポリシーに加えて UPDATE のポリシーの `USING` を満たす行しか対象にしないので、所有の条件を外しても他社の行は RLS の UPDATE のポリシー（`owner_write`）に隠れ、単体の結果が変わらない（`guides/testing.md`「行列テストとの分担」の最後の段落）
- **比べた形**：
  - (a) 同じ補助で、同じ設定のときだけ他社の行を UPDATE の対象に入れる UPDATE のポリシーを足す。`USING` は設定が `on`、`WITH CHECK` は `false` にする。PostgreSQL は許可のポリシーの `WITH CHECK` を OR でつなぐので、書いた後の行の確かめは、いまの `owner_write` の `WITH CHECK`（自社の行）だけが効く。所有の条件を外した公開 API は、他社の行を引いて書こうとし、`WITH CHECK` の違反で例外になる。所有の条件があれば他社の行を引かない。ただし、設定が `on` の間は、他社の行を自社の名義に書き換える UPDATE と `INSERT ... ON CONFLICT DO UPDATE` が通り、他社の行に `FOR UPDATE` のロックが取れる（裁定で Codex が指摘した）
  - (b) M31 の `files_purge_owner_spec.rb` の形を広げる。公開 API が流した SQL を `sql.active_record` で拾い、所有ロールの接続で流し直して、自社の行だけを選ぶことを確かめる。公開 API ごとに、拾う文と流し直し方（`FOR UPDATE` と UPDATE を SELECT に読み替える）を書くことになる
  - (c) 構文木で、操作者のいない入口の公開 API が `Current.tenant_id` を条件に使うかを照らす。条件の書き方（`own_users` のような補助、関連をたどる絞り込み）が多く、外れが多い
- **計測**：(a) を試作した。補助に UPDATE のポリシーを足し、`Inventory::Stocks.set_safety_stock` から scope を外し、共有の文脈で `cross_read!` を呼んでから他社の品目を渡す example を足して流した。足す前は、scope を外しても `NOT_FOUND` が返って通った（1 example, 0 failures）。足した後は `PG::InsufficientPrivilege: new row violates row-level security policy for table "stocks"` で落ちた。scope を戻すと、`stocks_spec.rb` は 9 examples, 0 failures。UPDATE のポリシーを足した補助で、入口の行列と行列の世界とテナントの強制（`spec/matrix spec/db/tenant_enforcement_spec.rb`）を流すと 1319 examples, 0 failures で、時間は変わらなかった（19 秒）。試作は戻した
- **合い方**：(a) は M37・M32 で作った補助と共有の文脈をそのまま使い、公開 API ごとの example は「`cross_read!` を呼んでから他社の対象を渡す」の 1 つで済む。ポリシーの SQL は `spec/support` にだけ置き、`structure.sql` と本番には載らない（M37 と同じ）。設定が `on` の間に通る所有の移し替えは、example の対照（他社の行が変わらないこと）で捕まえる必要がある
- **残る穴**：冪等キーにグローバルな一意索引がある受け手（受注の連結・審査・出荷依頼・入荷）と、自社の品目の ID で引く `PartMatching.prices` は、他社に同じキーの行を作れないので、(a) でも確かめられない。所有の条件が無くても他社の行に当たらない形で、条件は二重の守りである。行ロックだけを取って書かない箇所（他社の行のロックが黙って通る）と DELETE（DELETE のポリシーは変えない）も届かない（裁定で Claude が指摘した）。IB-59 も外に残る
- **移す費用**：補助に UPDATE のポリシーを足す数行と、足している間のポリシーの形の確かめ、確かめる箇所ごとの example。`tenant_enforcement_spec.rb` は、ポリシーの名前の集合を確かめるので、新しい名前の消し忘れを変更なしに落とす。`testing.md` の段落を書き直す
- **効いたとする基準**：確かめる箇所（操作者のいない入口の公開 API とイベントの受け手のうち UPDATE・`update_all`・`lock` で引く箇所を、正本とコードから集める）から 1 つずつ所有の条件を外すと、それぞれの単体の example が落ちる。外さない状態で全件が 0 failures。ポリシーが残らない（`tenant_enforcement_spec.rb`）
- **推奨**：採用（実装を伴う、小さい）。(a) にする

### IB-61・IB-62 シードの `DemoWorld` の頑丈さ

- **いまの形**：`DemoWorld::Jobs` はジョブを claim せずにその場で流し、`DemoWorld` の冪等は受注側のテナントの有無だけで判定する。`README.md`「開発環境」は、シードの間は `bin/jobs` を止め、途中で失敗したら `db:reset` から流し直すと書く
- **M33 との関わり**：M33 の計画は、E2E の世界を `bin/rails e2e:prepare` が DB を作り直してから作り、その後で Playwright の `webServer` が `bin/jobs` を起こす（`implementation-plan.md`「M33 フロントエンド」の作るもの 4）。世界を作る間にワーカーが動かず、DB を毎回作り直すなら、どちらの穴にも当たらない。開発の DB では、`bin/jobs` を起こしたまま手でシードを流すと IB-61 に当たり（受け手は冪等なので壊れない）、ワーカーを止めていても途中で失敗すると IB-62 に当たる（`README.md`「開発環境」が `db:reset` からの流し直しを決めている）
- **推奨**：見送り。調べ直す条件：E2E か開発の環境で、`DemoWorld` とワーカーが同じジョブを流した、または途中で失敗した世界を 2 回目が黙って返したことによる失敗が 1 件出たとき
