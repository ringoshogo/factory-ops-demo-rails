# サイクル 11 の終わりに作者が決めること

サイクル 11 のサイクル末の PR をマージする作者が、判断の要る点を 1 件ずつ決めるために読む。取りまとめ役が 1 件ずつ問い、決まった答えを台帳（`open-items.md`）の行に書いて、行の ID で担当に渡す（`guides/dev-cycle.md`「残件の台帳」）。

各項目には、何が問題か、流用元（`factory-ops-demo`）ではどうしているか、選べる形ごとの作るものと費用、見せ場になるか、既定とおすすめを書いた。流用元の作りは、`factory-ops-demo`（commit 958de71）の実物のファイルと行を開いて確かめた。費用は、このブランチのコードと計画と証跡を読み、変えるファイルを数えて確かめた。流して確かめていないものは、そう書いた。

答え方：項目ごとに「既定のまま」か、選ぶ形の記号を書く。全部既定でよければ「全部既定で」。

## 3. 乱順が既定であることを確かめる形（OI-239）

- **何が問題か**：M58 で、spec を乱順で流す設定（`spec/spec_helper.rb` の `config.order = :random` と `Kernel.srand config.seed`）を、生成器の注釈の外に出した。設定を誰かが消したときに落ちる守りが要る。計画は「名前と置き場は実装で決める」としていたので、計画レビューで形を決めた。親のプロセスの設定（`RSpec.configuration`）を読む形は、CI と再現の手順が `--seed` を渡して流すので、設定を消しても乱順のまま通る（rspec-core 3.13.6 は、コマンドラインの `--seed` と `--order` を設定より優先する）。そこで、`spec/platform/spec_order_spec.rb` が子のプロセスで 10 個の example（`spec/fixtures/spec_order/examples.rb`）を順も seed も渡さずに流し、(a) 出力に seed がある、(b) その seed で同じ並びになる、(c) 同じ seed で `Kernel.rand` が同じになる、の 3 つを確かめる。子には `--options .rspec` を渡して手元の個人の設定を読ませず、親の `SPEC_OPTS`・`COVERAGE`・`FULL_SUITE` を渡さない
- **流用元では**：乱順で流していない。バックエンドは `go test -p 1 ./...`（`.github/workflows/ci.yml` 53 行）で、`-shuffle` を渡さないので、テストは定義の順で流れる。画面の単体テストの `frontend/vitest.config.ts` も並びを混ぜる設定を持たない。順を守る検査は無い
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し | 無し。1 回の子のプロセスは約 0.5 秒（計画レビューで測った）で、2 つの example が合わせて 6 回流す | 見せどころのテーマ 9 に、乱順と、設定を外すと落ちる守りが載っている（サイクル 11 の知見の収穫） |
  | (a) 親のプロセスの設定を読む形にする | `spec_order_spec.rb` を `RSpec.configuration.ordering_registry` などを読む 1 つの example にし、流す対象のファイルを消す | spec 2 つ（小さい）。設定を消しても、`--seed` を渡す流れでは落ちなくなり、守りが弱くなる | 載り方は変わらないが、「設定を外すと落ちる」とは言えなくなる |
  | (b) 守りを置かない | `spec_order_spec.rb` と流す対象を消し、`guides/testing.md` の参照を直す | spec 2 つと文書 1 つ（小さい） | 乱順は載るが、守りは載らない |

- **既定**：いまの形のまま
- **おすすめ**：既定のまま。(a) は費用が同じくらいで、守りだけが弱くなる

## 4. 移行の spec の後始末を確かめる形（OI-240）

- **何が問題か**：M58 で、`Sales::Item` の `unit_price` の無視を外すために、移行の spec（`packs/sales/spec/public/sales/item_prices_backfill_spec.rb`）が消した列を足し直した後の後始末で、モデルの列の読み込みを戻す形にした（`guides/config.md` の規則 3）。後始末が読み込みを戻したかを確かめる形を、計画レビューで決めた。内側のグループを流す補助（`run_inner_group`）は、作る内側のグループが外側の `after` を受け継がないので、後始末を写して写しを確かめるだけになる。そこで、`after` の中身を 1 つのメソッドに出し、書き直した example がそのメソッドを呼んで、モデルの列から `unit_price` が消え、品目を作れることを確かめる形にした。あわせて、無視を外すとモデルと食い違うマイグレーションのコメント 1 行（「Sales::Item は ignored_columns でこの列を読み書きしない」）を消した
- **流用元では**：列を消したことが無い。マイグレーションは `backend/migrations/000001_init.up.sql` と `000001_init.down.sql` の 1 組だけで、移行の前の形を作るテストも無い。DB の形を変えるテストは、テストごとに空の DB を作り直して消す（`backend/main_test.go` の `createFreshDB`、319〜335 行）ので、後始末でモデルの情報を戻す必要が無い
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し | 無し | 見せどころのテーマ 10 に、spec が足し直した列の後始末でモデルの列の読み込みを戻すことが載っている |
  | (a) 内側のグループを流す補助で確かめる | example を `run_inner_group` で内側の example を流す形に書き直し、後始末を内側に写す | spec 1 つ（小さい）。写しを確かめるだけになり、`after` から後始末を呼ばなくなっても落ちない | 変わらない |
  | (b) 流用元のように、移行の spec だけ別の空の DB で流す | 一時の DB を作って消す補助と、移行の spec の書き直し | spec と補助で中くらい。一時の DB の名前の規則と後始末（`guides/config.md`）に足す | 「テストが共有の DB の形を変えない」と言えるが、遅くなる |

- **おすすめ**：既定のまま

## 5. 列を消した後も無視を残すと決めた OI-106 を替えたこと（OI-241・OI-106）

- **何が問題か**：M27 で `items.unit_price` を消したとき、`Sales::Item` の `ignored_columns` を列を消した後も残すと決めた（OI-106、`judgment`）。理由は、移行の spec が列を足し直す間にモデルが列を読み、列を消した後の INSERT が落ちることだった。M58 で、後始末でモデルの列の読み込みを戻す形にして、無視を外した（上の 4）。OI-106 は作者が確かめていない判断なので、`decided` にせず `judgment` のまま残し、内容の欄の末尾に M58 で外したことを書いた（OI-241）。作者に確かめてほしいのは、OI-106 の判断（無視を残す）を M58 の形（後始末で戻して無視を外す）に替えてよいかである。替えると、列を消した後の規則（`guides/config.md` の 3 つの規則）から例外が無くなる
- **流用元では**：列を消したことが無い（上の 4）。ORM の列の情報を持ち続ける仕組みも無く、Go の SQL は列を名指しして書く
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し。作者が確かめたら、OI-106・OI-241 を `decided` にする | 無し | 見せどころのテーマ 10 の列を消す変更の規則に、例外が無い |
  | (a) OI-106 のとおり無視を残す形に戻す | `item.rb` に `ignored_columns` とコメントを戻し、規則 3 を「足し直すあいだは外さない」に戻す。後始末の読み込みの戻しは残してよい | モデル 1 つ、`config.md` の規則 3 と見せどころのテーマ 10 の文、マイグレーションのコメント（小さい） | 規則 3 が例外として戻る |

- **既定**：いまの形のまま
- **おすすめ**：既定のまま
