## 調べたテーマ

### 1. IB-158 後始末で列の読み込みを戻したかを機械で捕まえるか

- **いまの形**：規則 3（spec が消した列を足し直すときは、後始末でモデルの列の読み込みを戻す）を守るのは、移行の spec の後始末を確かめる example だけである。消した列を足し直す spec は、`git grep -n -i 'ADD COLUMN\|add_column' -- '*_spec.rb'` で `packs/sales/spec/public/sales/item_prices_backfill_spec.rb` の 1 つだけである
- **比べた形**：(a) spec のファイルを読むガード：`ADD COLUMN` を含む spec が `reset_column_information` も呼ぶことを確かめる（spec 1 つ、約 15 行。文字列で見るので、呼ぶ場所が後始末かは見ない）。(b) 全件の終わりの守り：`after(:suite)` で、列の情報を読み込んだモデルの列が DB の列の部分集合であることを確かめる（`spec/rails_helper.rb` に約 10 行。列の読み込みを戻し忘れた spec が全件の中にあれば落ちるが、どの spec かは名指ししない）。(c) いまのまま
- **合い方**：当てはまる spec が 1 つで、その spec の後始末は example が確かめる。戻し忘れの壊れは、同じプロセスの後の INSERT が `PG::UndefinedColumn` で落ちる形で必ず表に出て、乱順（IB-157）でどの順でも当たりうるので、定義の順に隠れていた M58 の前より見つかりやすい。(a) と (b) は、2 つ目の spec が出るまで守る相手が無い
- **推奨**：`見送り`。調べ直す条件：消した列をテストの DB に足し直す spec が 2 つ目になったとき

### 2. IB-159 `Kernel.srand config.seed` を残すか

- **いまの形**：M58 で `config.order = :random` と一緒に注釈から出し、乱順のガードの (c) が守る。spec と factory の乱数の使い手を `git grep -n -E 'rand\(|Kernel\.rand|\.sample\b|\.shuffle\b|Random\.(rand|new)|Faker'` で数えると、ガードの流す対象のほかは `SecureRandom` の 1 か所だけで、`SecureRandom` は seed に依らない。Gemfile に Faker は無い。factory の値は `sequence` で、乱数を使わない
- **比べた形**：(a) 残す（いまのまま）。(b) 外す：`spec/spec_helper.rb` の 2 行とコメント、ガードの (c) と流す対象の値を書く example、`spec_order_spec.rb` の名前とコメント、計画と台帳の参照を直す（spec 2 つと設定 1 つ）
- **合い方**：(a) の費用は 1 行の実行で、効き目は今のコードでは無いが、乱数に頼る spec を足した人が seed で再現できる。(b) は守りを 1 つ減らすだけで、得るものが無い
- **推奨**：`見送り`（いまのまま残す）。調べ直す条件：`Kernel.srand` が原因の失敗が出たとき

### 3. IB-160 子のプロセスが packs-rails の統合を読むことを、前提として書くか守るか

- **いまの形**：`.rspec` は `--require spec_helper` と `--require packs/rails/rspec` を持ち、子は `--options .rspec` で両方を読む。packs-rails 0.1.0 の `lib/packs/rails/rspec.rb` は `packs-rails`（`packs`・`active_support`・`rails/application`・`sorbet-runtime`）を読み、`Packs::Rails::Integrations::RSpec.new` で流すファイルの一覧を書き換えるだけで、アプリ（`config/application.rb`）も DB も読まない。子に渡すのは 1 つのファイルなので、一覧は書き換わらない（パックのディレクトリに当たらない）
- **比べた形**：(a) 前提を書く：計画は終えた節なので書き換えず、流す対象のコメントに「`.rspec` の packs-rails の統合も読むが、統合は流すファイルの一覧を書き換えるだけで、アプリも DB も読まない」を 1 文足す（コメント 1 行）。(b) 守る：流す対象に、アプリを読んでいないこと（`defined?(ActiveRecord::Base)` が偽など）を確かめる example を足す。対象の example の数（10 個）と並びの期待が変わる（spec 2 つ）。(c) いまのまま
- **合い方**：害が出るのは、packs-rails が統合でアプリを読む形に変わったときだけで、そのときは子が DB に触れて遅くなるか、`rails_helper` の判定を通らずに子が落ちる。後者は (a)〜(c) のどれでも乱順のガードが落ちて表に出る。packs-rails の更新は Dependabot の PR で来るので、更新の PR の CI で見つかる
- **推奨**：`見送り`。調べ直す条件：packs-rails の版を上げたとき、または子のプロセスが DB に触れたか遅くなったとき

### 4. IB-161 列を消す規則 1 の前例を、いまの木で両側が読める形にするか

- **いまの形**：`guides/config.md` の規則 1 は、列を消す変更の前例として 2 つのマイグレーションを挙げる。両方のモデルから規則 2 のとおり無視を外したので、いまの木では前例の片側（モデルの `ignored_columns`）が見えない。`20261016100000` のマイグレーションのコメント「モデルの ignored_columns に列を入れた版と一緒に置く」も、置いた時の事実である
- **比べた形**：(a) 前例を、無視を入れた commit で指す（規則の文に commit の SHA を 2 つ書く。`guides/` の SHA は `bin/check-commit-refs` の対象外で、載せ直しで消えても気づかない）。(b) 前例の名指しを消し、規則の文だけにする（`config.md` の 1 文）。(c) いまのまま
- **合い方**：規則 1 の文そのものが、無視を入れることと同じ変更で列を消すことの両方を書いていて、前例は「同じ変更にまとめた例がある」ことを示すだけである。いまの木で前例の片側が見えなくても、規則を読み違える経路は無い。次に列を消す変更が出ると、その変更が外すまでの間は両側の見える前例になる
- **推奨**：`見送り`。調べ直す条件：前例を読んで規則を読み違えた指摘が出たとき
