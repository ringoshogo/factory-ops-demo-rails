# サイクル 11 の計画レビュー：M58 と、M33・M41 の残り

この文書は、`implementation-plan.md` の M58 を 2 系統の独立したレビュー（Claude と Codex）にかけ、指摘を計画に反映した記録である。M58 から着手する担当者と、計画をレビューする人が読む。担当者は、計画の節が「なぜこう書いてあるか」をここで引ける。

サイクル 11 に入るのは、サイクル 10 の改善の探索で起こした M58（IB-157・IB-154・IB-156）と、作者を待つ M33 の残り（OI-177）と M41 の残り（OI-196）である。サイクル 10 の作者の答え（2026-10-20）は、`plans/cycle-10/author-decisions.md` の 3〜10 が全部既定のままで、答えで作るものは無い。

レビューは `973ad9c` を読んだ。この版は、計画レビューの担当が M58 の節の「実装で決める」「計画レビューで決める」とした形を決め、全件を乱順で流した結果を書いた後の版である（下の「M58 で決めたこと」）。依頼には読む版の commit を書き、`git show 973ad9c:<パス>` で読ませた。全体の判定は、Claude が Conditional Go（High 1 件）、Codex が Go だった。名指しの High を直したので、`guides/dev-cycle.md`「判定の形」の Conditional Go の扱いどおり、読み直しには出していない。Claude のサブエージェントは最終報告を返さずに終わり、依頼に書かせた結果のファイルから読んだ。2 系統とも DB を使う spec は流さず、完了条件の `git grep` と、DB を使わない rspec の小さな実行（試しのファイルの `--dry-run`、`RSpec::Core::Ordering::Random` のメモリの上の並べ替え）を行った。

読む順は、マイルストーンの分け方 → 乱順で流した結果 → M58 で決めたこと → 判定 → 指摘ごとの対応 → 違和感 → 作者に渡すもの → 計画の数の空き、である。指摘の出典は `Claude R1`・`Codex R1` の形で示す。

## 乱順で流した結果

```sh
TEST_DATABASE=factory_ops_c11plan_test RAILS_ENV=test bin/rails db:test:prepare
TEST_DATABASE=factory_ops_c11plan_test bundle exec rspec --seed <seed>
```

| 202 | 3198 examples, 0 failures | 3 分 22.5 秒 |

落ちた spec は無い。サイクル 10 の改善の探索が `audit_examples_spec.rb` を直した後に流した 11・22・33 と合わせて 8 つの seed で落ちていないので、M58 の費用に直す spec を見込まない。完了条件に全件を 3 つの seed で流す行を足し、合わせて約 10 分かかることを「判断」に書いた。

## M58 で決めたこと

### 作るもの 1：乱順が既定であることを子のプロセスで確かめる（OI-239）

計画は「`RSpec.configuration` の順の既定が乱順であること。名前と置き場は実装で決める」としていた。親のプロセスの設定を読む形は、完了条件と再現の手順が `--seed` を渡して流すと、設定を注釈に戻しても乱順のまま通る。rspec-core 3.13.6 は `--seed`・`--order` を設定ファイルより優先する（`configuration_options.rb` の `force?`、`ordering.rb` の `ConfigurationManager#force`）からである。そこで、子のプロセスで何も渡さずに流す形にした。

計画レビューの担当が、試しのファイルで次を確かめた。いまの版の `--dry-run --format json` は `seed` を出さず（`nil`）、`--seed 7` で整数の `seed` を出し、同じ seed で 2 回流すと並びが同じだった。`json_formatter.rb` は乱順で並べたときだけ `seed` を出す（2 系統とも原文で確かめた）。1 回の子のプロセスは約 0.5 秒だった。

### 作るもの 2：後始末をメソッドに出して確かめる（OI-240）

改善の探索は、後始末の後の列を同じ example の中で見られないので、内側のグループを流す補助（`run_inner_group`）で確かめる形を計画レビューで決めるとした。補助は `RSpec.describe` で新しい最上位のグループを作り、外側の `after` を受け継がない（`spec/platform/tenant_example_spec.rb`）。内側に後始末を写すと、写しを確かめるだけになる。そこで、`after` の中身を 1 つのメソッドに出し、書き直した example がそのメソッドを呼んで列の情報を確かめる形にした。メソッドを `after` から呼ばなくなる壊れは、後に流れる example の `before` とファイルの終わりの `after(:context)` が捕まえる。2 系統とも、この形を妥当とした。

あわせて、`ignored_columns` を外すとモデルと食い違うマイグレーションのコメント（`db/migrate/20261012200100_remove_unit_price_from_items.rb` の「Sales::Item は ignored_columns でこの列を読み書きしない」）を消すことと、前の形を数える `git grep` を完了条件の囲みに足した。列を消した後も無視を残すと決めた OI-106 は、作者が確かめていない判断なので、`judgment` のまま M58 で外したことを書く（OI-241）。

## 違和感

Codex は 2 つ（改善の探索の案と違う形を採ったこと、M33・M41 の残りに食い違いが無いこと）で、どちらも記録の観察で、移すものは無い。Claude は 5 つだった。

- 1（子のプロセスは `~/.rspec` と `.rspec-local` も読む）：子を `--options .rspec` で流すと書いた。`--options` を渡すと、rspec はそのファイルだけを読む（`configuration_options.rb` の `file_options`）。直したので改善の候補に移さない
- 2（(c) の値と JSON の受け取り方が書かれていない）：JSON は `--out` のファイルで、(c) の値は対象の example がファイルに書いて受け取ると書いた。直したので移さない
- 3（完了条件の `for` の `exit` が対話のシェルを閉じる）：サブシェルで包んだ。直したので移さない
- 4（新しい規則 3 の守りが 1 つの example だけ）：改善の候補 IB-158 に移した
- 5（`Kernel.srand config.seed` の利点が、いまのコードでは小さい）：改善の候補 IB-159 に移した。M58 は IB-157 の採用どおり 2 行とも出し、ガードも足す
