# M33 フロントエンドの着手前に作者が決めること

M33 では、別のリポジトリにある画面（流用元の Next.js）を本リポジトリの `frontend/` に写し、データの取り方を REST から GraphQL に替える。計画（`implementation-plan.md` の M33）は、下の 9 点に既定の案を置いて書いてある。作者は各項目で「既定のまま」か「変える」かを決める。決まった答えはコーディネーターが台帳（`open-items.md` の OI-06〜OI-14）に先に書き、それからサイクル 05 の計画レビューを始める。

答え方：全部既定でよければ「全部既定で」。変えるものがあれば、番号と変えたい形を書く。

## 画面を見る人の流れ

デモを見る人は、次の順に画面を通る。各項目は、この流れのどこで効くかの順に並べた。

1. リポジトリを開き、手元で起動する（項目 8・9）
2. ログイン画面でアカウントを選んでログインする（項目 3・5）
3. サイドバーから受注側・発注側の画面を行き来する（項目 4・6）
4. 一覧で受注・発注・入荷を見て、状況のバッジで状態を見分ける（項目 1・2・7）

## 1. リポジトリを開いて起動する

### 項目 8：公開の配置（OI-14）

- **何が問題か**：流用元は、インターネットに公開して、訪問者ごとにデータを分ける「デモを開始」の仕組みを持つ。これを写すには、配置先と、訪問者ごとの DB の分け方を作る必要がある。
- **既定**：手元（`bin/rails server` と `next start`）で起動して見せるところまでにする。公開の配置と訪問者ごとのデータの分離は作らない。
- **変えるなら**：公開の配置を作る。配置先の選定と、訪問者ごとのデータの分離が、新しいマイルストーンになる。

### 項目 9：GitHub のリポジトリを public にする時期（OI-06）

- **何が問題か**：いまのリポジトリは private である。ポートフォリオとして見せるには public にする必要がある。public にする前に、履歴まで含めて、仕事の会社名などの書いてはいけない語が無いことを確かめる。
- **選択肢**：
  - (a) M33 を終えたら public にする
  - (b) いますぐ public にする
  - (c) まだ決めない
- **おすすめ**：(a)。画面まで揃ってから見せられ、確かめの作業を M33 の完了条件に入れられる。

## 2. ログインする

### 項目 3：ログイン画面（OI-09）

- **何が問題か**：デモを見る人は、シードのアカウントのメールアドレスとパスワードを知らない。
- **既定**：ログイン画面に、シードの 6 つのアカウントの一覧を並べる。押すとメールアドレスとパスワードが入力欄に入る。一覧は `db/seeds/demo_accounts.json` の 1 か所に置き、シードと画面の両方が読む。
- **変えるなら**：一覧を出さず、README にアカウントを書く。

### 項目 5：ログインの期限（OI-11）

- **何が問題か**：Rails は、応答のたびにログインの期限を延ばす。Next の仕組みでは、画面を読むだけの処理はブラウザの Cookie を書き換えられないので、延びた期限をブラウザに渡せない。
- **既定**：期限は、データを書く操作をしたときだけ延びる。読むだけの使い方なら、ログインか最後の書き込みから 12 時間で切れる。
- **変えるなら**：読むだけでも期限を延ばす。画面ごとに、延ばすための処理を Next に足す必要がある。

## 3. 画面を行き来する

### 項目 4：サイドバーと、ログイン直後の画面（OI-10）

- **何が問題か**：1 つの会社が、売る側（受注側）にも買う側（発注側）にもなる。どちらの画面を出すかを決める必要がある。
- **既定**：サイドバーには「受注側」と「発注側」の両方のグループを、いつも出す。ログインの直後は、売る相手がいれば受注側のダッシュボードへ、いなければ発注側の発注一覧へ移す。
- **変えるなら**：取引の無い側のグループを隠す。

### 項目 6：API に入口を 2 つ足す（OI-12）

- **何が問題か**：画面に要る入口が 2 つ無い。
  - 品目の単価の履歴の画面で、品目を ID で引く入口（`supplier.item(id:)`）
  - サイドバーに自社の名前を出す入口（`viewer.tenant`）
- **既定**：どちらも足すだけの変更なので、M33 で足す。行列テストの行も一緒に足す。
- **変えるなら**：足さずに、一覧を読んで画面の側で探す。

## 4. 一覧で見る

### 項目 1：一覧の読み方（OI-07）

- **何が問題か**：GraphQL の一覧は 1 ページずつ返し、並べ替えの引数を持たない。1 ページだけを画面で並べ替えると、並びが正しくない。
- **既定**：全ページを読み切ってから、画面で並べ替える。500 件で読むのをやめ、やめたことを画面に出す。デモの件数なら 500 件に届かない。
- **変えるなら**：API の一覧に並べ替えの引数を足し、サーバーで並べる。API と行列テストの変更が増える。

### 項目 2：状況のバッジの色（OI-08）

- **何が問題か**：流用元に無い状況がある。品番照合待ち・検収済・発注の各状況・出荷依頼・取り込み・請求書の状況である。これらのバッジの色を決める必要がある。
- **既定**：意味の近い流用元の状況の色を使い回し、新しい色は足さない。
- **変えるなら**：状況ごとに色を足す。足した色は、流用元のコントラストの検査に載せる。

### 項目 7：入荷の一覧（OI-13）

- **何が問題か**：買う側には、発注をまたいで入荷を並べる画面が無い。作るには API に一覧の入口を足す必要がある。
- **既定**：入荷の一覧の画面は作らない。発注一覧の「入荷予定」のタブで代える。検収は発注の詳細の画面で行う。
- **変えるなら**：入荷の一覧の画面と、API の入口（`buyer.inboundShipments`）を足す。
