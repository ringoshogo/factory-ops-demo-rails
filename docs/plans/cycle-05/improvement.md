## 調べたテーマ

### IB-94 CI のランナーの版

- **いまの形**：6 つのジョブがどれも `runs-on: ubuntu-latest`。`test` と `e2e` は、`apt.postgresql.org` の `$(lsb_release -cs)-pgdg` から `postgresql-client-18` を入れる（`adr/001` 決定 6 の pg_dump の版をそろえるため）
- **比べた形**：(a) `ubuntu-24.04` に固定し、上げるときを人が決める。(b) `ubuntu-latest` のまま、移った後に落ちたら直す。(c) PGDG を使わず、`postgres:18` のイメージの中の `pg_dump` を `docker run` で呼ぶ
- **合い方**：(a) は 6 行の書き換えで、移行の日にも CI の結果が変わらない。固定した版の保守が終わる前に上げる作業が要る。(b) は移った日に、PGDG が新しい版の名前を用意していなければ `test` と `e2e` が落ち、どの PR も通らなくなる。(c) は `bin/check-structure` と `db:prepare` が呼ぶ pg_dump・psql の置き換えになり、移す費用が大きい
- **移す費用**：(a) は `ci.yml` の `runs-on` の 6 行と、上げる時期を書く 1 文
- **効いたとする基準**：2026-10-19 の後も、ワークフローを変えない PR の CI が通る。`spec/platform/ci_checks_spec.rb` か `actionlint` 相当で、`ubuntu-latest` が残っていないことを確かめる
- **推奨**：採用（実装を伴う、小さい）。(a) にし、arm64 への移行（テーマ 2）と同じマイルストーンで行う

### IB-93・IB-91 `images` のジョブのランナーと push

- **いまの形**：`images` は amd64 のランナーで QEMU と buildx を使い、`linux/arm64` の 2 つのイメージを組み立てる。キャッシュが空の組み立ては、PR #60 で Rails のイメージが 24 分 47 秒、ジョブが 25 分 59 秒、main への push（`5c5d5cd`）でジョブが 35 分 21 秒だった。キャッシュが効いた後の時間は、このサイクル末の PR の CI で測る（OI-180）。main への push では、テストのジョブの結果を待たずに GHCR へ push する（IB-91）。再発防止で、PR ではイメージに入るものを変えたときだけ流す形にした（`recurrence.md`）
- **比べた形**：
  - (a) arm64 の GitHub ホストのランナー（`ubuntu-24.04-arm`）で、QEMU を使わずに組み立てる。public のリポジトリで使える（GitHub の changelog「arm64 hosted runners for public repositories are now generally available」、2025-08-07）。マニフェストの照合（kubectl と kubeconform）は amd64 の前提で書いてあるので、照合を別のジョブ（amd64）に分けるか、arm64 の kubeconform を sha256 で確かめて取る
  - (b) QEMU のまま、PR では流さない形（再発防止で入れた形）だけにする。main への push の時間は変わらない
  - (c) IB-91：main への push の `images` を、`test`・`e2e` の成功に `needs:` で結ぶ。arm64 で組み立てが数分になれば、待ちの費用は小さい
- **合い方**：(a) は ADR 009「見直す条件」が決めた移り先で、決定そのもの（GHCR に SHA のタグで置く、作者が SHA を選んで適用する）は変えない。Raspberry Pi と同じ arm64 で本番の環境の起動を確かめられ、QEMU の上の `bin/rails runner` の遅さも消える。(c) は、テストの落ちた commit のイメージが GHCR に置かれなくなり、作者が SHA を選ぶときの確かめが 1 つ減る
- **移す費用**：(a) は `runs-on` と QEMU の 2 つのステップの削除、照合のステップの分け直し。(c) は `needs:` の 1 行と、`image_inputs` のジョブとの条件の組み合わせ。どちらも PR の CI で確かめられる
- **効いたとする基準**：`images` のジョブが、キャッシュが空でも 10 分（`config.md`「CI の工程」の予算）の内に終わる。PR で `images` を流す条件（`image_inputs`）を外しても予算に収まるなら、条件を外すかを同じマイルストーンで判断する
- **推奨**：採用（実装を伴う）。(a) と (c) を、テーマ 1 と同じマイルストーンにする

### IB-90 手元の `demo:reset` の入口

- **いまの形**：`DemoReset.run` は、入口で `Platform::DemoWorldGate.open?`（本番の環境の外では常に真）を見て、ロックを取り、`Kubernetes.from_service_account` が ServiceAccount の場所（`KUBERNETES_SERVICE_HOST`）が無いことで例外を上げる。DB を消すのは、その後の `reset` である。`demo_reset_spec.rb` は、本番の環境の入口の門と、Kubernetes の API を差し替えた作り直しを確かめる
- **比べた形**：(a) `demo:reset` の入口で `Rails.env.production?` も求める。(b) いまのまま、順に頼る。(c) `DEMO_WORLD_ENABLED=1` をどの環境でも求める
- **合い方**：(a) は 1 行で、手元の誤った実行が Kubernetes の API の前で止まる。`demo_reset_spec.rb` は本番の環境を差し替えて作り直しを確かめているので、spec の準備が 1 つ増える。(c) は開発とテストのシードの公開 API の門（`DemoWorldGate`）の意味を変えるので、3 つの公開 API に波及する
- **移す費用**：(a) は入口の 1 行と、本番の環境の外で止まることを確かめる example
- **効いたとする基準**：開発の環境で `bin/rails demo:reset` が、ロックも Kubernetes の API も DB のタスクも呼ばずに止まる example が通り、入口の条件を外すと落ちる
- **推奨**：採用（実装を伴う、小さい）。(a)。M42 に入れるか M41 の残りに入れるかは、裁定に任せる
