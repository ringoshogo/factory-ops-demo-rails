# サイクル 07 の終わりに作者が決めること

サイクル 07 のサイクル末の PR をマージする作者が、判断の要る点を 1 件ずつ決めるために読む。各項目は、何が問題か、流用元（`factory-ops-demo`）ではどうしているか、選べる形ごとの作るものと作業量と見せ場、いまの形（既定）と取りまとめ役のおすすめ、を書いた。作業量は、取りまとめ役とも実装者とも別の Claude のサブエージェントが `cd585d3` のコードと流用元の実物を読んで見積もり、取りまとめ役がファイルと行と手元の PostgreSQL で確かめた。決まった答えは、取りまとめ役が台帳（`open-items.md`）の行の結果の欄に書き、行の ID で担当に渡す（`guides/dev-cycle.md`「残件の台帳」）。

答え方：項目ごとに「既定のまま」か、選ぶ形の記号を書く。全部既定でよければ「全部既定で」。おすすめが既定と違う項目（1・2）は、おすすめの形を書くか「既定のまま」を書く。

## 読む順

おすすめが既定と違い、答えで作るものが変わる問い（1・2）を先に、作者が手を動かすこと（3・4）を次に、確かめるだけの判断（5〜11）を最後に置いた。1 は答えが来るまで M50 の残りを閉じない。2 は既定で動いているので、答えが来るまでいまの形のまま置く。

## 1. 品目の単位の並び順（OI-199）

- **何が問題か**：M50 で、品目の画面（画面 10）を単位の見出しで並べられるようにした。単位の列は照合順序を持たせず、DB の既定の照合順序（`en_US.utf8`）で並ぶ。デモの世界の単位（「個」「本」「箱」）は、既定では「個 < 本 < 箱」に、取引先と品目の名前に使った ICU の日本語の照合順序（`ja-x-icu`、作者が OI-190 で選んだ）では「個 < 箱 < 本」に並ぶ（取りまとめ役が手元の PostgreSQL で確かめた）。サイクル 07 の逸脱検査が、設計文書の規則（照合順序を持たせるのは、ロックの順を決めるキーと画面に並べる名前の列）からは単位の扱いが決まらないとして、作者の判断に回した（`conformance.md` の D1）
- **流用元では**：品目の画面の列の並べ替えは、数値でない列をすべてブラウザの `Intl.Collator("ja")` で並べる（`frontend/components/master-screen.tsx` の `sortColumns`、`frontend/lib/sort.ts`）。単位も「個 < 箱 < 本」に並ぶ
- **選べる形**

  | 形 | 作るもの | 作業量 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し（`data-model.md` に、名前でない短い語の列は既定のままにすると 1 文を足す） | ほぼ無し | 照合順序を持たせる列の範囲を「名前の列」に限る判断として辿れる。単位が流用元と違う順に並ぶ |
  | (a) 単位の列も `ja-x-icu` にし、流用元とそろえる | マイグレーション 1 本（M49 の名前の列と同じ形）、`db/structure.sql`、`spec/platform/collations_spec.rb` の対応、単位で並べる request spec の期待、`data-model.md` の表に 1 行 | 小さい（M49 が名前の列で通した手順と同じで、strong_migrations も止めない） | 「画面に並べる日本語の列は `ja-x-icu`」の規則に例外が無いことを見せられる。作者の OI-186（流用元が並べる列をそろえる）にも合う |

  受注番号の写し（`shipment_requests.sales_order_no`）は `SO-000001` の形の ASCII で、どちらの照合順序でも並びは同じなので、問わない

- **答えで変わること**：(a) なら、サイクル 08 で M50 の残りとしてマイグレーションと spec を足す。既定なら、`data-model.md` に 1 文を足して OI-199 を閉じる

## 2. CI の `publish` が、テストの落ちた commit のイメージを置かない守りの書き方（OI-184 への追記）

- **何が問題か**：GitHub の CI で、main への push のたびに公開の配置のイメージを GHCR に置く `publish` のジョブは、ほかの 7 つのジョブがすべて成功したときだけ流れる。作者は OI-184 で「M48 で簡単にできるかを確かめる」と答え、M48 はその条件をワークフローに書かない形にした。`.github/workflows/ci.yml` の `publish` の `if:` は `github.event_name == 'push'` だけで、GitHub が状態の関数の無い `if:` に足す暗黙の `success()` が、`needs` のどれかが落ちたか skip されたときに `publish` を止める。守りは YAML の行に見えず、コメントと `guides/config.md`「CI の工程」と、`if:` が状態の関数を含まないことを確かめる `spec/platform/ci_checks_spec.rb` の example で補っている。暗黙の `success()` に頼る形そのものは、作者に確かめていない
- **流用元では**：`publish` に当たるジョブが無い。`.github/workflows/ci.yml` の `build-push` のジョブが、Go のテストの後のステップで `if: github.event_name == 'push'` を付けて push する。前のステップが落ちればジョブが止まるので、守りはステップの順で決まり、状態の関数も `needs` も使わない。画面のテスト（別のジョブ）は push を止めない
- **選べる形**

  | 形 | `publish` の `if:` | 作るもの | 作業量 | 見せ場 |
  |---|---|---|---|---|
  | 既定 | `github.event_name == 'push'` | 無し | 無し | spec が「書いていないこと」を照らす。`ci.yml` を開いた読み手は、コメントを読まないと守りに気づかない |
  | (a) `success()` を明示する | `success() && github.event_name == 'push'` | `ci.yml` の 1 行とコメント、`ci_checks_spec.rb` の example を「`success()` を含み、`failure`・`cancelled`・`always` を含まない」に替える、`config.md` の段落、壊して落ちる記録。M48 と同じく、ブランチへの push で止まる側と流れる側の 2 回を確かめる | 小さい（GitHub の文書では明示しても暗黙と同じ評価だが、OI-184 でジョブの段の評価が文書から読めない振る舞いをしたので、push で確かめる） | 守りが YAML の行と spec の両方から読め、「設計判断がコードのどこで守られているかを辿れる」というこのリポジトリの目的に合う |
  | (b) M42 の形に戻し、`needs` の結果を並べる | `!cancelled() && !contains(needs.*.result, 'failure') && …` | `ci.yml`・spec・文書と、push の確かめ | 中くらい（式が長く、OI-184 の skip の見え方をもう一度確かめる） | 守りは見えるが、理由の説明（OI-184 の経緯）が要る |

- **既定**：いまの形（暗黙の `success()`）
- **おすすめ**：(a)。作業は小さく、守りが行に見える
- **答えで変わること**：(a) なら、サイクル 08 の計画で M51 に足すか小さいマイルストーンを起こす

## 5〜11. 確かめるだけの判断（judgment）

取りまとめ役が、作者に確かめられないまま決めたことである。どれも既定で作ってあり、違う形を求めるときだけ答える。内容と理由は台帳の各行にある。

### 5. 出荷依頼の受注番号を、イベントで運んで写す（OI-193）

- **何が問題か**：出荷依頼の画面（画面 9）を受注番号の見出しで並べられる（作者の OI-186）。出荷のパッケージは受注に依存しないので、受注番号を「出荷可能」のイベントで運び、出荷依頼の表に写して並べる。画面に出す受注番号は、これまでどおり受注から読む。列を足す前からある DB では、作り直し（`bin/rails read_models:rebuild`）を流すまで写しが空で、受注番号で並べると末尾に来る
- **流用元では**：パッケージを分けず、出荷指示を受注の表に結合して受注番号（整数）を読み、ブラウザで並べる（`backend/internal/store/shipping_instructions.go`、`frontend/components/instruction-table.tsx`）。写しもイベントも無い
- **選べる形**：既定（イベントで写す）。(a) 出荷を受注に依存させ、受注の公開 API の副問い合わせを結ぶ：依存の向きを変え、写しの列・イベントの項目・作り直しの部分を消し、`context-map.md`・`adr/011`・見せどころを書き直す（中くらい〜大きい）。(b) 受注番号では並べない：並べ替えの値を非推奨にして画面から外す（小さい〜中くらい）
- **見せ場**：既定は、受注と出荷がイベントだけでつながる依存の向きを守ったまま相手の値で並べ、イベントの項目・写しの列・作り直し・一致の spec で辿れる。M46 の品目の写しと同じ型の 2 例目になる（`adr/011` 代替案 D）。(a) は 1 つの列のために依存の向きを変え、(b) は OI-186 を一部戻す
- **おすすめ**：既定のまま

### 6. 照合順序の版の記録の改め方（OI-197）

- **何が問題か**：PostgreSQL のイメージを上げて ICU の版が変わると、名前の列を使うたびに「照合順序の版が合わない」と警告が出て、並びが変わりうる。版の記録は DB ごとにあり、新しい DB は `template1` から写すので、毎日の作り直しでは古いまま残る。M49 は、イメージを上げた人が `template1` で `ALTER COLLATION pg_catalog."ja-x-icu" REFRESH VERSION` を流してから DB を作り直す手順にした（`guides/config.md`「照合順序の版」、`deploy/README.md`）。計画の「索引を作り直してから改める」は、DB を残すときだけの手順にした
- **流用元では**：無い。名前をブラウザの `Intl.Collator("ja")` で並べ、DB の照合順序に頼らない
- **選べる形**：既定。(a) 計画の形（DB を残し、索引を作り直してから改める。文書の入れ替えだけで小さいが、対象の索引を手で数える）。(b) 毎日の作り直しが版を比べ、食い違えばログに出して止める（中くらい。記録を改める `ALTER COLLATION` はスーパーユーザーが要るので、自動で改めるところまではしない）
- **見せ場**：既定と (a) は手順の文で、見せ場は名前の並びを DB の照合順序で解いた側（`spec/platform/collations_spec.rb` が版の食い違いを落とす）にある。(b) は運用性の例になるが、年に数回もしない作業のための仕組みになる
- **おすすめ**：既定のまま。作り直しに任せれば索引も新しい ICU で作られ、手で数えるより誤りにくい

### 7. 見出しの Shift の操作の細部（OI-195）

- **何が問題か**：一覧の見出しを Shift を押して押すと、2 つ目からの並べる列を足せる（作者の OI-187）。細部は M47 で次のとおり決めた（`frontend/lib/list.ts`）。URL は `sort=status,customer_name&dir=asc,desc` のようにつなぎ、列が 1 つの URL は前と同じ。並びに無い列は昇順で後ろに足し、並びにある列は 昇順 → 降順 → 並びから外す の順に進める。列は 3 つまで。何番目かの数字は 2 つ以上で並べているときだけ出す
- **流用元では**：並べる列は常に 1 つで、Shift の操作も数字も無い。`frontend/lib/sort.ts` の `nextSort` は「同じ列は 昇順 → 降順 → 既定の順、別の列は昇順」
- **選べる形**：既定。(a) Shift で並びにある列を押しても外さず、昇順 ⇄ 降順を行き来する（`nextSort` の 1 行と単体・E2E の期待。小さい）。(b) 数字を列が 1 つのときも出す（小さい〜中くらい。品目の画面は 1024px で幅が詰まっていて、番号の幅ではみ出すおそれがある）
- **見せ場**：どの形も画面の操作の細部で変わらない。見せ場は API の列の組の keyset のページングにある
- **おすすめ**：既定のまま。「昇順 → 降順 → 外す」は流用元の操作の順と同じで、覚え方がそろう

### 8. 並びが 2 つ以上のときに、Shift なしで並びにある列を押した結果（OI-198）

- **何が問題か**：たとえば「状況 ↑、取引先 ↓」で並べているときに、Shift を押さずに「取引先」を押すと、「取引先 ↑」の 1 つの並びになる。並びにあった向き（↓）は引き継がない
- **流用元では**：並びが常に 1 つなので、この場面が無い。別の列を押すと昇順になる
- **選べる形**：既定（その列の昇順）。(a) その列の向きを進める（取引先 ↓ の次で並びから外れる。小さいが、列 1 つにしたいだけの操作で並びを失う）。(b) その列の向きを保って 1 つにする（取引先 ↓。小さい）
- **見せ場**：どの形も無い
- **おすすめ**：既定のまま。押した列が並びにあってもなくても同じ結果になり、流用元の「別の列を押すと昇順」と同じ規則で説明できる

### 9. 品目の画面の「安全在庫」の列と、有効在庫を並べないこと（OI-194）

- **何が問題か**：品目の画面に「安全在庫」の列を足し、見出しで並べられるようにした。有効在庫の列は見出しで並べられない。有効在庫で並べたいときは在庫の画面を使う
- **流用元では**：品目の画面は品目コード・品名・単位・販売単価・安全在庫数の 5 列で、どれも並べられる。有効在庫・税率・カタログの列は品目の画面に無い（`frontend/app/(app)/items/page.tsx`）
- **選べる形**：既定。(a) 有効在庫でも並べる（安全在庫と同じ形の副問い合わせを 1 つ足す。小さいが、並べ替えの見出しは狭い幅でも隠せないので、10 の 1024px のはみ出しを別の形で解く要がある）。(b) 有効在庫の列を品目の画面から消し、流用元とそろえる（小さい。10 の列を隠す要が無くなる見込みだが確かめていない）
- **見せ場**：どれも画面の見た目の差で、見せ場ではない
- **おすすめ**：既定のまま。流用元の品目の画面に有効在庫は無く、並べられる在庫の画面にある

### 10. 品目の画面を 1024〜1279px で見るときに「税率」「有効在庫」の列を隠す（OI-200）

- **何が問題か**：ノートパソコンの小さめの画面の幅（1024〜1279px）で、品目の画面の税率と有効在庫の列が見えない。安全在庫の列を足して単位と単価を並べ替えの見出しにしたところ、1024px で表がパネルから 89px はみ出したためである。並べ替えの見出しの列は隠さない
- **流用元では**：列を隠さず、1024〜1279px では行の操作のボタンを「⋯」のメニュー 1 つにまとめて収める（`frontend/components/row-actions.tsx`）。品目の画面は 5 列である
- **選べる形**：既定。(a) 流用元と同じく品目の行の操作を「⋯」にまとめ、列は隠さない（中くらい。編集のダイアログをメニューから開ける形に直す要があり、89px を操作の列だけで取り戻せるかは確かめていない）。(b) 9 の (b) と同じく有効在庫の列を消す（小さい）
- **見せ場**：どれも画面の見た目の差で、見せ場ではない
- **おすすめ**：既定のまま。税率は編集のダイアログに、有効在庫は在庫の画面にあり、値は失われない。隠した列は API で並べられないので、隠れた列で並ぶことも無い

### 11. E2E の世界に足した、照合待ちのまま取り消した伝票（OI-201）

- **何が問題か**：取り消した伝票の合計の欄に「取消」と出すこと（作者の OI-192）を、E2E で画面に出して確かめるために、品番の対応の無い明細 1 つの発注を受注側が取り消した 1 組を世界に足した。発注側の依頼を受注側が承認して取り消した照合待ちの伝票（発注の `CANCELLED`）は世界に置かず、単体のテストだけが確かめる
- **流用元では**：無い。品番照合が無く、すべての受注が合計を持つ
- **選べる形**：既定。(a) 発注側が取消を依頼し、受注側が承認した 1 組も足す（小さい〜中くらい。世界の作り方を 1 つ足し、E2E の件数の期待が動きうる）
- **見せ場**：どちらも画面の文言の確かめで、見せ場ではない
- **おすすめ**：既定のまま。画面の分岐は取消の状況の集合 1 つで、2 つの取消の状況は単体がすべての値で確かめる
