## 調べたテーマ

### 1. IB-117 手元の E2E のログインの時間切れ

- **いまの形**：
  - 5 秒は Playwright の期待の既定の待ちである。`frontend/playwright.config.ts` はテスト全体の `timeout: 60_000` だけを置き、`expect.timeout` を置かない。Playwright の文書は、期待の既定を 5 秒とし、テストの時間切れとは別だと書く（https://playwright.dev/docs/test-timeouts 「Expect timeout」）。待っているのは `frontend/e2e/support/world.ts` の `login` の `toHaveURL`（38 行）で、ログインのボタンを押してから、Next の server action が Rails に問い合わせ、移った先の URL に変わるまでを 5 秒で待つ（URL を確かめる期待で、移った先の画面を描き終えたことまでは見ない）
  - E2E は、`next build` の後に `next start` の本番のサーバーを 2 つ起こす（`frontend/package.json` の `test:e2e`、`playwright.config.ts` の `webServer`）。Next の開発のサーバーの初回の翻訳は原因でない。Rails は `RAILS_ENV=test` の `bin/rails server`（Puma の単一のモード、スレッド 3）で、`bin/jobs` が 4 系統のキューで動く（`frontend/e2e/start-rails.sh`、`config/queue.yml`）。Playwright のワーカーは `E2E_WORKERS`（既定 2）
  - **手元と CI の違い**：`config/environments/test.rb` 18 行は `config.eager_load = ENV["CI"].present?` で、CI の `e2e` のジョブは `CI: "1"` を渡す（`.github/workflows/ci.yml` 217 行。GitHub Actions もすべてのジョブに `CI=true` を渡す）。CI の Rails は起動の時にアプリを読み込んでから `/up` に答え、手元の Rails は最初の要求のたびに遅延で読み込む。`config/boot.rb` は test の環境で bootsnap の命令列のキャッシュを止めるので、読み込むたびに Ruby を翻訳し直す（Claude の調査）
- **遅さの原因の候補**（推定。単独の実行との比べは測っていない）：
  1. 3〜5 の担当が同じマシンと同じ PostgreSQL のコンテナで rspec・E2E・Next の組み立てを並行で流す負荷。M33 の残りは load average 10〜17 で GraphQL の 1 回が DB で 4 秒かかり、52 件がすべてログインで落ちた。2 系統とも最も有力とみた
  2. 手元だけの遅延の読み込み。M50 の「各ワーカーの最初の example が落ちることがあった」、M49 の「同じ回の前の 2 件は 10 秒と 17 秒」は、最初の要求に読み込みの費用が乗る形に合う（Claude）
  3. ログイン以外の待ちも負荷で 5 秒を超えた（M50 の 2 回目の Shift の example）ので、ログインだけの問題ではない（Codex）
- **比べた形**：
  - (a) 手元の E2E の Rails も起動の時に読み込む（`start-rails.sh` が E2E のための専用の変数を渡し、`test.rb` の `eager_load` の条件に足す。`CI` そのものは渡さない）
  - (b) 期待の待ちを延ばす。`login` の `toHaveURL` にだけ延ばす形（Claude）と、`playwright.config.ts` で手元の期待の待ちを変数で明示できるようにする形（Codex）がある。M33 の残りは手元でだけ全体を 30 秒にして対象の 15 件を通した（commit していない）
  - (c) API でログインして `storageState` をワーカーごとに使い回す（https://playwright.dev/docs/auth 「Authenticate with API request」「one account per parallel worker」）
  - (d) `E2E_WORKERS=1` と、重い処理の同時実行を抑える。既存の変数で比べられる（Codex）
  - (e) 手元の E2E の全体を完了条件から外し、CI の `e2e` で代える
- **合い方**：(a) は手元と CI の差を消し、原因 2 だけに効く。`eager_load` は Zeitwerk の読み込みの誤りも手元で捕まえるので、確かめが強くなる側の変更である。(b) は原因 1 にも効く。ログインの待ちは製品の競合の待ちではなく、「ログインが済んだ」を確かめるだけなので、延ばしても `retries: 0`（1 回だけ落ちたテストを再実行で緑にしない方針）と矛盾しない。全体の待ちを無条件に 30 秒にすると、製品の遅さも隠す。(c) は、E2E の中にログイン・ログアウト・取り消し・テナントの切り替えを確かめる example があり、6 つのペルソナごとの状態と、ログアウトで進むセッションの世代（`world.ts`、`request.ts`）を扱う要がある。移った先の画面の GraphQL は残るので、原因 1 には効かない。(d) は全体の時間が延びる見込み。(e) は M50・M33 の残りが実際にした形で、証跡の書き方は再発防止で手順に置いた
- **移す費用**：(a) `test.rb` 1 行と `start-rails.sh` 1 行と、`guides/config.md` の 1 文（コードで確かめた）。(b) `world.ts` か `playwright.config.ts` の 1 か所とコメント。(c) ペルソナごとの fixture、Cookie の扱い、世代を進めた後の再認証、ログインを確かめる spec の書き分け（数十行の見込み）。(d) 測定の記録だけ
- **効いたとする基準**：同じ版で、負荷の低い手元（load average がコア数未満）と並行の負荷のある手元を分け、ワーカー 1・2、`eager_load` の有無、期待の待ち 5 秒と延ばした値を比べ、各ワーカーの最初のログインの時間（ボタンを押してから URL が変わるまで）と全体の時間を記録する。採る形にした手元で全体を続けて 3 回流し、ログインと Shift の時間切れが 0 件。わざと壊した期待は引き続き落ちる
- **推奨**：採用（実装を伴う、小さい）。2 系統とも採用で、形が少し違う。Claude は (a) と (b)（ログインにだけ延ばす）を推し、Codex は (b)（設定で明示）と (d) の比べを先に置き、30 秒を無条件に既定にすることと (c) は比べの後に決めるとした。まとめると、サイクル 08 の最初のマイルストーンで、上の基準の比べを先に流し、(a) と、ログインの待ちを延ばす (b) を入れ、比べの結果を証跡に書く。(c) は見送り（負荷の側に効かず、ログインと取り消しの example の書き分けが要る。調べ直す条件：(a)(b) の後も、負荷の低い手元でログインの待ちで落ちるとき）。(d)・(e) は回し方の側なので、比べの結果を振り返りに渡す

### 2. IB-130（新）一時の DB の後片付け

- **いまの形**：
  - DB を作る入口は 3 つ。(i) rspec を別の DB で流す `TEST_DATABASE=<名前>_test bin/ci`（`handoff.md`「開発環境」、`guides/config.md`「database.yml：同じ DB に 2 つのロールで接続する」）で、`bin/ci` が `db:test:prepare` で作る（`config/ci.rb`）。(ii) E2E は `E2E_DATABASE` を `playwright.config.ts` 41 行が `TEST_DATABASE` に写し、`start-rails.sh` が毎回 `db:drop db:prepare` で作り直す。終わったときには消さない。(iii) レビュアーが `factory_ops_m47_review_test` のように別の名前で作る
  - 消す入口は無い。`bin/` に一時の DB を一覧するか消すコマンドは無く、`guides/dev-cycle.md` の担当への依頼の項（「着手の前に」）は worktree と一時ファイルの置き場を書くが、DB に触れない。名前の規則は「`_test` を区切りとして含める」（行列の補助 `spec/support/matrix_cross_read.rb` 90 行が `/_test(_|\z)/` を見るため）だけで、E2E の DB の名前の規則は無い。残る 14 個のうち `factory_ops_m49` は `_test` も `_e2e` も含まない
  - 残る DB の費用：照合順序の版を改める手順（`config.md`「照合順序の版」）は、`TEST_DATABASE` で使う DB もそれぞれの名前で作り直すことを求めるので、残った DB の数だけ手間が増え、作り直さない DB は版の食い違いの警告を出し続ける（Claude）。ディスクの量は測っていない
- **比べた形**：(a) 一時の DB を一覧し、明示して消す `bin/` のコマンドか rake のタスク。対象は名前が `factory_ops_` で始まり、`_test` か `_e2e` を区切りとして含み、既定の 3 つ（`factory_ops_demo_rails_development`・`factory_ops_demo_rails_test`・`factory_ops_e2e`）でないもの。`DROP DATABASE` を `FORCE` なしで流す。PostgreSQL の文書は、対象の DB に誰かが接続していると `FORCE` なしでは失敗すると書く（https://www.postgresql.org/docs/18/sql-dropdatabase.html 「Description」）。(b) 担当の依頼の型に後始末を書く。(c) 取りまとめ役が担当を止めるとき（worktree を消すとき）に、その担当の DB を消す。(d) 名前の規則（`factory_ops_<担当>_test`・`factory_ops_<担当>_e2e`）だけを足す。(e) `bin/ci` の終わりに常に消す
- **合い方**：(a) は、どの担当が作ったかを知らなくても消せ、接続中の DB は消えずに失敗するので、動いている担当を壊さない。ただし、レビューの直しを待つ担当の DB は接続が無いので消える。消えても `bin/ci` と `start-rails.sh` が作り直すので、失うのは作り直しの時間だけである。(b) は担当が途中で止まると残る。(c) は担当の名前と DB の名前が対応していれば確実だが、レビュアーの DB は担当と別の名前になる。(d) は (a) の対象の判定を確かにするだけで、消しはしない。(e) は失敗の調べや流し直しに使う DB まで消す
- **移す費用**：(a) タスク 1 つ（所有ロールの接続で `pg_database` を引き、`DROP DATABASE` を流す。数十行の見込み）と、既定の DB と名前の形に合わない DB と開発・本番の DB を対象に入れないことを確かめる spec、`guides/bin.md` の 1 行と `config.md` の名前の規則の 1 文。DB のスキーマの変更は要らない
- **効いたとする基準**：(a) の spec が、既定の DB と名前の規則に合わない DB を対象に入れると落ちる。接続中の DB は消えずに残る。サイクル 08 の末に、一時の DB の一覧がそのとき動いている担当の DB だけで、作者が手で消した回が 0 回
- **推奨**：採用（実装を伴う、小さい）。2 系統とも (a) と名前の規則を推した。(c) の、担当を止めるときに (a) を流す 1 文と、(b) の依頼の型は、回し方の変更なので、裁定の後に `dev-cycle.md` に書く。台帳に IB-130 を起こした

### 3. IB-122・IB-101 画面の組み立ての時の `next/font/google` の取得
