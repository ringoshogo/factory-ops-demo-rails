# サイクル 02 の計画レビュー：M34・M35・M21〜M24 への反映

`implementation-plan.md` の M34・M35・M21〜M24 を、2 系統の独立レビュー（Claude と Codex）にかけ、指摘を計画に反映した記録である。Codex の初回の High を直した計画を Codex で読み直し（読み直し 1）、Claude の初回の High を直した計画をもう一度 Codex で読み直した（読み直し 2）。読み直し 2 で出た High は直し、3 回目の読み直しには出さなかった（下の「判定」）。M34・M35・M21〜M24 に着手する担当者と、計画のレビューをする人が読む。担当者は、計画の節が「なぜこう書いてあるか」をここで引ける。

読む順は、マイルストーンごとの判定 → 指摘ごとの対応 → 指摘の根拠を確かめた結果 → 作者の判断 → 直さなかった指摘である。指摘の出典は次の形で示す。

| | Claude | Codex |
|---|---|---|
| 初回 | `<マイルストーン>-<番号>`（`M21-2` など） | `P<番号>` |
| 読み直し 1・2 | — | `N<番号>` |

## 判定

| マイルストーン | 初回 Claude | 初回 Codex | 読み直し 1 Codex | 読み直し 2 Codex |
|---|---|---|---|---|
| M34 依存の更新と使っていない部品の削除 | Conditional Go | No-Go | Go | Go |
| M35 分岐の網羅率の警告 | Conditional Go | No-Go | Go | Go |
| M21 取消依頼と審査 | Conditional Go | No-Go | Go | Go |
| M22 受注側の取消と、取消と出荷の競合 | Go | No-Go | Go | Go |
| M23 検収 | Go | No-Go | Go | Go |
| M24 請求の締め | Conditional Go | No-Go | Go | Conditional Go |

初回の Codex は、マイルストーンごとの判定ではなく、全体を 1 つの No-Go とした。表の初回 Codex の列は、取りまとめ役が重大度から決め直したものである。6 つのマイルストーンのどれにも High の指摘があるので、どれも No-Go になる。No-Go の理由は次の 2 つに集まる。

- **完了条件が保証を確かめない**：M21〜M24 の完了条件に spec のパスとコマンドが無く、目的に書いた保証（出荷指示の停止、受注側へ 1 回だけ、取引先ごとの直列化、遅れた検収）の一部を確かめていなかった。M34 の警告の件数と保守の判定は、書いたコマンドでは判定できなかった。
- **成り立たない前提**：M35 は、サイクル 01 の M20 の X1 を分岐の網羅率で拾えることを、採用の根拠と完了条件にしていた。M23 は、受け手の無いイベントを配送する方法が無かった。

Claude は、初回で High を 6 件挙げ、それを直せば Go とした（Conditional Go）。M34-1（OI-58）・M35-1（X1）・M21-1（OI-24・OI-53）・M24-2（直列化と遅れた検収）は Codex の P04・P05・P09・P16 と同じ指摘である。M21-2（新しいイベントが宛先テナントを運ばない）と M24-1（締めで集める明細が設計文書の間で食い違う）は Claude だけが挙げた。Claude の報告は、作業を始めた時点の計画（`5f67a8e`）に当てたものを正とした。Claude は、Codex の指摘で直している途中の計画にも当てた報告を別に返し、そちらは全 Go だった。途中の版への再読として扱い、判定には使わない。

読み直しは、前の Critical・High の対応を評価し、High 以上の新しい指摘だけで判定した。

- **読み直し 1**：Codex の初回の High 11 件を見て、すべて解消と判定した。新しい High 以上の指摘は無く、Medium の N01 が出た。
- **読み直し 2**：Claude だけが挙げた M21-2・M24-1 を直した計画を見て、2 件とも解消と判定した。M24 に新しい High の N02（下書きの請求番号と GraphQL の型の食い違い）が出て、Conditional Go とした。N02 は名指しの直しなので直し、3 回目の読み直しには出さない。

これで 6 つのマイルストーンに No-Go は残っておらず、M34 から着手できる。

## 指摘の根拠を確かめた結果

指摘の根拠は、リポジトリのコードと、インストール済みの gem（Rails 8.1.4・bundler 2.5.3・graphql-ruby 2.6.11・bootsnap 1.26.0）で確かめた。Ruby 3.4 は手元に無いので、どちらのレビュアーも 3.4 での全件の実行はしていない。

| 根拠 | 結果 |
|---|---|
| 配送表に無いイベントは `Contracts.publish` が失敗し、受け手の無い行は配送表の spec が落とす（P14） | 正しい。`Contracts::Subscriptions.routes` は `TABLE.fetch` で `KeyError` を出し、`spec/contracts/subscriptions_spec.rb` は表の受け手が `handle` を持つことを確かめる |
| 付帯情報の無いイベントのジョブは、受信の監査の行で失敗する（P09・OI-53） | 正しい。`ApplicationJob#deserialize` は付帯情報の無いジョブで `app_metadata` を `nil` にし、`Contracts::EventJob#record_receipt` はそれに `fetch` を呼ぶ。`guides/config.md` の「項目の無いジョブも動く」と食い違う |
| 分岐の網羅率では M20 X1 を拾えない（P05・M35-1） | 2 系統とも、`ded1244` の親で計測して確かめた。Codex が `ded1244` の親の互換の判定と spec を Ruby 3.3.3 の `Coverage`（行と分岐）で流し、22 examples, 0 failures で、X1 に当たる未通過の分岐は無かった。未通過は、空の報告・YAML の形の誤り・非破壊の変更の報告・削除の種類の届かない分岐だけだった。Claude も同じ結果で、型の参照を数える処理は `select` のブロックの中の `&&` で書かれ、Ruby の分岐の網羅率は `&&` を分岐に数えないことを確かめた |
