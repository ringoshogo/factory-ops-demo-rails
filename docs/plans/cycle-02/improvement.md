# サイクル 02 の改善の探索

サイクル 02 の台帳の棚卸し（`inventory.md`）が起動を決めた改善の探索の記録である。手順は `guides/cycle-end.md`「改善の探索」にある。取りまとめ役が候補を調べ（計測は、取りまとめ役とも実装者とも別の Claude のサブエージェントが、別の作業ツリーと別名のテスト DB で行った）、テーマごとの裁定（`採用`・`監視`・`見送り`）は、2 系統のレビュアーが下の調査を読んで出し、「裁定」の節と改善の候補の台帳に書き足す。

## モード

**検証**。台帳の棚卸しの時点で、改善の候補の台帳に `未着手` が 20 件あった（IB-06〜IB-13、IB-15〜IB-26）。棚卸しで IB-22 を残件に移し、IB-24 を再発防止で `反映済み` にし、振り返りの想定外のうち設計と実装のやり方に関わる CI の test のジョブの時間を IB-27 として足したので、探索を始めた時点では 19 件である。回し方に関わる想定外（レビューの対象の版、結果の返し方、依頼の型）は、再発防止で手順に直したので、ここでは扱わない。IB-24（bootsnap）は、再発防止で仕組みにした（`recurrence.md`）。

あわせて、`起票済み` の IB-01（M35 分岐の網羅率の警告）の効き目を、サイクル 02 の警告の件数で確かめる。

## 調べたテーマ

### IB-27 行列テストの世界を、example ごとに作り直すのをやめるか

- **いまの形**：`spec/matrix/table_matrix_spec.rb` と `spec/matrix/graphql_matrix_spec.rb` は `let(:world) { MatrixWorld.new }` で、example ごとに世界（5 つのペルソナ × テナントの表 32 個の行、取引関係 3 つ、連結した発注・受注・出荷 3 組）を作り直す。世界を 1 回作る費用は 0.477 秒（INSERT 475 文、`set_config` 356 文、factory 464 回）で、1 example の時間のほぼ全部である。表の行列の example は「20 × 表の数 + 4」で、世界を作る費用も表の数に比例するので、全体は表の数の 2 乗で伸びる。CI の Run tests は、サイクル 01 の末の 415 秒から M24 の 864〜921 秒に伸びた。同じ example 数でも、ランナーの揺れで最大 1.6 倍違う
- **比べた形**：(a) 世界をファイルごとに 1 回作り、外側のトランザクションで包む。各 example は、いまと同じく rspec-rails の savepoint の中で動いて巻き戻る。(b) 1 つの表の 20 example を `aggregate_failures` で 1 example にまとめる。(c) CI でジョブを分けるか並列に流す。(d) 行列だけ分岐の計測を外す。(e) test-prof の `before_all`
- **計測した結果**：(a) を別の作業ツリーで試した。表の行列（644 examples）が 302 秒から 5.4 秒に、入口の行列（207 examples）が 102 秒から 3.3 秒になった。全件（1635 examples、`COVERAGE=1`）は 523 秒から 67.5 秒で、0 failures。`--order rand` の 3 つのシードで行列の 851 examples が通った。`invoices` の RLS を外すと、いまの形と (a) で同じ 20 examples が落ちた。(d) は、(a) の後の行列で、計測ありが 8.1 秒、なしが 8.7 秒で、差は揺れの範囲だった
- **合い方**：(a) はアプリのロールで動くこと（`data-model.md`「RLS」）も、example ごとの巻き戻しも変えない。弱まるのは、example が別の接続でコミットしたときに、汚れた世界が次の example に渡ることで、行列の 2 ファイルはどちらも別の接続を使わない。外側のトランザクションに接続を固定するのに `ActiveRecord::ConnectionPool#pin_connection!`（Rails 7.2 以降で transactional fixtures が使うメソッド）を呼ぶ。(b) は example の粒度と層の件数を変える。(c) は半分が上限で、ジョブごとに Ruby と DB の準備がかかり、2 乗の伸びを止めない。(e) は gem が 1 つ増える
- **移す費用**：2 ファイルでそれぞれ数行の置き換え。`guides/testing.md`「行列テストとの分担」に、世界をファイルごとに作ることと、行列の spec で別の接続を使わないことを書く
- **効いたとする基準**：CI の Run tests が 3 分以下。行列の 2 ファイルが合計 30 秒以下。RLS を外したときに落ちる example の集合が、いまの形と同じ
- **推奨**：採用（実装を伴う）。(a) にする。(c) は、(a) の後も Run tests が 5 分を超えたら調べ直す

### IB-26 競合テストの後始末の呼び忘れを止めるガード

- **いまの形**：`delete_owned_rows`（`spec/support/concurrency.rb`）は、呼ばれれば消し漏れを検出する。既存のガード（`spec/concurrency/concurrency_helpers_spec.rb`）は、残す表を渡したときの失敗と、表の書き漏らしを確かめる。`after` を消して呼ばなくなったことは、誰も捕まえない。テナントを毎回乱数で作るので、業務の行が残っても一意の制約ではぶつからない。ただし、残ったイベントのジョブは、テナントで絞らない `deliver_enqueued_events` に後の example で拾われる（裁定の Claude の指摘）
- **比べた形**：(1) `delete_owned_rows` が呼ばれた印を立て、設定の `config.after(:example, :concurrency)` で印が無ければ失敗させる（設定の `after` は、example group の `after` より後に走る）。(2) rspec の終わりに、所有ロールでテナントの表が空かを見る
- **合い方**：(1) は、`spec/platform/bullet_spec.rb` の内側の example group を走らせる型で、`after` を持たない内側の example が落ちることを確かめられる。(2) はどの example の漏れかが分からず、途中で止まった前の実行の残りでも落ち続ける
- **移す費用**：補助に数行と、ガードの example 1 つ。走る時間はほぼ 0
- **効いたとする基準**：競合テストの 1 本から `after` を消すと、その example が落ちる
- **推奨**：採用（実装を伴う、小さい）。(1) にする

### IB-09 request spec の補助を `spec/support` に寄せる

- **いまの形**：`def login_as(user)` が request spec の 9 本と `spec/support/scenarios.rb` の計 10 か所にあり、中身は同じである。`def graphql(` は 11 本で、応答をそのまま返す形（7 本）、`errors` が空であることを確かめて `data` を返す形（3 本。`ScenarioHelpers#query` と同じ）、その他（1 本）に分かれる。`def mutate(` は選ぶフィールドの受け取り方で 4 つの形に割れている
- **比べた形**：`login_as` と、2 つの `graphql` の形だけを `spec/support/request_helpers.rb` に置き、`type: :request` に取り込む。`mutate` は寄せない
- **合い方**：spec の中で定義したメソッドは、取り込んだモジュールより優先されるので、1 ファイルずつ移せる。`rails_helper` は `spec/support` を自動で読まないので、`require` を足す
- **移す費用**：11 ファイルの機械的な置き換え
- **効いたとする基準**：`git grep "def login_as(user)"` が 1 か所になる。次のサイクルで足した request spec に `def graphql` の複製が無い
- **推奨**：採用（実装を伴う、小さい）

### IB-25 上限ちょうどの example

- **いまの形**：上限の定数と、それを確かめる example を突き合わせた。発注の明細の件数（100）・品番の長さ（64）・取消の理由（200）は、上限 + 1 と上限ちょうどの両方がある。検収の明細の件数（100）は上限 + 1 だけで、在庫の調整の理由（200）はどちらも無い（分岐はサイクル 01 の探索でも未通過だった）。台帳の行の「発注の明細も同じ形」は誤りである
- **比べた形**：`guides/testing.md`「層への配分」の業務の分岐（数量の上限）に、上限 + 1 と上限ちょうどの両方を書くことを足し、2 か所の example を足す
- **合い方**：上限を誤って 1 つ下げる変更は、上限 + 1 の example では落ちない。上限ちょうどの example が落とす
- **移す費用**：検収は別々の明細を 100 件作るので、example が数秒かかる見込み。在庫の調整は 2 examples
- **効いたとする基準**：上限の定数を 1 つ下げると、上限ちょうどの example が落ちる
- **推奨**：採用（規則の変更と、小さな実装）

### IB-18 `BUNDLED WITH` を同梱の bundler へ上げる

- **いまの形**：`Gemfile.lock` の `BUNDLED WITH` は 2.5.3 で、Ruby 3.4.11 に同梱の bundler は 2.6.9 である。CI は毎回 2.5.3 を入れ直す（約 2 秒）
- **比べた形**：2.6.9 に上げる。lockfile の差分は `BUNDLED WITH` の 1 行だけだった
- **合い方**：M34 の事象（net-pop の依存が lockfile から落ちる）は、いま 2.5.3 で同じ全更新をしても再現しなかった。2.6 系がこれを防ぐという根拠は無い。上げることで得るのは、CI と本番のイメージが同梱の版をそのまま使うことである
- **移す費用**：1 行。全件・`docker build`・`bin/bundler-audit` で確かめる
- **効いたとする基準**：CI のログが同梱の版を使う。`docker build` が通る
- **推奨**：採用（実装を伴う、小さい）。次の依存の更新に入れる

## 正本の棚卸し
