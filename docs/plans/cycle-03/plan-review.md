# サイクル 03 の計画レビュー：M36・M25〜M29 への反映

この文書は、`implementation-plan.md` の M36・M25〜M29 を 2 系統の独立したレビュー（Claude と Codex）にかけ、指摘を計画に反映した記録である。M36・M25〜M29 に着手する担当者と、計画をレビューする人が読む。担当者は、計画の節が「なぜこう書いてあるか」をここで引ける。

レビューに出す前に、作者の判断（OI-71〜OI-73・OI-77・OI-78）を設計文書と計画に反映した（`248d3f5`）。初回のレビューは、その版を読んだ。2 系統の High を直した版（`9d478b3`）を Codex で読み直し（読み直し 1）、そこで残った High を直した版（`21f029d`）を Codex でもう一度読み直した（読み直し 2）。読み直し 2 で High は出なかった。

読む順は、マイルストーンごとの判定 → 指摘ごとの対応 → 指摘の根拠を確かめた結果 → 作者の判断 → 直さなかった指摘と台帳に積んだもの、である。指摘の出典は次の形で示す。

| | Claude | Codex |
|---|---|---|
| 初回 | `<マイルストーン>-<番号>`（`M25-1` など） | `P<番号>` |
| 読み直し 1・2 | — | `N<番号>` |

Codex は、初回の指摘にも `M26-1` の形の ID を振った。Claude の ID とぶつかるので、この文書では Codex の初回の指摘を `P01`〜`P09` に振り直した。対応は、M26-1→P01、M26-2→P02、M27-1→P03、M28-1→P04、M28-2→P05、M29-1→P06、M29-2→P07、M29-3→P08、M29-4→P09 である。

## 判定

| マイルストーン | 初回 Claude | 初回 Codex | 読み直し 1 Codex | 読み直し 2 Codex |
|---|---|---|---|---|
| M36 行列テストの世界の作り方と、テストの検出力の小さな穴 | Go | Go | Go | Go |
| M25 請求書の発行と受領請求書 | Conditional Go | Go | Conditional Go | Go |

| M29 大量データの取り込み | Conditional Go | No-Go | No-Go | Go |

全体の判定は、初回が Claude は Conditional Go、Codex は No-Go だった。Claude は High を 6 件挙げ、それを直せば Go とした。Codex は M26 と M29 の High を、仕様を決めてから読み直す必要があるとした。

2 系統が同じことを挙げた指摘は次の 4 つである。

- ダッシュボードの型と集計の境界が無い（Claude M26-1、Codex P02）
- M26 の完了条件にコマンドと spec のパスが無い（Claude M26-2、Codex P01）
- sandbox mode の成功の応答 200 が、応答の扱いの表に無い（Claude M28-1、Codex P05）
- `limits_concurrency` の既定の `duration`（3 分）を考えていない（Claude M29-1、Codex P07）

片方だけが挙げた High は次のとおりである。

- Claude だけ：請求書の確定の入力と結果（M25-1）、確定の競合（M25-2）
- Codex だけ：送信の一体性を確かめるテストの抜け（P04）、M29 の件数の冪等（P06）、強制終了からの復旧（P08）、CSV の入力の契約（P09）

読み直しでは、前の Critical・High の指摘が解消したかと、High 以上の新しい指摘だけで判定した。

- **読み直し 1**：前の High 11 件のうち 10 件を解消と判定した。M25-1 は、確定した請求書に結んだ明細と集計の INSERT を防がないので未解消だった。M29 には新しい High の N01（同じ取り込みの 2 つのジョブ）が出た。
- **読み直し 2**：M25-1 と N01 の 2 件を解消と判定した。新しい High 以上の指摘は無く、6 つのマイルストーンがどれも Go になった。

High が出たのは 2 回目の読み直しまでなので、3 回目には出していない。M36 から着手できる。

## 指摘の根拠を確かめた結果

指摘の根拠は、リポジトリのコードと、インストール済みの gem で確かめた。

| 根拠 | 結果 |
|---|---|
| `limits_concurrency` の既定の `duration` は 3 分（P07・M29-1） | 正しい。solid_queue 1.7.0 の `lib/solid_queue.rb` で `default_concurrency_control_period` の既定が `3.minutes` で、README「Concurrency controls」は、この期間を過ぎると待っているジョブが動きうると書く |
| 強制終了したジョブは自動で再試行されない（P08） | 正しい。solid_queue 1.7.0 の README「Jobs interrupted by non-graceful process death」は、`ProcessPrunedError` で失敗にし、意図して再試行しないと書く |
| sandbox mode の成功は 200（P05・M28-1） | Claude が SendGrid の文書の原文を引いた。手元では確かめられないので、メッセージ ID の有無と一緒に `adr/007` の未確認の事項に入れた（OI-15） |
| データの移行はマイグレーションに入れない（P03） | 正しい。`adr/001` 決定 4 |
| `pin_connection!` は入れ子を数え、`unpin_connection!` は偽を返しうる（M36 の観点 3） | 2 系統とも、activerecord 8.1.4 の `connection_pool.rb` で、計画の書き方と合うと確かめた |
| `member` で `admin` に限る操作を呼ぶ既存の spec は 3 本だけ（M25 の観点 1） | 正しい。`billing_spec.rb`・`cancellations_spec.rb`・`inspections_spec.rb` で、作るもの 3 が挙げたものと一致する |

## 作者の判断

計画レビューの前に出ていた作者の判断（2026-10-11）を、台帳で `decided` にし、反映先を結果の欄に書いた。

- **OI-71〜OI-73（業務の mutation の役割）**：役割で制限する。取消の審査の承認と却下・受注側の取消・取消依頼・検収・請求条件の設定・締め・下書きの破棄・請求書の確定を `admin` に限る。表は `context-map.md`「自社の中の役割」と `graphql-schema.md`「役割による制限」に置いた。既存の規則を直す実装は M25 に入れた。M25 は確定で同じ形の規則を初めから作るからである。サイクル 03 は上限の 6 つに達しているので、新しいマイルストーンは作らない。M36 は業務の振る舞いを変えないので入れない。
- **OI-77（未来の締め日）**：許す。確定も、締め日を過ぎるのを待たない。`data-model.md`「請求（`billing`）」と M25 に書いた。
- **OI-78（SDL の一覧の `filter`）**：文書から外す。画面の検索の項目が決まったら、入力型を定義して足す作業を M33 に書いた。

あわせて、認可の 3 段（RLS・scope・規則）の分担を、`graphql-schema.md` の冒頭と「認可」の節、`showcase.md`、`README.md` に表で示した。

## 直さなかった指摘と、台帳に積んだもの

- 取りまとめ役が決めた業務の振る舞いは、`judgment` で台帳に積んだ。作者の確認を待つが、実装は計画のとおりに進める。
  - OI-80：単価の改定と取り込みを、役割を問わない操作に入れた
  - OI-81：ダッシュボードの集計の境界
  - OI-82：取り込みの CSV
  - OI-83：`new_sales_order` の宛先
  - OI-84：請求書の確定の入力と結果、確定した請求書を変えない仕組み
- 違和感は改善の候補に移した。
  - Codex：M36 の撤退先の test-prof も同じ `pin_connection!` に依存する（IB-28）
  - Claude：行列の役割の検査が `admin` に限る読み取りに届かない（IB-29）
  - Claude のもう 1 つの違和感（`member` を足した後の行列の時間）は、M25 の「文書に残すこと」に入れた
- M36 の `pin_connection!` に渡す `lock_thread` の値（Claude の Low）は、計画に書いていない。M36 の実装で決め、`guides/testing.md` に書く。
