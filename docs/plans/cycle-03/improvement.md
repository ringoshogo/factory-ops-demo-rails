## 調べたテーマ

### IB-35 scope の呼び忘れを、RLS が隠さない形で検出する

- **いまの形**：認可は RLS・scope・規則の 3 段で、scope は「RLS に任せない」（`graphql-schema.md`「認可」）。RLS が守る条件と scope が守る条件は、自社の行については同じである。表の行列は生 SQL で RLS だけを確かめる。入口の行列と単体の spec は、RLS が効いたアプリのロールで動くので、相手から読む経路の無い 34 の表では、公開 API の scope を外しても他社の行が RLS に隠れ、結果が変わらない。scope を確かめているのは、経路のある 6 つの表（品目・単価・取引関係・権限付与・出荷・出荷明細）だけである
- **比べた形**：
  - (a) テストの DB にだけ、設定の値（`app.matrix_cross_read`）が `on` のときだけ全行を読ませる SELECT のポリシーを、テナントの表ごとに足す。入口の行列を、その値を `on` にして 2 回目に流す。RLS の SELECT が開いても、scope と規則が正しければ期待値は同じで、scope を外した入口だけが他社の行を返して落ちる。書き込みのポリシーは変えないので「何も書かない」の確かめはそのまま効く
  - (b) 公開 API の構文木で、テナントの表のモデルを引く呼び出しが `Scope.*` か所有の条件を通るかを照らす。サブクエリで絞る形（`where(sales_order_id: Scope....select(:id))`）があり、データの流れを構文木で追うので外れが多い
  - (c) テストの間だけ、アプリのロールに `BYPASSRLS` の別のロールへの `SET ROLE` を許す。ロールはクラスタ全体のものなので、開発の DB でもアプリのロールが RLS を外せるようになり、`spec/db/tenant_enforcement_spec.rb` が守る前提を崩す
- **計測**：(a) の試作（テストの DB にポリシーを足し、アプリのロールの設定の値を変えて入口の行列を流す）は、この探索では流していない。共有のテストの DB とロールの設定を変える操作を、実行の環境が止めた。採用したら、マイルストーンの中で別名のテスト DB で測る
- **合い方**：(a) は入口の行列の期待値をそのまま使うので、入口ごとの example を足さずに全入口に効く。ポリシーは spec の補助が所有ロールの接続で、そのファイルの `before(:context)` で足し、`after(:context)` で消す。`structure.sql` と本番には載らない。`spec/db/tenant_enforcement_spec.rb`・`spec/db/tenant_table_spec.rb` はポリシーを列挙するので、同じプロセスで消し忘れると落ちる（消し忘れの検出になる）。GraphQL を通らない公開 API（通知の宛先・再登録・移行。OI-118）は入口の行列に出ないので、(a) の外に残る
- **移す費用**：補助に 30 行ほど、入口の行列のファイルを 1 つ足す。入口の行列は約 3 秒なので、2 回目の時間は小さい
- **効いたとする基準**：経路の無い表の公開 API（受注の一覧・在庫の一覧など）から scope を外すと、2 回目の入口の行列が落ちる。scope を外さない状態で 2 回目が 0 failures（落ちたら、いまの scope の抜けとして直す）
- **推奨**：採用（実装を伴う）。(a) にする

### IB-02 テストの基盤の壊し方を spec にする（調べ直し）

- **見送りの理由との差分**：見送りの理由は、表が新しく防ぐ事象が無かったこと（10 件はガードを足し済み）と、効いたとする基準を測れないことだった。サイクル 03 の 3 件（M36 X2 後始末のガードの読み込み、M28 F3 公開鍵の復元、M26 X1 一覧の確かめ）は、どれもそのマイルストーンで新しく足した基盤で、足した時点では表に行が無い。既存の基盤の壊し方を表にして繰り返し流しても、新しい基盤のガードの抜けは捕まえない。3 件とも実装レビューの観点 4 が捕まえた
- **推奨**：見送り（理由は変わらない）。調べ直す条件を、実装レビューより後（逸脱検査か作者のレビュー）で、基盤を壊しても落ちないことが見つかったときに変える

### IB-29 行列テストの役割の検査を、`admin` に限る読み取りにも広げる

- **いまの形**：入口の行列は、mutation の行に許す役割（`role:`）を必ず持たせ、`admin` の行を `member` でも呼ぶ。読み取りの行は `role:` を持てない（持つと落ちる）。`admin` に限る読み取りは `viewer.auditLogs`（規則 `Platform::AuditLogPolicy#index?`）と `viewer.partnerCode`（`member` には空）の 2 つで、`spec/requests/audit_spec.rb` などの個別の example だけが確かめる
- **比べた形**：読み取りの行にも `role:` を許し、`admin` の行を `member` でも呼んで `FORBIDDEN`（`partnerCode` は空）を確かめる。読み取りの `role:` の無い行は、どのペルソナの `member` でも `admin` と同じ値を返すことを確かめる
- **合い方**：mutation の行と同じ形で、役割の表（`graphql-schema.md`「役割による制限」）と行列の対応が 1 か所でそろう。規則に誤って `user.admin?` を足した読み取りも落ちる
- **移す費用**：期待値の 2 行と、行列の分岐を数行。読み取りの全行を `member` でも呼ぶので、入口の行列の example が読み取りの行の数だけ増える（数秒）
- **効いたとする基準**：`AuditLogPolicy#index?` から `admin?` を外すと、入口の行列が落ちる。受注の一覧の規則に `admin?` を足すと、入口の行列が落ちる
- **推奨**：採用（実装を伴う、小さい）。IB-35 と同じマイルストーンに入れる
