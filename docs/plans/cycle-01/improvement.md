## モード

## 調べたテーマ

### IB-02 テストの基盤の壊し方の表を spec にする

- **いまの形**：実装者が基盤を手で壊して落ちることを確かめ、証跡に書く。基盤を足したらガードの example を足すことを、再発防止で `dev-cycle.md`「テストから書く」に足した。どちらも人が覚えて行う手順で、基盤が後から変わったときに繰り返されない
- **比べた形**：(1) ミューテーションテスト（mutant）。Ruby 3.2〜4.0・Rails 7.2〜8.1・rspec に対応し、公開している OSS は無料で使える。ただし、10 件のうち 6 件は `spec/support` と `spec/rails_helper.rb` にあり、mutant が書き換える範囲の外である。当たりうるのは 2 件ほど（Cop の分岐と、ジョブの文脈の戻し方）。同じ DB への 2 つの接続・RLS・トランザクションを使わない並行の spec があり、ワーカーごとに DB を写す設定も要る。(2) 壊し方の表を spec にする。基盤ごとに「壊し方（stub か環境変数でガードを外す）→ 落ちるべき example」の行を持ち、メタの spec が行ごとに子のプロセスで rspec を流して、失敗することを確かめる
- **合い方**：(2) は、いまの「手で壊して証跡に書く」をそのまま機械で繰り返す形で、10 件すべてに当てられる。`spec/bin` が子のプロセスで検査を流す形がすでにある
- **移す費用**：行ごとに壊し方を書く手間。1 行あたり数秒（rspec の起動が約 1.5 秒）。基盤の側に、ガードを外すための差し込み口（環境変数か stub できる 1 か所）が要る
- **効いたとする基準**：サイクル 01 の 10 件の壊し方を表に戻すと、全件が落ちる。次のサイクルで「基盤を壊しても落ちない」指摘が 10 件から 3 件以下になる
- **推奨**：採用（実装を伴う）。mutant は見送る

### IB-01 分岐の網羅率を CI で示す

- **いまの形**：確かめる example が無いことは、実装レビューの観点 2・4 で捕まえる。サイクル 01 の 4 件はどれもレビューで捕まった
- **比べた形**：Ruby の標準の `Coverage`（分岐を数える）を、SimpleCov（全体の割合）か undercover（PR が足した分岐だけを見る）で使う。どちらも MIT
- **計測した結果**：全件を分岐の計測付きで 1 回流した。分岐 382 のうち 39 が未通過（通過率 89.8%）、`packs/` だけなら 247 のうち 22。計測ありは素の実行より約 30% 遅い（3 分 58 秒 → 5 分 10 秒。eager_load と bootsnap を切った分を含む）。子のプロセスで流す検査は数えていない
- **合い方**：rspec だけで動き、DB を使う spec とも衝突しない。CI はすでに eager_load で流している。4 件のうち、M20 X1（互換の判定）と M18 C7（ログイン）の分岐はいまも未通過で拾えた。M19 X3 は DB の NOT NULL で止める経路で、Ruby の分岐が無いので拾えない。網羅率は「実行したか」だけを見て「確かめたか」は見ないので、レビューの代わりにはならない
- **移す費用**：gem を 1 つ足し、`spec/spec_helper.rb` の先頭で計測を始める。全体の下限は割合が機能の種類で揺れるので置かず、PR が足した分岐が未通過なら警告する形（undercover）にする
- **効いたとする基準**：指摘を直す前の commit で、サイクル 01 の 4 件のうち 2 件が未通過として出る。次のサイクルで「確かめる example が無い」指摘が 4 件から 1 件以下になる
- **推奨**：採用（実装を伴う）。最初は警告にとどめ、失敗にはしない

### IB-04 Ruby を上げる

- **いまの形**：Ruby 3.3.3。`.ruby-version` と Dockerfile が一致している。3.3 系は 2026-04 から security の保守だけで、2027-03 に終わる。最新の patch から 9 つ遅れている
- **比べた形**：(1) 3.3 系の最新の patch に上げる。(2) 3.4 か 4.0 に上げる
- **合い方**：Rails 8.1・graphql-ruby・bullet・solid_queue・packwerk・mutant（参考）は 3.4 に対応する。(1) は互換の問題がほぼ無い。(2) は文字列の凍結の警告や `Hash#inspect` の表記の変化で、文字列を比べる spec が落ちうる
- **移す費用**：(1) は `.ruby-version` と Dockerfile と CI の版を変え、全件を流すだけ。(2) は加えて、警告と表記の違いの修正
- **効いたとする基準**：全件が通り、警告が増えない。3.3 系の保守が終わる前に、保守の続く版で動いている
- **推奨**：採用。(1) をマイルストーンに属さない依存の更新として先に行い、(2) は保守が終わる前のマイルストーンに起こす

### IB-03 使っていない Rails の部品を外す

- **いまの形**：`config/application.rb` が Action Mailbox・Action Text・Active Storage・Action Cable を読み込む。どれも表が無く、使う箇所も無い。kamal（デプロイの設定が無い）と image_processing（と Dockerfile の libvips）も使っていない。thruster は Dockerfile の起動の命令が使うので外さない。Action Mailer は、通知（`adr/007`）でメールをどう送るかが決まるまで残す
- **比べた形**：(1) 外す。(2) 残して、`guides/config.md`「使っていない機能の設定」に使っていないと書く
- **合い方**：(1) は読み込む部品が減り、AI が Active Storage などを使える前提で設計する誤りを止める。計画は取り込みのファイルで Active Storage を避ける判断をしている。Dependabot の #17（image_processing のメジャー更新）も一緒に閉じられる
- **移す費用**：`require` の 4 行と gem 2 つ、Dockerfile の libvips、使っていない雛形の削除。全件と本番の起動（子のプロセスの spec）で確かめる
- **効いたとする基準**：全件が通り、本番の環境が起動する。読み込む部品と `guides/config.md` の記述が一致する
- **推奨**：採用（実装を伴う、小さい）

### IB-05 スキーマの比較器を使い続けるか

- **いまの形**：graphql-schema_comparator 1.2.1 が新旧の SDL の差分を変更のクラスで返し、`lib/schema_compat.rb` が自前の規則で通すか落とすかを決める。規則は比較器の重大度を、削除・既定値・非推奨のフィールドの引数の 3 方向で上書きしている。比較器は 2023-10 から更新が無く、graphql < 3.0 に縛る
- **比べた形**：(1) 使い続ける。(2) 差分の列挙も自前にする（`GraphQL::Schema` の反射で、型・フィールド・引数・入力項目・enum の値・既定値の増減を数える）。(3) Node の graphql-inspector を CI でだけ使う
- **合い方**：判定はすでに自前の規則の表で、比較器に頼るのは差分の列挙と変更のクラス名だけである。比較器の限界（`@oneOf` の追加と `repeatable` を外す変更を出さない）は `graphql-schema.md` に書いてある
- **移す費用**：(2) は比較器が出す変更のクラスの多く（20 余り）を自前で書き直し、例外の一覧の書式（クラス名）も変わる。いま壊れていないものを、大きな費用で置き換えることになる
- **効いたとする基準**：— （移さないので置かない）
- **推奨**：見送り。graphql-ruby の 3 系が出て比較器が動かなくなったら調べ直す（M20 の計画の判断の裏返る条件と同じ）
