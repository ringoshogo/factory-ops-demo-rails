# サイクル 10 の計画レビュー：M57 と、M54・M33・M41 の残り

この文書は、`implementation-plan.md` の M57 と M54 の「残り（サイクル 10）」を 2 系統の独立したレビュー（Claude と Codex）にかけ、指摘を計画に反映した記録である。M57 から着手する担当者と、計画をレビューする人が読む。担当者は、計画の節が「なぜこう書いてあるか」をここで引ける。

サイクル 10 に入るのは、サイクル 09 の改善の探索で起こした M57 と、作者の判断 OI-226 の (a)（写しを残す）で作る M54 の残りと、作者を待つ M33 の残り（OI-177）と M41 の残り（OI-196）である。レビューの前に、取りまとめ役の指示で、作者の判断 OI-223 の (a) の注記を計画の冒頭に置いた（`85ef2da`）。

初回のレビューは `2a070ba` を読んだ。この版は、M57 の作るもの 1 の形と作るもの 3 の分け方を取りまとめ役が決めて節に書いた後の版である（下の「M57 で決めたこと」）。依頼には読む版の commit を書き、`git show 2a070ba:<パス>` で読ませた。2 系統とも全体は Conditional Go で、High は Claude が 2 件、Codex が 1 件だった。名指しの High を直したので、`guides/dev-cycle.md`「判定の形」の Conditional Go の扱いどおり、読み直しには出していない。直した版は `8b274d1` である。Claude のサブエージェントは最終報告を返さずに終わり、依頼に書かせた結果のファイルから読んだ。Codex は、指定の commit を読み、DB を使わない Ruby の小さな実行（いまの 6 つの期待を写して 3 つの迂回を流す、`after(:suite)` の例外で終了コードが 1 になる）を行った。どちらも DB を使う spec と全件は流していない。

読む順は、マイルストーンの分け方 → M57 で決めたこと → 判定 → 指摘ごとの対応 → 作者に渡すもの → 直さなかった指摘と台帳に積んだもの → 計画の数の空き、である。指摘の出典は `Claude M57-1`・`Codex M57-1` の形で示す。

## マイルストーンの分け方

| マイルストーン | 中身 | 分けた理由 |
|---|---|---|
| M57 CI とテストの守りの照らし方を直す | `publish` の `if:` を 1 つの式に一致させて照らす（IB-144）、呼ばれない公開 API を全件で落とす（IB-150）、内部の一覧と GraphQL の enum の一致（IB-145） | サイクル 09 の改善の探索で採用した 3 つで、どれも CI とテストの守りの照らし方である。同じ `spec/platform/ci_checks_spec.rb` と `guides/config.md`「CI の工程」に触れるので 1 つにした |
| M54 の残り | ADR 011 の写しの理由と、経緯で書いたコメント 3 か所と文書 2 か所の直し（OI-226） | 作者の答え (a) で作るものが決まった。振る舞いを変えない |
| M33 の残り | 作者の画面の指摘を待つ OI-177 | 作るものは無い |
| M41 の残り | 作者の実機の手順（OI-196） | 作るものは無い |

実装の順は M57 → M54 の残りである。M57 は、改善の探索で採用した変更をサイクルの最初に置く規則（`guides/dev-cycle.md`「全体の流れ」）による。2 つは `showcase.md` に触れるが、M57 はテーマ 8・10、M54 の残りはテーマ 3 で節が重ならず、同じ落ちるテストも当てにしない（2 系統の「順序と依存」）。M54 の残りは M57 のブランチから切る。

## M57 で決めたこと

### 作るもの 1：一致の形にした（IB-144）

改善の探索は、`publish` の `if:` を照らす形を「許す形を補助で照らす」か「式をちょうど一致させる」かの 2 つから、計画レビューで決めるとした。取りまとめ役は一致の形に決め、計画の「判断」に書いた（OI-229）。

| | 許す形を補助で照らす | 1 つの式に一致させる（採った） |
|---|---|---|
| 照らすもの | `${{ }}`・文字列・外側の括弧をそろえ、深さ 0 に `\|\|` が無く、深さ 0 の `&&` の項の 1 つがちょうど `success()` | 空白と `${{ }}` をそろえた値が `success() && github.event_name == 'push'` |
| 補助 | 約 25 行の構文の補助 | そろえる 3 つの処理と比べ |
| 閉じ方 | 補助の条件ごと。条件を 1 つ落とすと穴が戻る（改善の探索の調べが深さ 0 の論理和を落とし、裁定の 2 系統が High で挙げた） | 構文を解かず、迂回の種類を数えずに閉じる |
| 式を変える人の手間 | `success()` と論理積でつながる書き換えなら直さなくてよい | spec の文字列も直し、`needs` が落ちたときに偽になるかを確かめて証跡に書く |

`publish` の `if:` は M57 の範囲外で、変える予定が無いので、一致の形の費用は小さい。式を変えるたびに確かめを求めることは、守りたいことそのものである。2 系統とも、この決め方を妥当とした。Codex は、いまの 6 つの期待を `2a070ba` から取り出して流し、3 つの迂回がどれも通ることを確かめ、RED の手順が成り立つとした。

### 作るもの 3：集合だけを比べ、19 個を分けた（IB-145）

順は比べない。GraphQL の enum の宣言の順を並べ方に使う読み手が無く、進みの並べ方は `PurchaseOrderTimeline::RANKS`、状況で並べる順は各状況の `SORT_ORDER` が持ち、それぞれの spec が確かめるからである（2 系統とも妥当とした）。

比べる相手は、値を作るか受け付けるコードが読む一覧か、値を作る式との一致をパッケージの spec が確かめる一覧に限る。初回の版は「値を作る側が読む一覧」と書いたが、取り込みの種類の `Imports::Import::KINDS` は使い手が無く、状況の `ALL` は状況の式が読まない（Claude M57-2・Codex M57-3）。並べる向きは `Page::Sort.of` が独立した配列で受け付けを限っていた（Codex M57-4）。直した後の分け方は計画の作るもの 3 にあり、比べる 10 個と、理由付きで比べない 9 個である（OI-230）。

## 作者に渡すもの

答えで作るものが変わる問いは無い。確かめるだけの判断は、`judgment` の 3 行である。

- OI-229：M57 の作るもの 1 を一致の形にした
- OI-230：M57 の作るもの 3 で、順を比べず、19 個を比べる 10 個と比べない 9 個に分け、一覧を公開 API の別名で出す
- OI-231：M54 の残りで、ADR 011 の直す 3 か所と、見直す条件に足す条件

M33 の残り（OI-177）と M41 の残り（OI-196）は、作者の指摘と実機の結果を待つ。

## 直さなかった指摘と、台帳に積んだもの

Critical と High と Medium と Low は、すべて計画の節で直した。直さなかった指摘は無い。

違和感は、Codex が「なし」、Claude が 3 つだった。

- 1（撤退コストの書き方が小さすぎる）：計画の「判断」の撤退コストを、補助を書き、補助の処理を 1 つずつ外して確かめ直すことに直した。直したので改善の候補に移さない
- 2（冒頭の注記が、終えた節の「残り」の段落を直してよいかを書いていない）：注記に、次のサイクルへ移した「残り」の段落は、片付けるまで計画レビューで直すと 1 文足した。直したので移さない
- 3（作るもの 3 の「計画レビューの時点（`aba5836`）」と、レビューに出した版 `2a070ba` の食い違い）：2 つの版で enum の型は同じ 19 個で、`aba5836` は計画レビューを始めた main の先端なので、そのままにした。結果は変わらないので移さない

## 計画の数の空き

サイクル 10 は M57・M54 の残り・M33 の残り・M41 の残りの 4 つで、上限の 6 つまで 2 つ空いている。足すかは作者の判断で、取りまとめ役は足していない。台帳と改善の候補から挙がる候補は次の 2 つで、どちらも改善の探索で判定していない `未着手` の行である。

- IB-151：列を消した後の `ignored_columns`（`Fulfillment::ShipmentRequest` の `cancelled_at`）を、いつ外すかをどこに書くか
- IB-152：出荷指示の取消のロックの順を、ADR 012 と `data-model.md` のロックの順の文に書くか

`open` の残件で、引当先が M33・M41 のほかのものは無い。
