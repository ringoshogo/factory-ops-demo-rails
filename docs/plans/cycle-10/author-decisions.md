# サイクル 10 の終わりに作者が決めること

サイクル 10 のサイクル末の PR をマージする作者が、判断の要る点を 1 件ずつ決めるために読む。取りまとめ役が 1 件ずつ問い、決まった答えを台帳（`open-items.md`）の行に書いて、行の ID で担当に渡す（`guides/dev-cycle.md`「残件の台帳」）。

各項目には、何が問題か、流用元（`factory-ops-demo`）ではどうしているか、選べる形ごとの作るものと費用、見せ場になるか、既定とおすすめを書いた。流用元の作りは、`factory-ops-demo` の実物のファイルと行を開いて確かめた。費用は、このブランチのコードと計画と証跡を読み、変えるファイルを数えて確かめた。流して確かめていないものは、そう書いた。

答え方：項目ごとに「既定のまま」か、選ぶ形の記号を書く。全部既定でよければ「全部既定で」。

## 4. `publish` の `if:` を 1 つの式に一致させて照らす（OI-229）

- **何が問題か**：M52 で 3 回続けて High が出た `publish` の `if:` の守りを、M57 で、そろえた値が `success() && github.event_name == 'push'` にちょうど一致する形で照らすことにした。許す形を構文の補助で照らす形と比べ、迂回の種類を数えずに閉じる一致の形を選んだ。費用は、式を変える人が spec の文字列も直し、`needs` が落ちたときに偽になることを確かめて証跡に書くことである。裏返る条件は、`publish` の `if:` を繰り返し変えるようになったときである
- **流用元では**：別のジョブを持たない。テストと同じジョブの後ろのステップに `if: github.event_name == 'push'` を付けてイメージを置き（`.github/workflows/ci.yml` 59〜75 行）、前のステップが落ちればステップの既定の条件で止まる。`if:` を照らす検査は無い
- **選べる形**：既定。(a) 許す形を補助で照らす：`spec/platform/ci_checks_spec.rb` に約 25 行の構文の補助（`${{ }}` と文字列と外側の括弧をそろえ、括弧の深さ 0 に `||` が無く、深さ 0 の `&&` の項の 1 つがちょうど `success()`）を書き、補助の処理を 1 つずつ外して式の表の行が落ちることを確かめ直す（サイクル 09 の改善の探索の試作で 134 行 → 162 行、壊し方 5 行）。`guides/config.md`「CI の工程」の文を許す形の 1 文にする（小さい）

## 5. enum と公開 API の一覧の比べ方（OI-230・OI-235）

- **何が問題か**：M57 で、スキーマのすべての GraphQL の enum の型を、公開 API の一覧と比べるか、理由付きで比べない表に載せる spec（`spec/graphql/enum_values_spec.rb`）を足した。決めたことは 3 つである。(1) 値の集合だけを比べ、順は比べない。並べ方は各一覧と `SORT_ORDER` が持ち、enum の宣言の順を読む読み手が無いからである。(2) 19 個の型を、比べる 11 個と比べない 8 個に分けた。比べない 8 個は、並べ替えの列の 4 個（列の表が操作者から作る private のメソッドで定数が無い）、DB の CHECK 制約にだけ値がある 2 個、導出の分岐にだけ値がある 2 個である。計画は比べる 10 個としたが、実装で在庫の並べ替えの列が公開 API の定数を持つと分かり、比べる側に移した（OI-235）。(3) `app/models/` の一覧は、公開 API に同じオブジェクトを指す定数の別名を置いて出す
- **流用元では**：無い。流用元は Go の REST の API で、GraphQL も、一覧と API の値の一致を確かめる検査も無い（`backend`・`frontend/lib` を `graphql` で検索して 0 件）
- **選べる形**

  | 形 | 作るもの | 費用 | 見せ場 |
  |---|---|---|---|
  | 既定 | 無し | 無し | 見せどころのテーマ 8 の表に、enum の一致の行がある |
  | (a) 順も比べる | spec の集合の比べを配列の比べにする | spec 1 つ。いまの 11 組はどれも順まで一致することを、このサイクル末に手元で流して確かめた（直す一覧は 0）（小さい） | 変わらない。enum の宣言の順を一覧の順に縛るだけになる |
  | (b) 並べ替えの列の 4 個も比べる | 品目・発注・受注・出荷依頼の公開 API の列の表を、操作者に依らない定数の列の名前の一覧と、操作者から作る式に分け、定数を比べる組に足す | 公開 API 4 つと spec 1 つ、比べない表の 4 行を消す。列の式の組み立ては変えない（マイルストーン 1 つ、中くらい） | 「すべての enum を比べる」と言える。いまも enum にだけある列は、その列で並べたときに実行の時に拒まれる |
  | (c) 一覧を `app/public/` へ移す | 5 つの一覧を公開 API に移し、`app/models/` の読み手を直す | 4 つのパッケージ（購買の 2 つ・受注・出荷・在庫）（小さい〜中くらい） | 変わらない |

- **おすすめ**：既定のまま。(b) は見せ場が増えるが、並べ替えの列の取り違えは実行の時に拒まれ、データを壊さない

## 6. ADR 011 の直した 4 か所と、見直す条件に足した条件（OI-231）

- **何が問題か**：作者の判断 OI-226 の (a)（写しを残す）で、ADR 011 にいま写しを持つ理由を書いた。計画は「理由を書く」とだけ書いたので、計画レビューで直す場所を決め（決定 2・代替案 D・見直す条件）、実装で「ステータス」の裏返る条件の文にも同じ条件を足した。見直す条件に足したのは「写しを守る作り直しのタスクか一致の spec を外すとき」である。実装レビューの Claude は、写しを残したまま守りだけを外す場面は想像しにくいと違和感を書いた
- **流用元では**：写さない。出荷指示の一覧は、受注の表を結んで受注番号を引く（`backend/internal/store/shipping_instructions.go` 303〜312 行）
- **選べる形**：既定。(a) 足した条件を消し、見直す条件を受注番号を後から変える入口だけに戻す：ADR 011 の「ステータス」と「見直す条件」の 2 文（小さい）
- **見せ場**：どちらも見せどころのテーマ 3 の写しの箇条は変わらない
- **おすすめ**：既定のまま。条件は、写しを守るものを外すときに ADR 011 を開かせる目印で、費用が無い

## 7. 出荷指示の取消のロックの順（OI-233）

- **何が問題か**：作者は IB-152 で、ADR 012 決定 4 と `data-model.md`「取消と出荷の競合を止める場所」に、出荷指示の取消の順（受注をロックせず、出荷依頼 → 出荷指示）とデッドロックしない理由を書くと決めた。担当は、同じ文書の「出荷（`fulfillment`）」の「出荷指示の取消は、受注を読まずに出荷依頼の行だけをロックする。」が、出荷指示もロックするいまのコードと食い違うので、3 か所目として直した。ロックの箇所の一覧の spec（`spec/db/lock_sites_spec.rb`）は、足した文と食い違わないので変えていない
- **流用元では**：取消でも受注を先にロックする。出荷指示の取消は、受注の状況が「出荷指示済」かを受注の行ロックの後に読み直す（`backend/internal/store/shipping_instructions.go` 181〜196 行、`lockOrderWithStatus` は `orders.go` 292 行）。流用元は受注の状況だけで取消せるかを決めるので、受注を読む必要がある
- **選べる形**：既定。(a) 流用元と同じく、取消でも受注を先にロックする：`packs/fulfillment/app/public/fulfillment/instructions.rb` の `cancel`、ロックの順の example と競合テスト、ADR 012 決定 4 と `data-model.md` の 3 か所（マイルストーン 1 つ、中くらい）。取消は受注の行ロックで受注の取消・計上とも直列になるが、いまも出荷依頼の行ロックで計上と直列で、受注の取消とは同じ行を取らないので、防げる競合は増えない
- **見せ場**：既定は、見せどころのテーマ 4 の「ロックの順」に、計上の順の部分列としてデッドロックしない例が載る（サイクル 10 の知見の収穫）
- **おすすめ**：既定のまま
