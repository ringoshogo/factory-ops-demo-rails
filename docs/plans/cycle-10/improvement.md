## 調べたテーマ

### 1. IB-157 spec を乱順で流すか

- **いまの形**：`spec/spec_helper.rb` の `config.order = :random` と `Kernel.srand config.seed` は、rspec の生成器が置いた `=begin`〜`=end` の注釈の中にあり、効いていない。spec はファイルと example の定義の順で流れ、`--seed` を渡したときだけ乱順になる。M54 の残りで書いた `guides/config.md` の規則 3 は「どの spec が落ちるかは `config.order = :random` の順で変わる」と書き、計画レビュー（M54R-1）も同じ前提で直した。前提は事実と違ったので、このサイクル末に規則 3 の文を事実に合わせた（下の「この調べで直したもの」）
- **手元での確かめ**：全件を `--seed 4242` で流すと 3197 examples, 14 failures で、どれも `spec/graphql/audit_examples_spec.rb` だった。このファイルだけを `--seed` 1・2・999・4242 で流すと 6・14・10・14 failures、`--seed` なしでは 0 failures だった。原因は、見本の example（「action の文字列があっても…」）が、ファイルの上で全 spec を読んだ外側のローカル変数 `sources` に見本の 2 ファイルを代入していたことで、この example が先に流れると、後に流れる action ごとの example が見本の 2 ファイルだけを読んで落ちる。定義の順ではこの example が最後なので、いまの CI では表に出ない。変数の名前を分けて直し、4 つの seed で 0 failures を確かめた後、全件を `--seed` 11・22・33 で流し、どれも 3197 examples, 0 failures だった
- **比べた形**：(a) `config.order = :random` と `Kernel.srand config.seed` を注釈の外に出す。(b) いまのまま定義の順で流す。(c) CI だけ `--order random` を渡す
- **合い方**：(a) は、順への依存を毎回の CI で別の順に当てて見つける。落ちたときは rspec が seed を出すので、`--seed` で再現できる。`dev-cycle.md`「テストから書く」の「1 回だけ落ちたテストを、再実行で緑にして流さない」の手順がそのまま使える。(b) は、今回のような外側の変数への代入や、規則 3 のような順で落ちる形を、定義の順に隠したまま残す。(c) は、手元の `bin/ci` と CI で順の扱いが分かれ、手元で通って CI で落ちる形を足す
- **移す費用**：`spec/spec_helper.rb` の 2 行を注釈の外に出す。`guides/config.md` の規則 3 の文を乱順に合わせ、`guides/testing.md` に、順への依存で落ちたら seed で再現して直すことを 1 文書く。入れたときに直す spec は、このサイクル末に直した `audit_examples_spec.rb` のほかに、4 つの seed では見つかっていない
- **効いたとする基準**：(1) `spec/spec_helper.rb` が `--seed` なしでも乱順で流し、出力に seed を出す。(2) 入れたマイルストーンの `bin/ci` と CI で全件が通る。(3) 入れた後のサイクルで、順への依存で落ちた spec が出たら、seed で再現して直したことが証跡にある
- **推奨**：`採用`（実装を伴う変更）。行き先は、サイクル 11 の最初の小さいマイルストーン

### 2. IB-154 移行の spec の後始末で列の読み込みを戻し、`unit_price` の無視を外す

- **いまの形**：`Sales::Item` は `unit_price` を `ignored_columns` に残し、規則 3 の唯一の当てはまりである。移行の spec（`packs/sales/spec/public/sales/item_prices_backfill_spec.rb`）は、列を足し直して戻す `after` で `Sales::Item` の列の読み込みを戻さない。M54 の残りで足した example は、無視があれば列を読ませてから消しても品目を作れることを確かめる
- **手元での試作**：移行の spec の `after` の最後に `Sales::Item.reset_column_information` を足し、`item.rb` から `ignored_columns` の行を消した。`packs/sales/spec` を `--seed` 1・2・3 で流すと、どれも 187 examples, 1 failure で、落ちたのは無視を確かめる M54 の残りの example だけだった。全件を `--seed 4242` で流すと、その example と、テーマ 1 の `audit_examples_spec.rb` だけが落ちた。試作は複製から戻した
- **合い方**：後始末で読み込みを戻すと、列を足し直した example の外ではモデルが列を持たないので、無視が無くても後の spec の INSERT は落ちない。列を足し直した example の中でモデルが列を読み、同じ example で列を消して品目を作ると落ちるので（M54 の残りの example がその形）、その example は、後始末を確かめる形に替える。ただし `after` は example の後に流れるので、同じ example の中では後始末の後の列を確かめられない。内側のグループを流す補助（`run_inner_group`。前例：`spec/platform/tenant_example_spec.rb`）で内側の example を流し、外側で列を見る形を計画で決める（裁定の Claude A4 で直した）。規則 3 は「spec が消した列をテストの DB に足し直すときは、後始末でそのモデルの列の読み込みを戻す」に変わり、無視を残す例外が消える
- **移す費用**：spec 1 つ（後始末の 1 行、example 1 つの書き直し）、`item.rb`（コメント 2 行と 1 行）、`guides/config.md` の規則 3、見せどころのテーマ 10 の箇条の 1 文
- **効いたとする基準**：(1) `git grep -n 'ignored_columns' -- packs` が 0 件。(2) 後始末の `reset_column_information` を外すと、書き直した example が落ちる。(3) 全件を 3 つの seed で流して通る
- **推奨**：`採用`（実装を伴う変更）。テーマ 1 と同じマイルストーンに入れる。どちらも spec の順と後始末に関わり、同じ規則 3 の文を直す

### 3. IB-155 公開 API の定数の別名の値の配列を凍結する

- **いまの形**：`Inventory::Stocks::MOVEMENT_EFFECTS` は `Stock::EFFECTS` と同じ Hash で、Hash は凍結しているが、値の配列は凍結していない
- **数えたこと**：公開 API（`packs/*/app/public/`）のモジュールが持つ、モジュールでない定数 31 個を `Ractor.shareable?` で調べると、14 個が深く凍結されていなかった（Hash や配列の中の値のほか、`ActiveSupport::Duration`・`Arel::Table`・`Thread::Mutex` など）。`MOVEMENT_EFFECTS` はその 1 つである
- **合い方**：比べた形は、(a) `Stock::EFFECTS` の値の 5 つの配列だけを凍結する（裁定の Codex A2 で足した。1 行の直しで、要素を変えると `FrozenError` になる）、(b) 公開 API の定数をすべて深く凍結する規則とガード、(c) いまのまま、である。(b) は `Ractor.shareable?` を物差しにすると、凍結しても共有できない値（`Thread::Mutex` など）を扱えず、物差しから決め直すことになる（調査の版は「`Mutex` は凍結できない」と書いたが、凍結はできて共有できないだけである。Codex A2 で直した）。(a) は費用が小さいが、同じ形の値を持つほかの定数は残る。定数を書き換えて振る舞いが変わった不具合は、どの証跡にも出ていない
- **推奨**：`見送り`。調べ直す条件：公開 API の定数を書き換えて振る舞いが変わった不具合が出たとき、または Ractor を使うとき

### 4. IB-156 使い手の無い `Imports::Import::KINDS` を消す

- **いまの形**：`packs/imports/app/models/imports/import.rb` の `KINDS = %w[items stocks].freeze` は、`git grep` で定義のほかに読み手が無い。取り込みの種類は `Imports::CsvFormat::COLUMNS` のキーが持ち、M57 の一致の spec もそれと比べる
- **合い方**：読む人が使い手の無い一覧を正と取り、そこに値を足しても何も変わらない。消しても、値を限る守りは減らない
- **移す費用**：1 行を消す。spec は変えない
- **効いたとする基準**：定義が消え、全件が通る
- **推奨**：`採用`（実装を伴う変更）。費用が 1 行なので、テーマ 1 と同じマイルストーンに入れる

## 裁定

2 系統のレビュアー（Codex と、取りまとめ役とも実装者とも別の Claude）に、この文書の調査の版（`dcdb3ce`）と台帳とリポジトリを渡して裁定を頼んだ。依頼には読む版の commit を書き、その版を展開したディレクトリだけを読ませた。同じ依頼で、サイクル末のブランチの変更の実装レビューも頼んだ（下の「サイクル末の変更の実装レビュー」）。Codex は Ruby 3.4.11 で、検査の lambda を実在の計画と証跡に当ててメモリの上で流し、Claude は展開した版を一時の置き場に写して `spec/bin/check_open_items_spec.rb` を流した。どちらも DB を使う spec は流していない。Claude のサブエージェントは最終報告を返さずに終わり、依頼に書かせたファイルから結果を読んだ。Codex は `--skip-git-repo-check` を付けて読み取りだけで流し、一時の失敗を起こさなかった。
